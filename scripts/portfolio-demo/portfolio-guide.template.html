01 / POSITIONING

같은 프로젝트, 다른 설명의 시작점.

지원 직무에 따라 먼저 보여줄 근거를 바꿉니다. 아래 선택은 이 프로젝트의 경험을 정리한 것이며 채용 시장 통계나 합격 가능성 평가가 아닙니다.

먼저 보여줄 근거

    모델 학습·파인튜닝·추론 엔진 최적화 경험을 직접 입증하는 프로젝트는 아닙니다. 현재 강점은 모델을 제품의 데이터·권한·상태·UI와 연결한 응용 계층에 있습니다.
    02 / SYSTEM & RESPONSIBILITY

    제안과 실행의 책임을 구분합니다.

    LLM이 제안한 구조화 지표를 서버가 검사하고 SQL로 집계합니다. 사용자는 차트·집계표·SQL을 확인한 뒤 저장합니다.

    01 → INPUT가게 · 파일 · 질문

    사용자가 출처와 원본/누적 범위를 선택합니다.

    02 → PROPOSALLLM의 도구 호출

    집계, 그룹, 기간, 차트 형태를 지표 정의로 제안합니다.

    03 → EXECUTION검증 · SQL · 결과

    소유권과 계산 조건을 확인하고 실제 데이터로 집계합니다.

    04 → REUSE검토 · 저장 · 재계산

    정의와 출처를 보관합니다. 일반 재계산에는 LLM이 필요 없습니다.

    배포 구조 · Archify · 확대 / 테마 / 노드 탐색 가능
    __ARCHITECTURE_SVG__

    기존 코드 근거가 있는 구조도를 재검증해 포함했습니다. FastAPI 자체 JWT 인증을 사용합니다. RAG는 관련 자료 탐색, 정확한 금액은 DB 집계가 담당합니다. 촬영은 파일을 직접 선택한 경로이며 RAG 검색 실행의 촬영 증거는 아닙니다.

    03 / A REPRODUCIBLE CLAIM

    “같은 기준”을 숫자로 보여주기.

    왜 파일 원본과 누적 장부를 분리했는지 설명할 때 사용하세요. 새 거래가 들어와도 원본 파일의 통계는 유지됩니다.

    파일 원본 · 8행690,200원
    누적 장부 · 8행690,200원

    막대의 기준축: 0 ~ 720,200원 · 원본 SHA-256 유지 확인

    SOURCE SCOPE IS PART OF THE DEFINITION
    차이 0원

    처음에는 같은 8개 거래를 집계하므로 두 범위의 결과가 같습니다.

    이 비교는 검증된 합성 데이터를 재현한 설명용 도표입니다. API를 호출하거나 실제 거래를 추가하지 않습니다. QA의 추가 거래는 준비 API로 1회 반영했습니다.

    04 / ENGINEERING DECISIONS

    기술 이름보다 선택의 이유를 설명하세요.

    각 선택의 이점과 감수한 비용을 같이 이야기하면, 시스템을 이해하고 있다는 근거가 됩니다.

    01 / STRUCTURED METRICS

    지표 정의를 실행 계약으로

    선택: 집계·그룹·필터를 정해진 형식으로 받고 서버가 SQL을 구성합니다.

    가치: 계산 조건과 소유권을 검증하고 동일한 정의로 다시 계산합니다.

    비용: 지원하지 않는 계산은 스키마와 컴파일러 확장이 필요합니다.

    metric_definitions.py ↗
    02 / SOURCE INTEGRITY

    원본과 누적 범위를 분리

    선택: 파일 분석 행을 보존하고 이후 거래는 연결 장부에 반영합니다.

    가치: “이 파일의 통계”가 다음 업로드 때문에 달라지지 않습니다.

    비용: 보관 공간과 범위 선택을 설명하는 UX가 필요합니다.

    file_snapshots.py ↗
    03 / DIRECT UPLOAD

    비공개 Storage로 직접 업로드

    선택: 서명 대상에 파일을 전송하고 완료 API가 크기·해시를 확인합니다.

    가치: API가 원본 파일 전체를 요청 본문으로 중계하지 않습니다.

    비용: 전송·등록 사이 실패와 미완료 업로드 정리가 필요합니다. 현재 상한은 20MiB입니다.

    direct_uploads.py ↗
    04 / RIGHT-SIZED OPERATIONS

    DB 공유 제한과 유한 배치

    선택: 현재 규모에서는 Redis 없이 DB로 공유 요청 한도와 작업 상태를 관리합니다.

    가치: 서버리스 인스턴스 간 상태를 공유하고 운영 구성 요소를 줄입니다.

    비용: 제한 검사도 DB 비용·가용성에 의존합니다. Cron은 기존 데이터 재계산이며 PG 수집이 아닙니다.

    rate_limiter.py ↗
    05 / THE INTERVIEW STORY

    HTTP 성공이어도 요청은 실패할 수 있습니다.

    오케스트레이션 직무에서는 이 사례를 가장 먼저 설명할 수 있습니다. 도구 호출의 성공과 사용자 요구 충족을 구분한 경험입니다.

    OBSERVED / 발견

    선그래프를 원했는데
    두 종류의 결과가 생성

    재계산 가능한 선그래프를 요청했지만 정적 선그래프와 재계산용 막대 지표가 함께 나왔습니다. 차트 수와 저장 버튼도 중복됐습니다.

    DIAGNOSED / 원인과 수정

    상충한 도구 지침을
    재계산 경로로 정리

    일반 차트 지침과 재계산 지표 지침이 충돌했습니다. preview_metric에 chart_type=line과 date_grain=day를 전달하고 중복 차트 생성을 피하도록 수정했습니다.

    VERIFIED / 검증

    형태 · 정의 · 숫자를
    저장 이후까지 확인

    새 가게에서 수정본으로 2회 연속 전체 흐름을 통과했습니다. 차트 1개, 일별 값, 정의, 저장·재계산을 확인했습니다. 이는 지정 시나리오의 반복 성공입니다.

    07 / APPLICATION PACKAGE

    읽는 사람이 깊이를 선택하게 구성하세요.

    첫 30초

    한 문장 소개, 사용자 문제, 실제 대시보드 화면, 공개 앱과 저장소 링크를 배치합니다.

    제품 110초

    파일 선택 → 질문 → 표·SQL 확인 → 저장·재계산을 영상으로 보여줍니다. 제출 시 별도 전달 채널이 필요합니다.

    기술 3~5분

    지원 직무에 맞는 기술 선택 2개와 실제 오케스트레이션 실패 사례를 설명합니다.

    근거 확인

    설계 코드, 실행 결과 JSON, QA 범위와 한계를 연결합니다. 원시 기록은 부록에 둡니다.

    직무별 이력서 문장 초안

    위의 직무 선택에 따라 바뀝니다. 실제로 설명할 수 있는 범위와 본인 기여에 맞춰 조정하세요.

    기여 설명: 이번 고도화는 제품 소유자의 요구·범위·디자인 결정과 Codex의 구현·검증·배포·자료 제작을 함께 진행했습니다. 모든 코드를 단독 작성했다고 설명하기보다, 본인이 결정하고 검토한 부분과 코드로 설명할 수 있는 부분을 구체적으로 밝히세요.
    08 / THREE-MINUTE WALKTHROUGH

    면접에서는 이 순서로 이야기합니다.

    00:00–00:30 · 문제와 제품

    “여러 가게의 현금·카드 매출이 파일과 장부에 흩어져 있다는 문제를 제품 가설로 잡았습니다. DATA:EZ는 파일을 보관하고 자연어로 필요한 지표를 만든 뒤, 같은 기준으로 다시 계산하는 대시보드입니다.” 실제 고객 효과를 검증한 사업 사례와는 구분합니다.

    00:30–01:15 · 실행 구조와 권한

    “LLM은 지표 정의와 도구 인자를 제안합니다. 서버가 계정·가게·출처와 컬럼을 검증하고 SQL을 구성해 정확한 값을 집계합니다. 사용자는 차트뿐 아니라 표와 SQL을 확인할 수 있습니다.” 구조도에서 API 검증 경계와 DB 집계 경로를 짚으세요.

    01:15–02:00 · 재계산과 데이터 범위

    “저장 단위에 계산 정의와 출처가 남아 일반 재계산은 LLM 없이 수행합니다. 원본 파일과 누적 장부를 구분해서, 거래 30,000원 추가 후 원본은 690,200원이고 누적 장부만 720,200원이 되는 것을 확인했습니다.” 비교 도표를 전환하며 설명하세요.

    02:00–02:40 · 실패와 평가

    “초기에는 요청한 선그래프와 재계산 정의가 서로 달랐습니다. 상충한 도구 지침을 수정하고, HTTP 성공에 더해 차트 수·유형·정의·일별 값과 저장 이후 결과를 검사했습니다. 수정본에서 새 가게로 2회 연속 전체 흐름을 통과했습니다.” 특정 시나리오의 성공을 전체 질문 정확도로 확대하지 않습니다.

    02:40–03:00 · 현재 상태와 다음 검증

    “공개 체험, 계정 격리, 실패 복구, 재접속과 영상 전달까지 검증했습니다. 다음으로는 낯선 파일과 모호한 질문의 평가 범위를 넓히고 실제 사용자가 원본/누적 구분을 이해하는지 관찰하려고 합니다. AI 코딩 도구를 활용했으며 기여와 검증 근거를 구분해 설명합니다.”

    추가 질문 · “왜 LLM이 SQL을 직접 생성하지 않나요?”

    현재 지원 범위에서는 구조화 정의가 권한·컬럼·집계 조건을 일관되게 검사하고 재계산하기에 적합했습니다. 대신 복잡한 자유 분석을 지원하려면 스키마와 컴파일러를 확장해야 합니다. 임의 SQL/Python을 실행하는 범용 환경이라고 설명하지 않습니다.

    추가 질문 · “RAG를 어디에 쓰나요?”

    관련 파일·스키마·문서 탐색에 사용합니다. 정확한 매출 계산은 구조화 데이터의 DB 집계가 담당합니다. 현재 대표 영상은 파일을 명시적으로 선택한 흐름이므로 검색 품질의 증거는 별도의 RAG 평가 문서로 제시합니다.
