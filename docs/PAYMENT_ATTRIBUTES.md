# G — 결제수단·판매채널·PG 수수료 분석

출처 등록 시 결제수단·판매채널·PG 수수료 컬럼을 선택적으로 연결한다. 연결한 값은 장부와 이벤트 비교 기록에 함께 보존되며, 자연어로 그룹별 합계·필터·미제공 건수 지표를 만들어 대시보드에 저장할 수 있다.

## 연결과 데이터 의미

장부 관리 → 출처별 파일 반영 → 새 출처 등록의 **분석에 사용할 추가 정보**에서 원본 헤더를 입력한다. 기존 일반 장부를 관리 출처로 전환할 때도 해당 장부의 컬럼을 연결할 수 있다.

| 요청의 mapping 필드 | 새 관리 장부 컬럼 | 처리 |
|---|---|---|
| payment_method_column | payment_method TEXT | 카드·간편결제 등 원본 분류값 유지 |
| channel_column | channel TEXT | 예약웹·매장 등 원본 분류값 유지 |
| fee_column | fee NUMERIC | 정확한 Decimal과 원본 부호 유지 |

연결하지 않은 속성은 분석 컬럼을 만들지 않는다. 연결한 컬럼은 이후 파일에도 있어야 하며, 행의 빈칸은 NULL(미제공)로 보존한다. 0원과 미제공은 다르다. 컬럼 중복 연결, 잘못된 숫자, 무한대 등은 원본 행·컬럼을 표시하고 파일 전체 반영을 거부한다.

수수료는 원 단위 금액이다. 취소 금액을 음수로 바꾸는 `refund` 매핑을 사용해도 수수료 부호는 원본대로 둔다. PG마다 수수료 환급 방식이 다를 수 있으므로 서버가 임의로 반전하거나 환급을 추정하지 않는다. `amount` 합계는 승인과 취소를 반영한 순결제액이며 수수료를 자동 차감하지 않는다. 정산 입금액이나 순이익과도 구분한다.

## 중복 검토와 이전 출처 호환성

동일한 거래 ID의 결제수단·채널·수수료가 바뀌거나 사라지면 내용 충돌로 판정한다. 기존 파일과 원본 행, 기존·신규 속성을 검토 화면에서 비교할 수 있으며 충돌 배치는 신규 거래까지 전부 미반영한다. 수수료 `3`과 `3.00`은 같은 값이다.

기존 6컬럼 출처는 그대로 읽고 반영한다. 새 optional 필드의 기본값 때문에 출처 재등록 요청이 다른 매핑으로 오인되지 않도록 비교 시 기본값을 정규화한다. 과거 이벤트에 미제공 속성을 임의 추가하지 않아 기존 해시도 유지한다. 기존 일반 장부 전환에서는 원본 컬럼을 유지하며 전체 행 검사와 중복 기준점에 선택 속성도 포함한다.

G 검증은 새 출처와 기존 일반 장부 전환을 대상으로 했다. 이후 [H의 과거 속성 복원](ATTRIBUTE_RESTORATION.md)에서 이미 등록한 출처에도 원본 검사를 거쳐 미연결 속성을 추가할 수 있게 했다. 자동 복원이나 이미 연결된 필드의 덮어쓰기는 하지 않는다. 같은 거래를 별도 출처에 재업로드해 합산하는 것은 해결책이 아니다.

## 자연어 지표

- “결제 분석원장의 전체 기간 결제수단별 순결제액을 막대차트로 저장하고 매시간 갱신해줘.”
- “결제 분석원장의 판매채널별 PG 수수료 합계를 대시보드에 추가해줘.”
- “카드 결제수단의 전체 기간 순결제액을 미리 보여줘.”
- “PG 수수료가 미제공인 거래 건수를 지표로 저장해줘.”

첫 두 요청은 기존 v1 지표의 `group_by`와 숫자 컬럼을 사용한다. 실제 범주값은 조회 후 필터에 사용하며, 미제공 범주는 차트에서 **미제공**으로 표시한다. API 결과에서는 NULL을 유지한다. RAG 카탈로그에는 연결된 실제 컬럼·원본 헤더·수수료 의미가 포함된다.

v1 숫자 집계(sum/avg/min/max)는 적용 기간·필터 내 숫자 누락이 있으면 422로 중단한다. 이전에는 SQL의 NULL 제외 동작으로 부분 합계가 나올 수 있었다. 이번 보완은 PG 수수료 외 일반 숫자 컬럼에도 적용한다. 실패한 갱신은 이전 정상 값과 계산 시각을 유지하고 오류를 기록한다. 건수 집계는 계속 COUNT(*)다.

필터에 `is_null` / `is_not_null`을 추가했다. 이때 `value`는 생략하거나 null이어야 한다. 기존 비교 연산자에는 문자열 value가 필요하다. 사용자가 **제공된 값만 계산**하라고 명시한 경우에만 `is_not_null`로 범위를 제한한다. 누락 오류를 해결하려고 모델이 임의로 행을 제외해 저장하도록 허용하지 않는다. v2의 각 출처 필터에도 같은 NULL 연산자를 사용할 수 있다.

## 합성 샘플 정답

기존 `01_gangnam_pg.csv`와 `03_gangnam_pg_overlap.csv`를 사용한다. 40건 최초 반영 후 겹치는 12건을 제외하고 14건을 추가하여 54건이 된다. 원본 CSV와 기존 XLSX의 선택 속성까지 동일함을 검사한다. 기대값은 앱 코드·SQL과 독립적인 `scripts/payment-eval/oracle.py`에서 표준 CSV/Decimal로 계산한다.

| 구분 | 순결제액 | PG 수수료 | 이벤트 수 |
|---|---:|---:|---:|
| 카드 | 980,000 | 29,400 | 37 |
| 간편결제 | 378,000 | 11,340 | 17 |
| 예약웹 | 736,000 | 22,080 | 27 |
| 매장 | 622,000 | 18,660 | 27 |

각 분류의 전체 합계는 순결제액 **1,358,000원**, 수수료 **40,740원**이다. 위 네 행을 모두 더하는 것이 아니라 결제수단 두 행 또는 채널 두 행을 각각 합산한다.

## 검증 재실행

2026-09-08 검증 결과:

- 전체 API 회귀 **543개 통과, skip 0개**. G 관련 22개를 추가했다. 실제 PostgreSQL에서 속성 변경 충돌·이전 매핑 재시도·원본 장부 전환·CSV/XLSX 일치·정밀 수수료·필터·저장/갱신·가게 격리·누락 시 이전 결과 보존을 확인했다.
- 프런트엔드 `tsc --noEmit`과 Next.js 운영 빌드 통과. 실제 Edge 브라우저에서 추가 매핑 입력 → 40건 반영 → 12건 중복 제외/14건 추가 → 실제 채팅의 차트 2개 저장을 확인했다. 페이지 오류는 0건이었다.
- 실제 모델 **6문항의 업무 결과 6/6 확인**: 화면의 수단별 순결제액 저장/매시간 설정, 채널별 수수료 저장/수동 설정, 카드 필터 미리보기, 수수료 전체 합계, 미제공 건수 저장, 불완전한 전체 합계 저장 거부. 자동 검사와 전체 답변·도구 인자·저장 정의 검토를 함께 했다. 단일 실행의 합성 사례 결과이며 일반 성공률 추정이 아니다.
- HTTP/DB/RAG 검증 조건 **13개 통과**. 임베딩은 text-embedding-3-small, worker/router는 프로젝트 설정 gpt-5.4/gpt-5.4-nano를 사용했다. 실제 pgvector 검색에서도 선택 속성이 포함된 원장을 찾았다. 검색 대상 1개인 이 G 사례의 top1 검사는 다양한 후보의 검색 품질 평가를 대체하지 않는다.
- 6개 모델 턴의 기록 사용량은 29호출·148,394토큰, 코드 요율 기준 약 $0.201687이다. 초기 색인과 별도 검색 검사의 호출은 제외하며 실제 청구액이 아니다. 모델 답변이 길고 기술 필드·지표 ID를 노출하는 UX는 후속 개선 대상으로 남겼다.

실행 ID는 `dataez_payment_eval_6917afdf84a04e3e8e2572935fb84c2a`이다. [전체 평가 기록](evaluations/payment-attributes-2026-09-08.json), [대시보드 화면](evaluations/payment-attributes-2026-09-08-dashboard.png), [거래 검토 화면](evaluations/payment-attributes-2026-09-08-review.png)을 보존했다. 테스트 DB는 삭제했고, 일반 웹 빌드도 복원했다. 사용자 운영 DB에는 샘플을 반영하거나 기존 매핑을 변경하지 않았다.

API 회귀 테스트는 일반 PostgreSQL과 pgvector 테스트 URL을 함께 설정한다. G 수용 스크립트는 루프백의 독립 DB를 생성하고 종료 시 삭제한다. 실제 사업자 데이터는 사용하지 않는다.

```powershell
$env:DATAEZ_TEST_DATABASE_URL='postgresql://dataez_test@127.0.0.1:55439/postgres'
$env:DATAEZ_RAG_TEST_DATABASE_URL='postgresql://dataez_test@127.0.0.1:55440/postgres'
python -m pytest api/tests -q
python scripts/payment-eval/run.py --browser
```

pytest는 `api/`에서 `python -m pytest -q`로 실행해도 된다. 테스트 DB에 필요한 권한과 Python·웹·Playwright 의존성은 E/F와 같다. `--browser`는 실제 모델 유료 호출을 사용한다. 생략하면 HTTP 적재·지표 계산·실제 임베딩 검색을 검사한다. 브라우저 실행 후 일반 웹 빌드를 복원한다. 원본 로그와 일회용 로그인 정보는 Git에서 제외한 `scripts/payment-eval/artifacts/`에 남는다.

## 남은 범위

기존 관리 출처의 속성 추가·과거 데이터 복원은 [H](ATTRIBUTE_RESTORATION.md)에서 구현했다. 여러 장부를 하나의 결제수단/채널 그룹으로 통합하기, 서로 다른 PG의 분류값 사전, 수수료 차감 같은 컬럼 간 수식 저장, PG 자동 수집, 실제 사업자 파일 파일럿은 별도 단계다. G 검증에서는 서버 주기 작업을 끄고 일정 저장과 재계산 서비스를 확인했다. 브라우저 종료 후 서버의 실제 주기 실행은 D의 검증 범위다.
