# 출처·업로드 이력 B단계

상태: **B단계 완료 당시 기록**. 이후 거래별 중복·충돌·후보 판정과 기존 장부 전환을 [C단계](EVENT_REVIEW.md)에서 구현했다. 아래 계약·제한·테스트 수치는 B 시점의 기록이다.

## 사용 흐름

1. 가게를 선택하고 제공자·가맹점 계정·자료 종류를 지정한다. 출처별로 새 결제 장부 하나를 생성한다.
2. 원본 헤더의 금액·발생일시, 선택 사항인 이벤트 ID·원거래 ID를 연결한다. 원화 결제/취소/원본 부호 유지 중 금액 해석을 선택한다.
3. CSV/XLSX/XLS 파일을 올린다. 파일 전체를 검증하고 전체 행 수·정확한 합계와 앞 5행을 보여준다. Excel은 첫 번째 시트만 지원한다.
4. 사용자가 반영 버튼을 누르면 기존 장부에 추가한다. 파일명 변경 후 같은 내용을 다시 올리면 기존 업로드 결과와 `이번 추가 0건`을 표시한다.
5. 같은 장부 ID를 사용하는 저장 지표는 수동 또는 기존 서버 일정으로 재계산한다. 장부 반영 완료와 지표 재계산 완료를 구분한다.

현재 매핑은 출처 등록 시 확정하며 변경 API가 없다. 원 단위/KRW 및 시간대가 없는 ISO 일시는 한국 시간이라는 규칙을 화면에 표시한다. 통화 컬럼의 명시적 연결은 API에서 지원하며 화면에서는 사용자가 KRW 자료임을 선언한다. 기존 일반 장부 연결, 헤더 선택형 매핑 UI, 규칙 편집은 아직 제공하지 않는다.

## 데이터와 일관성

- `ledger_sources`: 가게·사용자·제공자·계정·자료 종류, 고정 대상 장부, 매핑, 규칙 버전, 데이터 revision. namespace와 대상 장부는 DB 유일 제약으로 보호한다. 복합 외래 키가 장부의 가게·사용자 일치를 강제한다.
- `import_batches`: SHA-256, 파일명/크기/보관 키, 첫 시트 선택, 규칙 버전, 상태, 미리보기 토큰/revision, 요약/오류/완료 결과, 만료/반영 시각. `(source_id, content_hash, sheet_index, rule_version)`는 유일하다.
- `import_requests`: 출처와 요청 UUID를 업로드 배치에 연결한다. 같은 요청 키에 다른 바이트를 보내면 409다. 이름이 바뀐 동일 파일의 새 요청 키도 기존 배치에 연결된다.

상태는 `staging → uploaded → ready → committed`, 검증 오류는 `failed`, 미반영 보관 만료는 `expired`다. 매핑을 출처 생성 시 확정하므로 원안의 `needs_mapping` 상태는 이번 버전에 없다. 만료된 파일의 동일 바이트 재업로드는 같은 배치 ID를 다시 활성화하며 새 미리보기가 필요하다.

변경 요청은 출처 → 배치 순서로 잠근다. 출처 생성에는 namespace 단위 트랜잭션 advisory lock을 사용한다. **이미 반영한 배치는 미리보기 유효성 검사보다 먼저 저장된 완료 결과를 반환한다.** 새 반영은 토큰, 데이터 revision, 규칙 버전, 만료 여부를 재검사하고 저장된 원본의 해시를 확인해 다시 파싱한다. 그 뒤 원본 파일 메타데이터·거래 행·장부 row_count·출처 revision·완료 결과를 한 트랜잭션으로 저장한다. 중간 SQL 실패 시 모두 롤백되어 미리보기 상태에서 재시도할 수 있다.

완료 결과의 `result.rows_inserted`는 최초 반영 건수이고, 응답의 `rows_added`는 이번 호출의 추가 건수다. 완료 재시도는 `replayed=true`, `rows_added=0`이며 최초 결과는 바뀌지 않는다. 미리보기 합계는 Decimal의 기본 28자리 정밀도에 의존하지 않는다. 장부 조회 API도 NUMERIC을 문자열로 반환하며 화면은 TEXT ID를 숫자로 바꾸지 않는다.

같은 가게의 다른 출처에 같은 파일이 반영되어 있으면 출처 이름을 안내한다. 다른 출처의 행을 자동 제외하지 않으며, 다른 가게의 파일 일치 여부는 노출하지 않는다.

## 원본 보관과 복구

파일 객체를 쓰기 전에 UUID 기반 보관 키와 배치 예약을 DB에 확정한다. 파일명은 객체 경로에 사용하지 않는다. 쓰기 도중 프로세스가 중단되어도 예약된 키로 재시도하거나 만료 정리할 수 있다. 미반영 원본은 일반 `/files` 목록에 공개하지 않고, 완료 트랜잭션에서만 파일 메타데이터를 생성한다.

`IMPORT_CLEANUP_ENABLED=true`가 기본값이다. API 내부 작업이 60초마다 최대 20개의 기한이 지난 미반영 배치를 정리한다. 업로드/반영과 같은 출처 잠금을 사용하고, 현재 잠긴 출처는 건너뛴다. 삭제 실패는 다음 주기에 재시도하며, 로컬 파일 삭제는 검증된 staging 하위 경로만 허용한다. 완료된 원본은 자동 만료하지 않는다.

출처 장부의 일반 INSERT/UPDATE/DELETE/ALTER, 이전 append 경로, 장부 삭제와 스키마/건수 메타데이터 변경을 공통 서비스에서 409로 차단한다. 채팅 도구도 같은 오류와 화면 안내를 반환한다. 반영 이력의 원본 파일도 직접 삭제할 수 없다. 가게 삭제는 기존처럼 접근을 막는 soft delete이며, 출처 장부와 완료 원본은 일반 30일 물리 정리에서 제외한다. 복구/완전 삭제 정책은 별도 구현이 필요하다.

이 보관·재업로드 보장은 새 출처 업로드 경로에 적용된다. 기존 일반 CSV 가져오기/일반 장부의 추가 업로드까지 자동으로 관리 출처로 전환하지 않았으며, 그 경로의 과거 고아 객체 정리도 이번 단계에서 완료하지 않았다.

## API와 실행

모든 API는 인증된 현재 사용자와 가게 소속을 확인한다.

| 경로 (`/api/projects/{project_id}` 기준) | 역할 |
|---|---|
| GET/POST `/ledger-sources` | 출처 조회/생성 |
| POST `/imports` | multipart `source_id`, `request_key`(UUID), `file` |
| GET `/imports?source_id=...&limit=20&offset=0` | 페이지 단위 업로드 이력 |
| GET `/imports/{batch_id}` | 미리보기/오류/완료 결과 재조회 |
| POST `/imports/{batch_id}/preview` | 전체 원본 검증과 미리보기 토큰 생성 |
| POST `/imports/{batch_id}/commit` | JSON `preview_token`으로 반영 |

API 시작 시 `ensure_ledger_import_tables()`가 기존 프로젝트 테이블 뒤에 멱등 DDL을 실행한다. 같은 DDL을 `db/migrations/004_ledger_imports.sql`로 제공하며 테스트에서 일치를 검사한다. 별도의 PG 연동이나 새 지표 스케줄러를 요구하지 않는다. 스키마 RAG 색인은 생성/반영 후 갱신을 시도하며, 색인 실패가 성공한 반영을 실패로 뒤집지 않는다. 색인 실패의 자동 재시도 큐는 후속 범위다.

## 검증

최종 전체 Python 테스트 **468개 통과, skip 0개**. 기존 실제 PostgreSQL 13개와 B 신규 실제 PostgreSQL 31개를 포함한다. Next.js 프로덕션 빌드와 TypeScript 검사도 통과했다.

PostgreSQL 16.15를 로컬 127.0.0.1 전용 포트에서 실행했다. 각 테스트는 `dataez_import_test_<uuid>` 스키마와 임시 파일 디렉터리를 사용하고 끝나면 자기 스키마를 제거한다. 실제 사용자 DB/파일이나 OpenAI 호출은 사용하지 않았다.

확인한 사례:

- 같은 출처 생성의 동시 요청, 동일 파일의 동시 업로드/반영, 요청 키 불일치, 이름 변경 재업로드, 완료 응답 유실에 해당하는 재시도.
- 가게/사용자별 조회·업로드·미리보기·반영 차단, 다른 출처 파일 일치 안내 범위.
- 오래된 미리보기 거부, 부분 SQL 실패 시 행/파일/메타데이터 롤백, 행 번호가 있는 오류 이력.
- 파일 쓰기 후 중단의 재시도/정리, 24시간 만료와 재업로드, 반영 중 정리 작업의 잠금 경합, 완료 원본 보존.
- 긴 문자열 ID·28자리를 넘는 Decimal 합계·ID 없는 동일 행 보존, 관리 장부 REST/도구 우회 차단.
- 새 출처의 파일 반영 후 저장 지표 **250,000원**, 새 파일 50,000원 반영 후 같은 지표 **300,000원**.
- Edge headless와 실제 프로덕션 UI에서 출처 매핑, 오류 후 파일·요청 키 유지, 오래된 미리보기 후 재확인, 반영, 재업로드 0건, 이력, 가게 전환. 브라우저 API는 모의 응답이며 실제 DB 테스트와 구분한다.

재현:

```powershell
$env:DATAEZ_TEST_DATABASE_URL='postgresql://<test-user>@127.0.0.1:<port>/<test-db>'
python -m pytest api/tests -q
npm run build --prefix web
# 웹을 127.0.0.1:3100에 실행한 후
npm run check:ledger --prefix scripts/ui-eval
npm run check:import --prefix scripts/ui-eval
```

DB URL이 없으면 실제 PostgreSQL 검증은 skip한다. S3는 호출 계약만 모의 클라이언트로 검증했다. 실제 S3 계정, 사업자 파일, 실제 LLM 업무 평가, 실제 DB를 연결한 브라우저 종합 시연은 미수행이다.

## 다음 C단계

`import_rows`와 `source_events`를 추가해 다른 파일 사이의 확정 중복·내용 충돌·ID 없는 후보를 구분하고 행별 원본과 연결한다. 부분 취소 이벤트를 보존하며, 기존 장부의 전체 기준점 검사와 명시적 전환 절차를 구현한다. 현재 B 장부에 이미 반영된 행도 C 레지스트리를 생성하기 전에는 이벤트 중복 검증 완료로 간주하지 않는다.
