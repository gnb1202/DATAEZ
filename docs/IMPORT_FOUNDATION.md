# 업로드 신뢰성 A단계 — 구현과 검증

상태: **A단계 구현·기술 검증 완료**. 이후 신규 출처의 동일 파일 재반영 방지는 [B단계](LEDGER_IMPORTS.md), 같은 출처의 파일 간 이벤트 중복 판정은 [C단계](EVENT_REVIEW.md)에서 구현했다. 아래 테스트 수치는 A 완료 당시 기록이며, 실제 사업자 파일과 실제 LLM 업무 평가는 아직 수행하지 않았다.

## 원문 읽기와 검증

`data_import.py`를 원문 읽기, 전체 값 검증, 트랜잭션 내 저장으로 분리했다. 기존 REST 업로드·추가 업로드와 챗봇 `import_file`이 같은 저장 서비스를 사용한다.

- CSV를 먼저 문자열로 읽어 선행 0, 긴 숫자 ID, 대소문자, `NA`/`NULL` 문자열을 보존한다. 빈 셀만 결측값으로 처리한다. ID/번호/코드 등의 헤더와 선행 0 패턴을 보수적으로 인식하며, 임의의 헤더가 ID인지 자동으로 보장하지는 않는다.
- 금액은 Decimal, 정수는 정확한 정수로 변환한다. 소수를 정수로 자르거나 NUMERIC 컬럼에 맞춰 조용히 반올림하지 않는다. 새 숫자 컬럼의 범위는 전체 행에서 결정한다.
- UTF-8 BOM·CP949 CSV, 여러 줄 셀과 원본 행 번호를 지원한다. 잘못된 CSV 구조를 다른 인코딩으로 재해석하지 않는다.
- XLSX 숫자는 XML에 저장된 숫자 문자열에서 읽는다. 숫자로 저장된 ID는 원본에서 텍스트로 제공하도록 안내한다. XLSX 수식·오류 셀은 거부한다.
- XLS는 xlrd로 읽는다. 원본의 이진 숫자나 Excel에서 이미 손실된 ID·정밀도를 복원하지 않는다. 현재 Excel은 첫 시트를 읽으며 시트 선택은 후속 출처 설정 범위다.
- 추가 파일의 컬럼 누락·추가, 타입 오류, 정밀도 손실은 전체 반영을 중단한다. 컬럼을 찾지 못했다고 빈값을 넣지 않는다.
- 새 장부의 `columns_schema`에 원래 헤더와 반복 순서를 보존한다. 특수문자 정리 후 이름이 겹치는 컬럼도 다음 파일의 순서가 바뀌면 원본 이름으로 연결한다. 내보낸 정규 컬럼 이름으로 재업로드하는 흐름도 지원한다. 매핑이 없는 과거 장부에서 이름이 모호하면 추가를 거부한다.

일반 장부의 자동 타입 추론은 결제 의미 검증이 아니다. 숫자·문자가 섞인 컬럼은 TEXT일 수 있다. 일반 파일의 통화·단위·취소 의미를 추측하지 않는다.

## 원자적 저장과 오류 표시

`table_imports.py`에서 새 장부의 파일 메타데이터, 실제 테이블·행, 장부 메타데이터를 한 DB 트랜잭션으로 저장한다. 중간 실패는 모두 롤백한다. 기존 물리 테이블에 데이터를 섞지 않도록 CREATE TABLE 충돌도 오류로 처리한다.

추가 업로드는 장부 메타데이터를 잠근 뒤 현재 스키마로 검증하고, 행과 row_count를 같은 트랜잭션에서 반영한다. 현재 row_count에 실제 추가분을 더하므로 동시 추가 요청이 서로의 행 수를 덮어쓰지 않는다. `write_import`는 호출자가 넘긴 커서를 사용하고 자체 연결이나 commit을 하지 않는다.

REST와 챗봇 서비스 모두 사용자·가게·장부의 소속을 재검증한다. REST 신규/추가 업로드의 크기·확장자·업로드 제한을 동일하게 적용한다. 검증 오류는 HTTP 422의 `detail`, `code=import_validation_error`, `issues`로 반환한다. issues에는 원본 행·컬럼·원인이 들어가며 최대 50개를 반환한다.

예: `3행 amount: 정수 컬럼에 소수를 저장할 수 없습니다.` 업로드 창은 오류가 나도 닫히지 않고 파일과 이름을 유지한다. 챗봇도 구조화된 오류를 받아 반영 성공으로 보고하지 않는다. 저장 후 검색 인덱스 갱신 실패를 파일 적재 실패로 반환하지 않는다.

파일 객체 저장은 DB 트랜잭션 밖이므로 실패 후 참조되지 않는 파일 객체가 남을 수 있다. 모호한 commit 실패에서 참조된 파일까지 삭제하지 않도록 자동 삭제하지 않는다. 배치 상태·만료·정리와 인덱스 재시도 관리는 후속 작업이다.

## 명시적 결제 매핑 기반

`payment_imports.py`의 `PaymentImportMapping`과 `prepare_payment_import`는 B단계 출처 서비스에서 사용할 어댑터다. A단계에서 일반 업로드 화면에 출처 매핑 UI나 새 API를 추가한 것은 아니다.

ID·원거래 ID·금액·발생일·통화 컬럼을 지정하면 `event_id / original_event_id / event_kind / amount / occurred_at / currency`로 정규화한다. 이름과 무관하게 지정된 ID를 문자열로 보존한다. ID가 없는 이벤트도 유지하고, `payment/refund/signed`를 구분한다. 별도 취소는 절댓값을 차감하며 원거래 ID가 같은 두 부분 취소도 각각 보존한다.

KRW·Asia/Seoul과 명확한 ISO 날짜를 지원한다. 시간대 없는 시각은 서울 시간으로 해석한다. 통화 컬럼을 연결하면 KRW 불일치를 거부한다. 연결하지 않으면 매핑이 원화임을 선언한 것으로 취급하며 자동 통화 감지를 주장하지 않는다. 금액 누락·모호한 날짜·비정상 숫자·연결된 ID 누락은 오류다.

## 검증 결과와 재현

- 전체 Python 테스트 **435개 통과**, 실제 테스트 DB URL을 지정하여 skip 없이 실행했다. 이 중 실제 PostgreSQL 테스트는 기존 지표 5개 + 새 적재 8개 = **13개**다.
- PostgreSQL 16.15 / Windows x64, 127.0.0.1의 독립 테스트 인스턴스. 테스트마다 고유 스키마를 만들고 제거했다. 설치형 서비스나 운영 데이터는 사용하지 않았다.
- 정확한 소수·ID 보존, 메타데이터 저장 실패 롤백, executemany 일부 실행 후 전체 롤백, 두 연결의 동시 추가, 다른 가게 차단, 실제 HTTP 422 응답을 확인했다.
- 실제 파일 적재 → 현금 100,000 + 카드 200,000 − 취소 50,000 = **250,000원** → 새 현금 50,000 추가 → 저장 지표 갱신 **300,000원**을 확인했다. 부분 취소와 월 경계도 TIMESTAMPTZ 저장 후 검증했다.
- Next.js 프로덕션 빌드·TypeScript 검사 통과. 실제 브라우저에서는 모의 API로 오류 표시·선택 유지·재시도를 검증했다. 실제 DB를 연결한 브라우저 업무 시연은 D단계에 남아 있다.

테스트 환경은 [PostgreSQL 공식 Windows 안내](https://www.postgresql.org/download/windows/)에서 연결한 [EDB 바이너리](https://www.enterprisedb.com/download-postgresql-binaries?lang=en)를 사용했다. 실행 파일과 테스트 클러스터는 git에서 제외한 `.local-test/` 아래에 두었다.

```powershell
# 별도 개발/테스트 PostgreSQL DB를 사용한다. Docker는 필수 조건이 아니다.
cd api
$env:DATAEZ_TEST_DATABASE_URL = 'postgresql://test:test@127.0.0.1:5432/test'
python -m pytest tests/ -q
```

DB URL이 없으면 실제 DB 테스트 13개는 skip한다. PGlite 테스트 의존성은 저장소 루트에서 `npm ci --prefix scripts/sql-eval`로 준비한다. 웹 서버 실행 후 `npm run check:import --prefix scripts/ui-eval`로 모의 API 브라우저 검증을 실행한다.
