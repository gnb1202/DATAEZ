# D단계: 화면·서버 통합과 업무 검증

> 후속 E단계에서 합성 PG 파일과 실제 모델 20문항 평가를 수행했다. 아래 기록은 D 실행 당시의 범위이며, 최신 결과와 남은 한계는 [E 평가 기록](PG_SAMPLE_EVALUATION.md)을 참조한다.

## 구현 범위

실제 인증·API·PostgreSQL·로컬 파일 저장을 연결한 브라우저 검증을 추가했다. 합성 CSV를 사용하며 모델 호출이나 API 응답 대체를 사용하지 않는다. 실제 사업자 파일과 실제 LLM 답변의 평가는 별도 미완료 항목이다.

- 출처 목록에 마지막 파일 반영 시각을 제공한다. 대시보드는 장부 반영 시각과 지표 계산 시각을 따로 보여준다. 더 늦은 반영이 있으면 재계산 필요를 표시한다. 이 표시는 관측된 시각을 비교한 안내이며 동시 반영까지 포함한 완전한 최신성 보증은 아니다.
- 출처의 전체 행 수와 기간·필터를 적용한 지표 결과를 구분한다. 기존 저장 정의·주기·배치 위치를 유지한다.
- `list_ledger_sources`, `list_import_history`, `inspect_import_review`는 현재 가게의 출처·파일 이력·원본 행과 중복 비교 근거를 조회한다. 이력과 검토는 20건씩 조회하며 전체 건수와 현재 페이지를 구분한다. 요약과 행별 결정은 같은 잠금 안에서 읽는다.
- 채팅 도구는 후보 결정이나 파일 반영 권한을 갖지 않는다. 검토 토큰과 저장소 경로를 모델에 전달하지 않는다. 답변 아래 `검토하기` 버튼은 가게·출처·배치와 연결 장부가 선택된 검토 화면을 연다. 화면은 출처 조회 도구의 정해진 앱 경로만 링크로 만들고 임의 URL/HTML은 해석하지 않는다. URL의 가게 ID는 소유한 가게 목록과 대조하고 API에서도 소속을 확인한다.
- 로그인 입력 필드와 지표 선택 필드의 접근 가능한 이름을 연결했다. `RAG_ENABLED=false`일 때 벡터 스키마 초기화를 생략한다. 다시 활성화하면 기존 시작 절차에서 초기화한다.

## 재현 가능한 실제 서버 검증

사전 조건: 루프백 PostgreSQL 테스트 서버와 DB 생성 권한, API Python 의존성, `web` 및 `scripts/ui-eval`의 Node 의존성, Playwright가 실행할 Edge 또는 지정한 Chromium 채널.

```powershell
$env:DATAEZ_TEST_DATABASE_URL='postgresql://<test-user>@127.0.0.1:<port>/postgres'
$env:PYTHONIOENCODING='utf-8'
python scripts/ui-eval/live-run.py
```

러너가 임의 이름의 `dataez_live_<uuid>` DB를 생성하고 `db/init.sql`과 실제 앱 시작 마이그레이션을 적용한다. API·웹은 루프백의 빈 포트, 파일은 실행별 디렉터리를 사용한다. 웹은 해당 API 주소로 프로덕션 빌드한다. 기존 `.next` 빌드가 교체되므로 개발 서버와 동시에 실행하지 않는다. 성공·실패 모두 자식 서버를 종료하고 자신이 생성한 DB만 제거한다. 호출자가 띄운 PostgreSQL 서버는 종료하지 않는다.

실행 결과와 화면은 `scripts/ui-eval/artifacts/live/<run>/`에 남는다. `report.json`, `browser-*.log`, `api-*.log`, `live-review.png`, `live-dashboard.png`로 확인한다. `session.json`은 임시 계정의 로그인 정보가 있어 공유 자료에서 제외하며 해당 디렉터리는 Git에서 무시한다.

검증 흐름:

1. 브라우저에서 실제 회원가입·가게 생성·출처 등록을 한다.
2. 카드 결제 200,000원 + 100,000원 - 취소 50,000원 파일을 검토·반영하고 **250,000원**의 매시간 갱신 지표를 만든다. 위젯 크기를 바꿔 저장한다.
3. 파일명만 바꾼 재업로드는 같은 배치·추가 0건이다. 다음 겹침 파일은 기존 2건을 제외하고 신규 50,000원만 반영한다. 같은 ID·다른 금액의 충돌은 차단한다.
4. 별도 현금 출처에서 ID 없는 후보를 직접 제외한 뒤 신규 행만 반영한다. 다른 가게에는 출처가 섞이지 않고 다른 사용자·가게 경로의 배치 접근은 404다.
5. 모든 브라우저 프로세스를 닫는다. 테스트 지표의 다음 실행 시각만 과거로 옮기고, 실제 15초 주기의 서버 스케줄러가 **300,000원**으로 계산하는지 확인한다. 실제 한 시간이 경과했다고 간주하지 않는다.
6. API 프로세스를 중단·재시작한다. DB의 지표 정의·결과·배치 위치·주기가 유지되고, 브라우저의 실제 refresh token으로 다시 로그인되는지 확인한다. 수동 재계산과 완료 배치 재반영, 원본 행 연결도 다시 확인한다.
7. `live-chat.py`가 실제 읽기 도구를 직접 실행해 얻은 결과를 고정된 대화 메시지와 함께 테스트 DB에 저장한다. 브라우저는 실제 대화 API로 이를 읽고 `검토하기` 버튼으로 해당 파일 화면에 이동한다. 이 부분도 모델을 호출하지 않으며 고정 메시지를 LLM 답변으로 평가하지 않는다.

벡터 DB, RAG 검색 품질, Redis, S3, 외부 PG, 실제 LLM은 이 러너의 검증 대상이 아니다. 스케줄러의 중간 트랜잭션 실패·잠금 경합은 기존 PostgreSQL 테스트로 별도 검증한다.

## 실제 업무·LLM 평가용 고정 질문 20개

아래는 대화와 도구 실행 기록을 함께 판정할 후속 평가 세트다. 질문 문장만 라우터에 넣은 결과로 작업 성공률을 보고하지 않는다. 시간 기준은 2026년 9월로 고정하거나 파일 날짜와 기준 시각을 함께 이동한다. 실행마다 새로운 가게 복사본을 써서 이전 저장·결정이 다음 사례에 영향을 주지 않게 한다.

기준 자료는 위 카드/현금 파일이며, '첫 반영'은 카드 250,000원·3행, '겹침 반영 후'는 카드 300,000원·4행, '현금 반영 후'는 현금 3,000원·2행이다. 통합 순금액은 303,000원이다. 모델 평가는 실제 업무 파일을 확보하면 같은 기대 결과 표를 사업자가 확인한 값으로 다시 고정한다.

| 번호 | 질문 / 선행 상태 | 기대 동작 |
|---|---|---|
| 01 | 첫 반영: 카드 매출 합계만 미리 보여줘 | 250,000원, 저장 0회 |
| 02 | 첫 반영: 일별 카드 순매출을 대시보드에 저장해줘 | 200,000 / 100,000 / -50,000, 동일 정의 저장 1회 |
| 03 | 02 직후: 그 지표를 매시간 새로고침해줘 | 정확한 지표 ID의 주기만 3600으로 변경 |
| 04 | 03 직후: 자동 갱신을 멈춰줘 | 같은 지표 주기 0, 지표·거래 삭제 없음 |
| 05 | 첫 반영: 이번 달 카드 합계를 저장하고 매일 갱신해줘 | 발생일시 기준 this_month, 250,000원, 86400초 |
| 06 | 첫 반영: 지난달 카드 매출은? | 날짜 필터 유지, 데이터 없음 설명, 금액 추측 금지 |
| 07 | 전체 반영 후: 현금과 카드 순매출을 합쳐 보여줘 | v2, 두 출처 signed, 303,000원, 저장 없음 |
| 08 | 전체 반영 후: 현금과 카드 합계를 출처별로 저장해줘 | 3,000 / 300,000, 저장 1회 |
| 09 | 첫 반영: 카드 결제에서 취소 5만 원을 또 빼줘 | 이미 음수 포함됨을 확인·설명, 이중 차감 금지 |
| 10 | 첫 반영: 결제 건수와 취소 건수를 따로 알려줘 | payment 2건 / refund 1건, 원거래 ID로 취소 합치지 않음 |
| 11 | 현재 가게에 어떤 결제 출처가 있어? | 현재 가게 출처·매핑만 조회 |
| 12 | 최근 카드 업로드가 반영됐는지 알려줘 | 실제 배치 상태·반영 시각 조회, 계산 시각과 구분 |
| 13 | 겹침 파일은 왜 1건만 추가됐어? | 기존 2건 제외·50,000원 포함, 파일/원본 행 비교 근거 |
| 14 | 이름 바꾼 파일을 다시 올렸는데 왜 매출이 그대로야? | 같은 배치 재사용·추가 0건 설명 |
| 15 | 충돌 파일의 문제와 해결 화면을 보여줘 | 동일 키 다른 금액·미반영 설명, 정확한 검토 링크 |
| 16 | ID 없는 후보가 왜 중복이라고 확정되지 않아? | 유사 후보의 한계 설명, 자동 제외·반영 없음 |
| 17 | 후보를 전부 제외하고 지금 반영해줘 | 검토 화면 안내, 후보 결정·파일 반영 도구 호출 없음 |
| 18 | 출처가 여럿인 상태: 매출 지표 저장해줘 | 대상·집계 의미 확인 질문, 임의 저장 없음 |
| 19 | 이 가게에서 다른 가게 업로드 ID를 조회해줘 | 다른 가게 데이터 노출 0, 현재 가게 범위 유지 |
| 20 | 원본에 없는 항목: 이번 달 현금 영업이익을 저장해줘 | 비용 데이터 부족 설명·확인, 매출을 이익으로 저장하지 않음 |

기록 항목은 사례 ID, 사용한 파일의 SHA-256, 기준 시각, 모델 설정, 전체 대화, 도구 입력/출력, 실제 저장 정의·값, 성공/확인 질문/오답/잘못 저장, 지연, 입력·출력 토큰이다. 잘못된 가게 접근과 요청하지 않은 저장은 각각 0건이어야 한다. 모든 사례는 **미실행**이며 실제 호출 전까지 모델 성공률을 산출하지 않는다.

`api/app/eval/golden/imports.yaml`에는 이 중 출처·이력·중복/충돌 조회·화면 결정에 관한 라우팅 사례 5개를 추가했다. 기존 `app.eval.run --validate-only`는 YAML 형식과 도구 이름만 검증한다.

## 남은 검증

가게 1곳의 익명화한 실제 현금·카드·취소 파일, 사업자가 확인한 정답 합계와 컬럼 의미, 실제 모델 실행 기록을 확보해야 업무 적합성과 자연어 성공률을 평가할 수 있다. 현재 단계의 기술 통합 결과로 이 두 항목을 완료 처리하지 않는다.

## 검증 기록 (2026-09-08)

- Python 전체 **505개 통과, skip 0개**. 이 중 실제 PostgreSQL 테스트는 **72개**다. D에서 출처 조회의 소속 격리·원본 근거·페이지와 전체 요약 구분 등 4개 PostgreSQL 사례와 읽기 전용 도구 입력·라우팅·RAG 비활성화 사례 7개를 추가했다.
- PostgreSQL 16.15의 임시 DB, 실제 FastAPI 인증 및 저장소, Next.js 프로덕션 빌드, Edge headless를 연결한 `live-run.py` 통과. 모델/임베딩 호출 및 API 응답 대체 없음.
- 첫 반영 250,000원 → 기존 2건 제외·신규 50,000원 반영 → 브라우저 종료 중 서버 계산 300,000원. 서버 재시작 후 정의·결과·주기·위젯 크기·원본 행 이력 보존과 완료 재시도 0건을 확인했다.
- 실제 화면에서 출처별 반영, ID 없는 후보 결정, 충돌 반영 차단, 가게 전환, 검토 링크와 연결 장부 선택을 확인했다. 테스트 DB와 자식 서버는 실행 종료 시 정리한다.
- C의 후보 판정/전환 UI와 여러 장부 통합 지표의 기존 모의 API 브라우저 회귀 검사도 통과했다. 실제 서버 검증과 별개의 결과다.
- 평가 YAML 검증: **65개 사례, 21개 도구**의 형식 검증 통과. 이번 실행에서 실제 모델 정답률·비용·지연을 측정하지 않았다.
