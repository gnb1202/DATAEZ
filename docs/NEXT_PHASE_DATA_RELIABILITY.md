# 다음 페이즈 — 반복 업로드와 결제 데이터 신뢰성

상태: **A/B/C/D 구현·기술 통합 검증, E의 합성 PG 실제 모델 반복 평가, F의 실제 RAG·채팅 저장, G의 선택 속성 보존·분류별 지표, H의 기존 출처 속성 복원 검증 완료. 실제 사업자 파일 검증은 미완료**. 기록은 [A](IMPORT_FOUNDATION.md), [B](LEDGER_IMPORTS.md), [C](EVENT_REVIEW.md), [D](INTEGRATED_ACCEPTANCE.md), [E](PG_SAMPLE_EVALUATION.md), [F](RAG_ACCEPTANCE.md), [G](PAYMENT_ATTRIBUTES.md), [H](ATTRIBUTE_RESTORATION.md)를 참고한다. 아래는 원래 설계이며 실제 계약과 제한은 각 구현 문서가 우선한다.

## 목표와 대표 흐름

**같은 가게의 같은 출처에서 받은 파일을 반복 업로드해도 결제액이 늘어나지 않고, 새 거래만 기존 지표에 반영되게 한다.** 사용자는 반영된 행과 제외된 행의 이유를 확인할 수 있어야 한다.

대표 흐름은 `가게 선택 → 기존 출처 선택 → 파일 업로드 → 컬럼 연결 → 신규/중복/충돌 미리보기 → 반영 → 저장 지표 재계산`이다. 예를 들어 카드 파일을 다시 올리면 추가 거래는 0건이고, 다음 파일에 새로운 결제 5만 원이 있으면 기존 순결제액 25만 원이 30만 원으로 바뀐다.

이번 페이즈의 완료는 코드 작성뿐 아니라 실제 PostgreSQL에 연결한 업로드·갱신 검증을 포함한다. 실제 사업자 파일이 준비되지 않으면 합성 파일로 개발과 기술 검증을 진행하되, 실제 업무 검증은 미완료로 기록한다. 일정 대신 아래 A→D의 완료 기준으로 진행한다.

## 현재 코드에서 확인한 출발점

| 현재 구조 | 다음 구현에 미치는 영향 |
|---|---|
| `main.py::api_import_table`은 매번 새 file ID와 table ID를 만든다. | 동일 파일을 재업로드해도 현재 `source_file_id` 검사로는 잡을 수 없다. 파일 내용 해시와 출처 연결이 필요하다. |
| `data_import.py::append_csv_to_table`은 전달된 모든 행을 INSERT한다. | 겹치는 기간 파일을 추가하면 같은 거래가 다시 들어갈 수 있다. |
| 추가 업로드 경로는 원본 파일·배치별 행 이력을 남기지 않는다. | 지표에서 어떤 업로드의 거래가 포함됐는지 추적할 수 없다. |
| `_cast_value`는 NUMERIC에 float, BIGINT에 `int(float(...))`를 사용한다. | 집계 전 적재 단계에서 금액이나 긴 ID가 손상될 수 있다. 지표의 Decimal 보존만으로는 충분하지 않다. |
| v2 지표는 저장된 table ID 2~5개를 `UNION ALL`로 집계한다. | 중복 처리는 적재 단계에 두고 기존 table ID를 유지한다. 지표마다 다른 중복 판단을 하지 않는다. |
| PostgreSQL 서버 연결 테스트 5개와 실제 LLM 검증이 남아 있다. | 기존 PGlite/모의 API 검증과 구분해 실제 연결 증거를 확보한다. |

위 표는 계획 작성 당시의 문제를 기록한 것이다. A 구현 후 원문 파싱·적재 트랜잭션·실제 PostgreSQL 검증 기반은 보완했다. 이전 지표 페이즈 기록은 [지표 구현 문서](METRIC_IMPLEMENTATION.md), 최신 검증은 [A단계 문서](IMPORT_FOUNDATION.md)를 참고한다.

## 제품 범위와 계산 규칙

첫 대상은 **원화 결제·취소 이벤트 파일**이다. 예약 현황, 정산 입금, 최종 상태만 담긴 거래 목록을 결제 이벤트로 자동 해석하지 않는다. 파일의 단위가 불명확하면 출처 설정에서 먼저 확인한다.

출처는 파일명과 다르다. 예를 들어 `강남점 / 카드사 A / 가맹점 계정 1 / 결제 이벤트`가 하나의 출처이고, 9월 1일 파일과 9월 8일 파일은 그 출처의 업로드 배치다. 같은 출처는 하나의 기존 장부에 계속 추가한다. 같은 ID라도 가게·결제 제공자·가맹점 계정이 다르면 별개 거래다.

| 상황 | 처리 |
|---|---|
| 같은 출처·시트·파싱 규칙으로 이미 반영한 동일 바이트 파일 | 기존 반영 결과를 반환하고 추가 행은 0건으로 표시한다. 파일명이 달라도 같다. |
| 같은 출처에서 이벤트 키와 정규화된 내용이 동일 | 확정 중복으로 분류해 신규 적재에서 제외한다. 원본 파일은 보존한다. |
| 같은 이벤트 키인데 금액·통화·발생일 등 계산 내용이 다름 | 충돌로 표시한다. 먼저/나중 파일을 임의로 선택하거나 덮어쓰지 않는다. |
| 결제 ID는 같지만 부분 취소 이벤트 ID가 다름 | 서로 다른 취소로 보존한다. 두 부분 취소를 하나로 줄이지 않는다. |
| 거래 ID가 없고 날짜·금액·결제수단만 비슷함 | 중복 후보로 표시한다. 자동 제외하지 않으며 반영 전에 사용자가 포함/제외를 결정한다. |
| 날짜·금액은 같지만 이벤트 ID가 다름 | 별개 거래로 포함한다. |
| 같은 파일 내용이 다른 출처에도 있음 | 같은 가게 안에서 출처 중복 후보를 보여준다. 내용 해시만으로 다른 계정의 거래까지 확정 중복으로 판단하지 않는다. |
| 금액 누락, 모호한 날짜, 잘못된 통화·단위 | 오류 행과 이유를 보여주고 전체 반영을 막는다. 정상 행만 몰래 반영하지 않는다. |

자동 중복 판정 키는 `(가게, 출처 namespace, 이벤트 종류, 이벤트 ID)`로 한다. 출처에 속한 사용자도 서버에서 검증한다. 원거래 ID와 취소 이벤트 ID는 별도 필드다. 취소에 독립된 이벤트 ID가 없으면 원거래 ID 하나로 중복을 확정하지 않는다.

이벤트 ID는 문자열로 읽고 선행 0과 대소문자를 보존한다. 금액은 명시된 단위로 Decimal 파싱하며 float를 거치지 않는다. 날짜 형식과 시간대는 출처 규칙에 저장한다. 원본 스프레드시트에서 이미 손실된 숫자 ID나 선행 0을 추측해 복원하지 않는다.

중복 키가 없는 출처는 동일 파일 재업로드 방지는 제공하되, 파일 간 확정 중복 제거는 제공하지 않는다. 첫 파일 안에 반복된 행도 동일한 판정 규칙으로 검사한다. 후보 판정은 이유를 제시하는 보조 기능이며 LLM의 판단을 최종 제외 규칙으로 사용하지 않는다.

## A. 적재 규칙과 실제 DB 검증 기반

첫 작업은 기존 import/append 경로를 **파싱·검증·저장**으로 나누고, 호출자가 넘긴 DB 트랜잭션 안에서 저장할 수 있게 하는 것이다. 현재 함수마다 별도로 commit하므로 배치 이력과 실제 행을 함께 반영할 수 없다.

산출물:

- 출처 매핑: 이벤트 ID, 이벤트 종류, 원거래 ID, 금액, 통화/단위, 발생일·시간대. 취소는 기존 `signed/refund` 의미와 일치시킨다.
- 원문을 보존하는 ID/금액 파서와 행 번호가 포함된 검증 오류. 기존 일반 장부 가져오기와의 호환성을 검사한다.
- 업로드·추가 업로드 모두 동일한 파일 크기·확장자·권한 검증을 사용한다.
- 현금/카드/취소 합성 파일, 기대 금액, 원본 행 번호, 월 경계·부분 취소·ID 없는 파일의 기대 판정을 함께 고정한다.
- 기존 실제 PostgreSQL 테스트 실행 환경과 v2 통합 집계 테스트. Docker 사용 여부와 무관하게 별도 테스트 DB URL로 실행할 수 있어야 한다.

완료 기준: 실제 PostgreSQL에 저장한 금액과 ID가 원문 규칙대로 보존되고, 현금 10만 + 카드 20만 − 취소 5만 = 25만 원이 재현된다. 실패한 적재는 장부 행과 메타데이터를 일부만 남기지 않는다.

## B. 출처·업로드 이력과 동일 파일 재반영 방지

파일을 기존 출처에 연결하는 모델을 추가한다. 새 출처는 사용자가 의미와 대상 가게를 지정하며, 파일명을 보고 서버가 임의로 기존 출처를 선택하지 않는다. 기존 장부를 연결할 때는 현재 행 전체의 기준점 검사가 선행되어야 한다.

제안 데이터 모델:

| 모델 | 핵심 정보와 제약 |
|---|---|
| `ledger_sources` | 소유자, 가게, 제공자/계정 namespace, 대상 table ID, 매핑 및 규칙 버전, 데이터 revision. 출처당 대상 장부 하나, 장부당 관리 출처 하나. |
| `import_batches` | 출처, 원본 file ID, SHA-256, 시트 선택, 규칙 버전, 요청 멱등 키, 상태, 미리보기 revision, 반영/중복/충돌/오류 건수와 계산 금액. |
| `import_rows` | 배치 ID, 시트·행 번호, 정규화된 내용, 이벤트 키·내용 해시, 판정/이유, 연결된 대상 행 ID. 신규·중복·제외 모두 추적한다. |
| `source_events` | 출처·종류·이벤트 ID의 유일 키, 정규화된 내용 해시, 최초 반영 배치와 대상 행 ID. 동일 키의 동시 적재를 DB에서 차단한다. |

ID가 없는 행은 `source_events`의 확정 이벤트 키를 만들지 않고 `import_rows`와 대상 행 연결로 추적한다. 새 요청을 이전 요청으로 오인하지 않도록 파일 내용 해시와 요청 멱등 키의 역할을 분리한다. 동일 파일 판단에는 출처·시트·규칙 버전도 포함한다.

상태는 `uploaded → needs_mapping → ready → committed`를 기본으로 하고 `failed / expired`를 기록한다. 미리보기 후 데이터나 매핑이 바뀌면 기존 미리보기를 무효화하고 다시 검사한다. 원본 파일 보관은 DB와 같은 트랜잭션이 아니므로 미완료 배치의 파일 정리·만료 정책을 함께 구현한다. 해시 검색 결과는 현재 사용자의 현재 가게 범위에서만 반환한다.

완료 기준: 같은 파일과 같은 요청을 반복해도 같은 반영 결과를 반환한다. 다른 가게의 같은 파일은 독립적으로 처리된다. 프로세스 실패 후 재요청에도 반영된 거래가 두 번 들어가지 않는다.

## C. 이벤트 중복 판정과 원자적 반영

미리보기는 파일의 신규·확정 중복·중복 후보·충돌·오류를 분류하고 포함 예정 금액을 보여준다. 후보에는 판단 근거와 기존 행 위치를 제공한다. 사용자가 결정하지 않은 후보, 충돌, 오류가 남으면 반영 버튼을 활성화하지 않는다. 첫 버전은 충돌 거래의 정정·기존 행 대체를 지원하지 않는다. 충돌이 해소되지 않은 배치는 반영 실패 상태로 남는다.

확정 반영 시에는 출처 행을 잠그고 소유권, 대상 장부, 규칙 버전, 데이터 revision, 기존 이벤트 키를 다시 검사한다. 미리보기의 전제가 바뀌면 `409`와 재검사 안내를 반환한다. 이미 성공한 요청의 재시도는 이 검사보다 먼저 저장된 완료 결과를 반환한다.

한 DB 트랜잭션에서 신규 장부 행, `source_events`, 행별 판정, 장부 row_count, 출처 revision, 배치 완료 상태를 함께 기록한다. 같은 키·같은 내용은 중복이고, 같은 키·다른 내용은 충돌이다. 유일 키 충돌을 모두 무시하는 `ON CONFLICT DO NOTHING`만으로 처리하지 않는다.

관리 대상으로 연결된 장부는 일반 CRUD나 이전 append 경로로 우회 변경할 수 없게 한다. 이벤트 키·금액·일시를 임의 수정하면 중복 레지스트리와 실제 집계가 달라지기 때문이다. REST와 에이전트 도구 모두 같은 서비스에서 이 경계를 검증한다. 기존 일반 장부와 현금 수기 입력은 유지하며, 관리 장부 전환은 별도 명시적 절차로 제공한다. 삭제된 출처·장부의 재사용도 복구/재연결 절차를 거친다.

기존 데이터 전환은 원본 행을 삭제하지 않고 전체 행을 검사해 기준점을 생성한다. 기존 중복·충돌이 있으면 해결 전까지 관리 전환을 완료하지 않는다. 검증되지 않은 과거 장부를 자동으로 '중복 검증 완료'로 표시하지 않는다.

완료 기준: 같은 출처에 겹치는 두 배치를 동시에 반영해도 확정 이벤트는 한 번만 들어간다. 두 부분 취소는 각각 보존되고, 충돌 배치 실패 시 마지막 정상 지표와 원본 거래가 유지된다.

## D. 화면·지표 연결과 실제 업무 검증

업로드 화면에 기존 출처/새 출처 선택, 컬럼 매핑, 검증 요약, 행별 문제, 반영 결과를 연결한다. '중복 3건'만 보여주지 말고 어떤 기존 파일의 어느 행과 같은지 확인할 수 있게 한다. 모든 원본 행은 하나의 판정에 속하며, 표시 건수의 합이 원본 행 수와 같아야 한다.

예시 표시: `총 103행 · 신규 95 · 확정 중복 5 · 확인 필요 2 · 오류 1`. 오류나 미결정 후보가 남은 동안 반영하지 않는다. 오류를 수정하고 후보 2건도 신규로 확정했다면 최종 결과는 `추가 98행 / 중복 제외 5행`이다. 최종 결정과 실제 저장 결과를 일치시키며, 제외가 발생하면 그 이유와 금액을 함께 제공한다.

저장 지표의 table ID와 v1/v2 정의를 유지하므로 신규 반영분은 기존 수동/주기 갱신으로 계산한다. 화면에는 '장부 반영 완료'와 '지표 재계산 완료'를 별도로 표시한다. 이번 페이즈에서 새 스케줄러를 만들지 않는다. 출처 기준 전체 이벤트 수·금액과 지표의 기간/필터 적용 결과도 구분한다.

채팅은 출처와 검증 결과를 조회·설명하고 문제 화면으로 연결할 수 있다. 파일 반영과 중복 후보 결정은 첫 버전에서 검증 화면을 통해 수행한다. 기존 자연어 지표 생성은 그대로 이용하고, LLM에게 임의의 원본 삭제나 출처 변경 권한을 추가하지 않는다.

완료 기준: 실제 API·DB에 연결한 브라우저에서 업로드 → 중복 검토 → 반영 → 25만 원 지표 → 5만 원 새 거래 반영 → 30만 원 갱신까지 재현된다. 브라우저를 닫은 뒤 서버 주기 갱신, 서버 재시작, 다른 가게 전환도 검사한다.

## 제안 API와 구현 위치

아래는 전체 계약 제안이다. B에서 출처 생성/조회와 업로드/미리보기/반영/결과 조회를 구현했으며, 별도로 GET `/imports?source_id=...` 이력을 제공한다. C에서 행별 `/rows`, 후보 `/decisions`, 기존 장부 `/preview-adoption`, 이전 출처 `/baseline`을 추가했다. 실제 요청 형식은 [C 문서](EVENT_REVIEW.md)를 참고한다. 모든 경로에서 사용자·가게·출처·배치의 소속을 서버가 검사한다.

| 계약 | 역할 |
|---|---|
| `GET/POST /api/projects/{project_id}/ledger-sources` | 가게의 출처 조회·생성 및 대상 장부 연결 |
| `POST /api/projects/{project_id}/imports` | 출처에 파일 업로드, 배치 생성 |
| `POST /api/projects/{project_id}/imports/{batch_id}/preview` | 매핑·규칙으로 검증하고 미리보기 revision 반환 |
| `GET /api/projects/{project_id}/imports/{batch_id}/rows` | 판정별 행 조회, 페이지네이션 |
| `POST /api/projects/{project_id}/imports/{batch_id}/commit` | 미리보기 revision·후보 결정·멱등 키로 원자적 반영 |
| `GET /api/projects/{project_id}/imports/{batch_id}` | 반영 결과·오류·원본 출처 이력 조회 |

작업 파일:

- `api/app/data_import.py`: 원문 파싱·Decimal/ID 보존, 파싱과 저장 분리.
- `api/app/ledger_imports.py`, `api/app/import_validation.py` 신규: 출처/배치 서비스·라우터와 판정 로직. 실제 구현 시 책임에 맞춰 파일명을 확정한다.
- `api/app/db.py`, `db/migrations/004_ledger_imports.sql` 신규: 제약·인덱스·권한 범위와 적재 트랜잭션. 마이그레이션 번호는 착수 시 기존 파일과 충돌 여부를 확인한다.
- `api/app/main.py`, `api/app/agent_tools.py`, 관련 쓰기 서비스: 기존 업로드/CRUD 경로와 관리 장부의 쓰기 경계 통합.
- `web/app/components/file-upload-modal.tsx`, `web/components/dashboard/sections/tables-section.tsx`: 출처 선택과 검증 화면 연결.
- `web/components/dashboard/sections/dashboard-section.tsx`: 반영 시각과 계산 시각, 출처 이력 연결.
- `api/tests/`, `scripts/ui-eval/`: 배치·동시 적재·실제 DB·브라우저 시나리오 추가.

## 수용 테스트와 종료 기준

| 시나리오 | 반드시 확인할 결과 |
|---|---|
| 기준 결제·취소 파일 | 순결제액 250,000원 |
| 동일 파일 이름 변경 후 재업로드 | 신규 0건, 금액 변화 없음 |
| 기간이 겹치는 새 파일 | 기존 이벤트 제외, 신규 50,000원만 추가되어 300,000원 |
| 같은 날짜·금액, 다른 이벤트 ID | 두 거래 모두 보존 |
| 같은 키·다른 금액 | 충돌, 배치 미반영, 이전 결과 보존 |
| 동일 원거래의 부분 취소 20,000원·30,000원 | 취소 이벤트 둘 모두 반영, 취소 파일 반복 시 추가 차감 없음 |
| 이전 달 결제와 이번 달 취소 | 저장된 결제일/취소일 규칙대로 각각 해당 기간에 반영 |
| ID 없는 유사 거래 | 후보로 표시, 결정 전 반영 불가, 자동 삭제 없음 |
| 선행 0/긴 ID·정확한 소수 | 원문 ID와 Decimal 금액 보존 |
| 통화 불일치·누락·파싱 오류 | 해당 행과 이유 표시, 부분 반영 없음 |
| 동시 요청·commit 직후 응답 유실·서버 재시작 | 같은 확정 이벤트 한 번 반영, 완료 결과 재조회 가능 |
| 미리보기 후 장부/매핑 변경 | 오래된 미리보기 반영 거부, 재검사 |
| 다른 가게/다른 사용자 배치 접근 | 조회·미리보기·반영 모두 차단 |
| 관리 장부의 REST/도구 직접 변경 | 중복 관리 우회 차단 |
| 기존 지표·레이아웃·일정 | 정의와 배치 유지, 다음 계산에서 신규 행 반영 |

종료 보고에는 테스트 실행 환경, 실제 DB 결과, 브라우저 결과, 사용한 파일 유형, 미해결 사례를 기록한다. 실제 모델 평가는 고정 질문에서 출처·기간·필터·취소 의미를 유지하는지 별도로 측정한다. 형식 검증 통과를 모델 성공률로 보고하지 않는다.

초기 모델 평가 후보는 미리보기/저장/후속 요청/모호한 출처/데이터 부족을 포함한 20개 질문이다. 정확히 처리한 수, 올바르게 확인 질문한 수, 잘못 저장한 수, 지연·토큰 사용량을 각각 공개한다. 잘못된 가게 접근이나 요청하지 않은 저장은 0건이어야 한다. 전체 성공률 목표는 파일과 질문 세트를 고정한 뒤 확정한다.

실제 사업자 파일은 가게 1곳의 현금·카드·취소 예시부터 적용한다. 파일이 없거나 테스트 DB가 준비되지 않아도 A~C 개발과 합성 데이터 검증은 진행할 수 있으나 실제 업무/서버 연결 검증을 완료 처리하지 않는다.

## 다음으로 미룰 범위

충돌 거래의 정정·대체와 되돌리기, 최종 상태 파일을 이벤트로 변환하는 커넥터, 자동 출처 재선택, PG 수집, 통화 변환, 여러 가게 비교, 임의 수식은 후속 범위다. 별개의 출처로 등록된 파일 사이에 같은 실제 거래가 있을 가능성까지 이번 규칙이 모두 해결한다고 주장하지 않는다.

착수 순서: **A의 원문 파서·검증 fixture → B의 배치/출처와 동일 파일 재반영 방지 → C의 이벤트 중복·동시성 → D의 화면과 실제 업무 검증**. 가장 먼저 확인할 제품 성과는 '카드 파일을 두 번 올려도 매출이 두 배가 되지 않는다'이다.
