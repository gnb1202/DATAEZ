# 다음 Phase 계획 — 반복 가능한 데모와 제품 품질

작성: 2026-09-10 · 갱신: 2026-09-11 · 계획 기준 코드: `main`의 `9747df8` · 상태: Phase 1 구현·검증 완료, Phase 2 내부 개선·자동 검증 완료 및 사용자 관찰 대기, Phase 3 구현·평가 완료

후속 결정: 배포·포트폴리오 데모를 우선하기 위해 Redis 의존성을 제거하고, 요청 제한은 단일 API 프로세스 메모리로 운영한다. 서버를 여러 개로 확장할 때 공유 요청 제한 도입을 다시 검토한다. 아래 Phase 1은 웹·API·PostgreSQL 구성을 기준으로 한다.

목표는 사용자가 실제 DATA:EZ 앱에서 파일을 선택하고, 자연어로 통계와 그래프를 만든 뒤, 대시보드에 저장하고 다시 확인하는 과정을 반복해서 체험할 수 있게 만드는 것이다. 아래는 최초 계획과 완료 조건이며 실제 구현·검증 결과는 마지막 진행표와 연결 문서에서 구분한다.

기간은 고정하지 않는다. **Phase 1 데모 환경 → Phase 2 사용성 개선 → Phase 3 새로운 파일·질문 평가** 순서로 진행하고, 각 단계에서 발견한 결함을 해결한 뒤 다음으로 넘어간다. Phase 3에서 발견한 출처·계산·설명 문제는 해당 기능으로 돌아가 보완한다.

2026-09-11 사용자 결정으로 Phase 2의 사람 참여 관찰은 대기로 유지하고 Phase 3를 먼저 수행했다. [새 자료 평가](UNSEEN_DATA_ACCEPTANCE.md)는 최초 28/30을 보존한 뒤 설명 오류와 채점기를 보완해 본 평가 30/30, 별도 평가 10/10을 통과했다. 이 결과로 사용자 관찰까지 완료 처리하지 않는다.

기존 실제 통합 테스트는 임시 DB를 생성하고 종료 시 정리하는 구조다. 지속적으로 사용하는 데모와 목적이 다르므로 검증 도구의 정리 동작을 변경해 데모를 유지하지 않는다. 데모 환경을 별도로 구성하고 기존 격리 테스트는 유지한다.

Spoqa Han Sans Neo, Charcoal + Blue, ECharts, 다크 기본·라이트 지원, 왼쪽 메뉴와 오른쪽 접이식 채팅을 유지한다. 원본 범위는 원본 행을, 누적 범위는 연결 장부의 최신 행을 계산한다. 주기 실행은 저장된 지표 정의를 다시 계산하며 외부 PG의 새 거래를 수집하지 않는다.

## Phase 1 — 지속형 데모 환경

### 1-1. 실행과 상태 확인

- 데모 및 첫 배포는 API 프로세스 1개·복제본 1개로 운영한다. 요청 횟수는 API 재시작 시 초기화되며 가게·파일·지표의 영구 보관과 별개다.
- 기존 `docker-compose.yml`을 기본 실행 경로로 사용한다. 구현 시작 때 Docker 엔진과 포트 사용 상태를 확인한다. Docker 실행이 어려운 환경에서는 기존 로컬 PostgreSQL·API·Next.js 경로의 지원 범위를 먼저 확정한다.
- 시작·상태·종료 명령을 마련한다. 필요한 설정 누락, API/DB 준비 실패, 포트 충돌을 구분해서 안내한다. 정상 시작 시 실제 앱 주소를 출력한다.
- 기본 주소는 Compose의 웹 `http://localhost:3000`, API `http://localhost:8000`을 따른다. `3131`의 디자인·검증 자료 화면과 실제 앱 진입점을 구분해 안내한다.
- 데모용 DB와 원본 저장 공간을 테스트용 임시 DB 및 기존 사용자 환경과 분리한다. 데모 종료·재시작은 데이터를 유지한다. 기존 Compose의 고정 컨테이너 이름과 볼륨이 별도 실행 환경과 충돌하는지도 확인한다.
- 실행 도구는 자신이 시작한 프로세스·컨테이너만 관리한다. API 키는 서버 설정으로 읽으며 데모 안내·로그·저장소에 노출하지 않는다.

### 1-2. 첫 사용과 완성 화면 준비

- 기존 샘플 가게 생성 경로를 재사용한다. 기본 체험은 **샘플 준비 → 선택 파일·질문 초안 확인 → 사용자가 질문 전송 → 결과 검토 → 저장**이다.
- 완성 화면을 빠르게 확인할 수 있는 데모 데이터를 별도 준비한다. 합계 KPI, 일별 결제액, 결제수단별 비교의 세 지표를 기존 검증·저장 서비스로 만든다. 미리 만든 지표임을 안내하고 실시간 LLM 실행 결과로 표시하지 않는다.
- 원본과 누적 장부 차이를 보여주는 추가 거래 시나리오를 준비한다. 추가 전·후의 정확한 기대 합계를 함께 기록한다.
- 기존 샘플의 고정 날짜·690,200원 기준은 유지한다. 상대 기간 질문을 시연할 자료가 필요하면 기준 날짜가 명시된 별도 자료를 사용한다.
- **샘플 체험 다시 시작**을 제공한다. 샘플 식별 정보와 소유권으로 범위를 제한하고, 대상과 영향을 보여준 뒤 사용자 실행으로 새 샘플 작업 공간을 준비한다. 기존 사용자 가게·업로드 파일·대시보드나 DB 전체를 초기화하지 않는다. 기존 샘플의 보존·정리 방식은 구현 시 기록한다.

### 산출물과 완료 조건

산출물은 `scripts/demo/`의 실행 도구, 필요한 데모 설정 예시, `docs/DEMO_RUNBOOK.md`와 데이터 기대값으로 계획한다. 경로는 구현 시 확정한다.

- 설정을 마친 환경에서 문서의 시작 명령으로 실제 앱이 준비된다. 설정 누락과 포트 충돌은 해결할 수 있는 오류로 안내된다.
- 로그인·샘플 생성·자연어 질문·차트/표/SQL 확인·대시보드 저장을 실제 API와 DB로 완료한다.
- 브라우저와 앱을 정상 종료한 뒤 재시작해도 파일·대화·저장 지표·레이아웃이 유지된다.
- 샘플 준비를 반복하거나 도중에 실패해 재시도해도 같은 요청의 가게·파일·위젯이 중복 생성되지 않는다.
- 샘플 체험을 다시 시작한 뒤 기존 일반 가게의 파일·거래·위젯이 동일하고, 다른 계정의 샘플에는 영향이 없다.
- 위 동작의 체크 결과와 실제 앱 주소가 안내 문서에 남는다.

## Phase 2 — 실제 사용 흐름 점검과 개선

### 2-1. 먼저 관찰할 과제

실제 앱에서 사용자가 직접 조작하고, 소요 시간·막힌 위치·잘못 이해한 부분·도움이 필요했던 지점을 기록한다. 자동 브라우저 테스트와 사람의 사용성 관찰을 구분한다.

| 과제 | 확인할 질문 |
|---|---|
| 샘플로 첫 분석하기 | 어디서 시작하고 언제 질문을 보내야 하는지 보이는가? |
| 내 파일 올리고 준비하기 | 업로드·검사·분석 준비·검색 준비 상태를 구별하는가? |
| 파일 원본/누적 장부 선택하기 | 새 거래가 어디에 포함되는지 설명할 수 있는가? |
| 결과를 확인하고 저장하기 | 금액·단위·기간·가게·출처와 저장 전 미리보기를 이해하는가? |
| 후속 질문·지표 수정하기 | 일회성 결과와 저장본 변경을 구별하는가? |
| 가게 전환·재접속하기 | 다른 가게로 데이터가 섞이지 않고 이전 지표를 다시 찾는가? |
| 실패에서 복구하기 | 느린 응답·분석 오류·검색 대기·저장 실패 이후 다음 행동이 보이는가? |

첫 관찰은 프로젝트 사용자와 함께 진행한다. 실제 소상공인 대상 파일럿의 별도 기준은 PRD의 **5명 중 4명 이상 첫 저장까지 10분 이내**를 유지한다. 참여자가 없으면 이 기준은 미검증으로 남기고 내부 점검만 완료했다고 표시한다.

### 2-2. 개선 우선순위

1. **금액·출처 오해와 원하지 않은 변경**: 원본/누적 범위, 취소 부호, 여러 가게 포함 여부, 저장본 수정 여부.
2. **진행이 막히는 문제**: 업로드 실패, 검색 미준비, LLM 오류, 중복 클릭·응답 유실, 저장 재시도.
3. **조작과 안내**: 시작 버튼, 용어, 빈 화면, 로딩·저장 상태, 채팅과 중앙 결과 이동, 키보드·모바일 동작.

새 튜토리얼이나 안내 모달은 실제로 관찰된 어려움에 맞춰 추가한다. 기존 시작 안내와 범위·저장 설정 화면을 우선 개선한다. 모바일·좁은 화면·다크/라이트에서도 같은 계산·저장 상태를 확인한다.

### 산출물과 완료 조건

`docs/DEMO_USABILITY.md`에 과제별 관찰, 변경 전후, 해결한 문제와 남은 문제를 기록한다. 바뀐 동작에 필요한 UI 회귀를 보완하고, API·저장 계약이 바뀌면 해당 통합 검사도 실행한다.

- 내부 관찰에서 위 핵심 과제를 처음부터 끝까지 완료하고, 진행 불가 문제를 해결한다.
- 사용자가 선택 가게·파일 범위·기간과 원본/누적 장부 차이를 설명하는지 과제별로 기록한다. 설명을 도와준 경우도 남긴다.
- 오류 뒤 초안·선택 파일이 보존되고, 재시도로 중복 저장·중복 반영이 발생하지 않는다.
- 가게 전환, 지표 저장·재접속, 좁은 화면과 키보드 조작의 관련 회귀가 통과한다.
- 실제 사용자 참여가 필요한 사용성 목표는 별도로 보고한다. 내부 확인만으로 시장 검증 완료를 선언하지 않는다.

## Phase 3 — 새로운 파일과 자연어 질문 평가

### 3-1. 평가 자료와 정답 고정

기존 50문항과 표현만 바꾼 자료 외에 새로운 구조의 합성 파일을 준비한다. 실제 PG 파일은 사용하지 않는다. 먼저 평가 목록·독립 정답·채점 규칙을 고정하고 해당 버전으로 실행한다.

| 자료 변화 | 평가할 내용 |
|---|---|
| 다른 컬럼명·순서·날짜 형식 | 매핑 제안, 전체 파일 검사, 날짜·금액 해석 |
| 음수 취소·부분 취소·월 경계 | 부호, 기간, 거래 건수와 순결제액의 의미 |
| 결측·빈 문자열·소수 금액·큰 식별자 | 미제공 값과 0 구분, 원문 정밀도 보존 |
| 같은 이름의 파일·여러 가게·겹친 기간 | 후보 구분, 명시 범위, 중복 포함 방지 |
| 자료 부족·미지원 구조·다른 통화 | 필요한 확인 질문 또는 명시적 미지원 처리 |
| 파일/표본/문서 안의 지시문 | 사용자 질문과 데이터 내용 구분, 범위 확대·원치 않는 실행 방지 |

첫 평가 규모는 **새 질문 30개**로 제안한다: 정상 분석 12개, 모호함·자료 부족·미지원 6개, 후속 질문·저장/수정 6개, 계정·가게·선택 파일 경계 및 데이터 내 지시문 6개. 출처 검색과 최종 계산을 각각 평가한다. 재계산 가능한 지표와 정적 결과도 구분한다.

### 3-2. 실행과 결함 보완

- 기존 독립 정답·실제 API/DB/LLM 평가 도구를 확장한다. 새 파일과 질문 ID는 기존 평가와 구분한다.
- 정답 금액뿐 아니라 출처 ID·가게·원본/누적 범위·기간·필터·정의·차트 데이터·위젯 상태를 비교한다. 원본 거래와 요청하지 않은 저장본이 바뀌지 않았는지도 검사한다.
- 모호한 질문은 무조건 숫자를 만드는 것보다 필요한 확인을 요청하는 것을 정답으로 정의한다. 모델 설명은 실제 도구 근거와 함께 검토한다.
- 실패를 검색/출처, 정의, 계산, 표시/설명, 저장/상태 변경 단계로 나눠 수정한다. 수정에 사용한 질문은 이후 회귀용으로 분류한다.
- 최초 30개 결과와 수정 후 결과를 각각 보관한다. 개선의 일반화는 수정에 사용하지 않은 별도 질문 10개로 확인하고, 기존/신규/부분 회귀 점수를 합치지 않는다.
- 모델·코드 커밋·자료 해시·기준 날짜·재시도 횟수·실행 시간을 기록한다. 질문별 지연과 토큰·추정 비용, 자료 준비/색인 비용을 구분한다. 평가 오류는 제품 정답 판정과 별도로 표시한다.

### 산출물과 완료 조건

`docs/UNSEEN_DATA_ACCEPTANCE.md`, 합성 자료와 독립 정답, 평가 스크립트, 인증정보를 제외한 공개 보고서를 계획한다. 실행 전 정한 기준을 결과를 보고 낮추지 않는다.

- 새 30문항의 전체 흐름 통과 **27/30 이상**, 보완에 사용하지 않은 10문항 **9/10 이상**을 초기 목표로 한다. 작은 표본의 결과라는 점을 명시한다.
- 독립적으로 계산한 고정 fixture의 SQL 금액·건수는 정확하게 일치한다. 출처·정의 오류를 답변에 정답 숫자가 포함됐다는 이유로 통과시키지 않는다.
- 계정 경계 침범, 선택하지 않은 자료의 묵시적 포함, 원본 거래 변경, 요청하지 않은 저장본 변경은 **0건**이어야 한다. 이 항목은 전체 통과율과 관계없이 실패로 처리한다.
- 실패·재시도·수정 근거를 포함한 보고서를 남기고, 남은 미지원 범위를 데모 안내에 반영한다.
- 기존 평가 전체를 실행하지 않았다면 최신 코드의 전체 평가 성적으로 표시하지 않는다.

## 이후 선택할 작업

Phase 1–3의 데모와 검증 결과를 보고 다음 작업을 고른다. 아래 작업은 데모 완성의 필수 의존성이 아니다.

| 후속 작업 | 시작할 이유 | 확인할 결과 |
|---|---|---|
| 원격 파일 저장소 연결 | 다른 기기·실행 환경에서도 같은 보관함을 체험할 필요 | 기존 S3 호환 경로의 원본 업로드·다운로드·소유권·재시도 검증 |
| 데이터 규모·성능 측정 | 큰 파일과 여러 위젯에서 실제 지연이 문제로 확인됨 | 행 수·위젯 수·동시성·환경을 고정한 집계 지연과 작업 지연 보고 |
| 외부 사용자 파일럿 | 첫 사용 안내와 데모가 안정되고 참여자가 확보됨 | 첫 저장 소요 시간·완료율·범위 이해도와 개선 과제 |
| 소개·제출 자료 | 시연이나 제출 일정이 정해짐 | 실제 기능·데모 화면·검증 범위를 설명하는 자료 |

실제 PG 파일, 외부 PG/API 연동, 실제 결제·환불 실행은 서비스 일정이 정해질 때까지 계속 보류한다. 임의 코드 실행, 예측 매출, 대규모 UI 재설계는 이번 세 Phase에 포함하지 않는다.

## 작업과 기록 방식

- 구현은 Phase별 브랜치와 PR로 나눈다. 예정 이름은 `codex/demo-environment`, `codex/demo-usability`, `codex/unseen-data-evaluation`이다.
- 각 PR에 문제와 최종 동작, 실행한 검사·건너뛴 검사, 남은 제약을 기록한다. 수정한 기능에 맞는 검사를 통과한 뒤 머지한다.
- API/화면 fixture/실제 DB/실제 LLM/사용자 관찰 결과를 구분한다. 기존 테스트의 통과 숫자를 매 단계의 성과로 반복 기재하지 않는다.
- 완료 시 이 문서의 진행표와 [문서 목차](README.md), 해당 기능 문서를 갱신한다. 검증 환경을 초기화하는 작업과 사용자의 지속형 데모 데이터를 다루는 작업을 분리한다.

| 단계 | 상태 | 완료 근거 |
|---|---|---|
| 계획 작성 | 작성 완료 | 본 문서 및 현재 코드·검증 기록 대조 |
| Phase 1 | 구현·검증 완료 | [실행 안내](DEMO_RUNBOOK.md), [실제 LLM·재시작·데이터 분리 점검](DEMO_ACCEPTANCE.md). 추가 거래 시나리오는 API로 제공 |
| Phase 2 | 내부 개선·자동 검증 완료 / 사용자 관찰 대기 | [사용성 문제 4개 개선·UI 회귀 56개·직접 체험 7과제](DEMO_USABILITY.md). 사용자 이해도·소상공인 파일럿은 미검증 |
| Phase 3 | 구현·평가 완료 | [합성 새 자료·독립 정답·실제 API/DB/LLM](UNSEEN_DATA_ACCEPTANCE.md). 최초 28/30 보존, 수정 후 30/30, 별도 10/10, 치명 조건 위반 0건 |

첫 구현 순서는 **실행 환경 확인 → 지속형 데모 시작/상태/종료 → 샘플 체험·재시작 → 실제 흐름 검증 → 사용자 체험**으로 한다.
