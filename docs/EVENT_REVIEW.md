# C단계 — 거래별 판정과 기존 장부 전환

상태: **구현·기술 검증 완료**. 같은 출처에 기간이 겹치는 다른 파일을 올려도 이미 확인된 이벤트를 한 번만 반영한다. 장부 관리 화면에 신규/중복/후보/충돌 건수, 행별 비교 근거, 후보 포함·제외, 기존 장부 전환을 연결했다. 실제 업무 검증은 D단계에 남아 있다.

## 판정 규칙

확정 이벤트 키는 `(출처, 이벤트 종류, 이벤트 ID)`다. 출처 자체가 가게·사용자·제공자·계정을 구분한다. 이벤트 ID의 선행 0과 대소문자는 유지하며, 원거래 ID는 별도 필드다. 취소에는 독립된 취소 이벤트 ID를 연결해야 한다. 원거래 ID만 있는 취소는 이벤트 ID 연결을 비워 확정 키 없이 관리한다.

| 비교 | 결과 |
|---|---|
| 같은 키와 정규화 내용 | `duplicate`, 추가 적재 제외 |
| 같은 키인데 금액·일시·통화·원거래 등 내용이 다름 | `conflict`, 배치 전체 반영 차단 |
| 같은 금액·일시라도 이벤트 ID가 다름 | 별개 이벤트 |
| 비교 대상 중 적어도 하나의 이벤트 ID가 없고 종류·한국 날짜·금액·통화가 같음 | `candidate`, 사용자가 포함/제외하기 전 반영 차단 |
| 위에 해당하지 않음 | `new` |

금액은 Decimal 값을 정확한 문자열로 정규화하며 `100`, `100.00`, `1e2`는 동일하다. 같은 순간의 UTC/한국 시간 표현도 동일하다. 합계는 정수부와 소수부의 최대 길이를 바탕으로 충분한 Decimal 정밀도를 사용한다. 파싱에 float를 사용하지 않는다.

처음 올리는 파일 안에서도 동일 규칙을 적용한다. 같은 키에 서로 다른 내용이 하나라도 있으면 해당 키의 모든 입력 행을 충돌로 표시한다. 같은 키/내용의 반복 행은 최초 행에 연결한다. 후보가 아직 포함되지 않았다면 뒤의 행이 이를 확정 중복으로 오인하지 않게 한다. 같은 후보 이벤트 키를 여러 번 포함하려는 결정도 거부한다.

연결한 이벤트 ID 컬럼의 빈 값은 기존 엄격한 파싱 규칙대로 오류다. 이벤트 ID가 없는 자료는 ID 컬럼 연결을 생략한다. 원거래 ID는 결제 행에서 비어 있을 수 있다. ID 없는 유사 거래는 같은 날짜·금액만을 근거로 자동 제외하지 않는다.

## 모델과 원자적 반영

`import_rows`는 배치·원본 행 번호, 정규화한 이벤트, 내용/유사성 해시, 판정/이유, 비교 대상 파일·행·내용, 최종 후보 결정, 대상 장부 행 ID를 보관한다. 전체 판정 개수는 정상 파싱한 파일 전체 행 수와 같고, `included / excluded / unresolved`는 후보 결정 상태를 별도로 집계한다.

`source_events`에는 실제로 반영된 장부 행과 최초 출처를 연결한다. 긴 ID도 PostgreSQL 인덱스 크기 제한에 걸리지 않게 원문 키의 SHA-256에 유일 제약을 둔다. 비교 시 원문 이벤트 ID와 정규화 내용도 확인한다. ID 없는 행은 NULL 키로 보관하므로 확정 유일 키를 만들지 않으며, 후보 검색과 출처 추적에만 사용한다. 이벤트 키와 유사성 검색은 출처 범위의 인덱스로 조회한다.

출처 → 배치 잠금 안에서 원본 파일 해시·매핑·revision·미리보기 토큰·판정 버전을 재검사한다. 커밋 직전에 최신 레지스트리로 전체 판정을 다시 계산하고, 저장된 미리보기의 내용·분류·비교 근거와 일치해야 반영한다. 후보 결정은 서버에 저장되며 결정할 때마다 새 토큰을 반환한다. 다른 탭의 오래된 토큰은 409다. 미리보기를 새로 실행하면 이전 후보 결정을 초기화한다.

한 트랜잭션에서 선택한 실제 행, 유일 이벤트 키, 모든 판정의 행 연결, 원본 파일 메타데이터, 장부 건수, 출처 revision, 배치 완료 결과를 저장한다. 실제 행 ID는 `INSERT ... RETURNING`으로 받으며 연속된 시퀀스 번호라고 추측하지 않는다. 중간 제약 위반은 모든 신규 저장을 롤백한다. 이미 완료한 요청의 재시도는 오래된 토큰이어도 최초 결과와 `rows_added=0`을 반환한다.

결과의 `amount`는 이번에 포함된 거래의 순금액이다. `amounts`에는 전체/포함/확정 중복/사용자 제외 금액을 별도로 제공한다. 제외 금액도 원본 이벤트 부호를 유지하므로 취소 중복 제외는 음수일 수 있다. 완료 결과에 `duplicates_skipped`, `candidates_excluded`를 기록한다.

## 기존 장부의 전체 검사와 전환

두 경로를 제공한다.

1. **B에서 이미 생성한 출처**: 새 업로드의 이벤트 판정을 사용하기 전에 `기준점 검사·전환`을 실행한다. 기존 물리 장부 전체를 읽고 검증한다. 충돌·확정 중복이 있으면 전환하지 않으며 기존 장부와 지표를 유지한다. ID 없는 유사 행은 사용자가 각각 별개 거래로 유지한다고 명시해야 한다.
2. **일반 장부**: 새 출처 등록에서 기존 장부를 선택하고 현재 장부 컬럼을 연결한다. 전체 검사 결과를 먼저 확인한 뒤 전환한다. 검사 토큰은 소유자·장부·출처 설정·매핑·전체 행/스키마의 지문에 연결된다. 커밋 시 잠금 아래에서 다시 검사하므로 중간 행 변경이나 설정 변경은 409로 거부한다.

전환은 기존 장부 ID·컬럼·행·`_row_id`를 바꾸지 않는다. 저장된 지표 정의도 유지한다. 일반 장부 전환 후 파일은 원래 장부의 전체 컬럼 형식으로 검증하여 적재하고, 그 값에서 이벤트를 별도로 정규화한다. 따라서 기존 지표의 금액 컬럼·취소 처리 설정은 그대로 적용된다.

전환과 일반 INSERT/UPDATE/DELETE/ALTER/append/장부 삭제/스키마·건수 갱신은 같은 테이블 단위 트랜잭션 잠금을 사용한다. 전환 중 시작한 일반 쓰기는 기다렸다가 관리 출처 여부를 다시 검사한다. 관리 장부가 된 뒤에는 기존 REST·채팅 경로의 직접 변경을 차단한다.

기준점 검사는 최대 **100,000행**까지 지원한다. 전체 행의 정합성을 확인하지 못하거나 기존 컬럼 형식이 이후 파일 적재에서 지원되지 않으면 전환하지 않는다. 기존 B 및 일반 장부의 과거 행은 `기존 장부 기준점 / 장부 행 ID`로 추적한다. 당시 원본 파일의 행 번호를 추측해 연결하지 않는다. 이후 C에서 반영한 파일은 배치와 실제 원본 행 번호까지 추적한다.

이미 관리 중인 B 장부에 과거 중복/충돌이 있으면 이번 전환은 차단된다. 그 거래의 수정·대체·삭제를 자동 실행하지 않으며, 별도의 복구/정정 절차는 후속 범위다. 일반 장부는 전환 전까지 기존 편집 기능으로 오류를 해결하고 다시 검사할 수 있다.

## 화면과 API

화면에서 판정별 필터와 페이지 이동으로 원본 행을 조회한다. 비교 대상을 펼치면 기존 파일/행, 금액·일시·원거래를 볼 수 있다. 후보는 `별개 거래로 포함 / 중복으로 제외`를 선택하며 미결정/충돌이 있으면 반영 버튼이 비활성화된다. 같은 판정은 서버에서도 강제한다.

기존 B API에 다음 계약을 추가했다. 기준 경로는 `/api/projects/{project_id}`다.

| 요청 | 입력/결과 |
|---|---|
| GET `/imports/{batch_id}/rows` | `classification`, `limit`(최대 100), `offset`; 판정 행·비교 근거·토큰 |
| POST `/imports/{batch_id}/decisions` | `preview_token`, `decisions: [{row_number, decision: include/exclude}]`(최대 1000); 갱신된 요약과 새 토큰 |
| POST `/ledger-sources/preview-adoption` | 출처 생성 필드 + `existing_table_id`, `accept_idless`; 검사 결과와 `adoption_token` |
| POST `/ledger-sources` | 기존 장부 전환 시 위 입력과 `adoption_token` 추가 |
| POST `/ledger-sources/{source_id}/baseline` | B 출처 검사, `accept_idless`(기본 false) |

모든 조회·결정·전환 요청은 사용자·가게 소속을 확인한다. 다른 가게의 행이나 비교 근거를 반환하지 않는다. SQL은 고정된 연산과 인용된 테이블/컬럼만 사용한다.

런타임은 `ensure_ledger_import_tables()`에서 B DDL 다음 C DDL을 실행한다. `db/migrations/005_event_review.sql`과 `api/app/event_schema.py`의 DDL 일치를 테스트한다. 기존 출처는 초기 `event_index_version=0`이며 자동으로 검증 완료 처리하지 않는다. 기존 B 완료 결과는 유지한다. 미반영 배치 만료 시 C의 판정/후보 결정도 정리하고, 재업로드 시 새 검토가 필요하다.

## 검증 기록

- 최종 전체 Python 테스트 **494개 통과, skip 0개**. 기존 468개에 C 신규 26개(실제 PostgreSQL 24개, 순수 정규화/정밀도 2개)를 추가했다. 전체 실제 PostgreSQL 검증은 68개다.
- PostgreSQL 16.15, 루프백 테스트 서버, 테스트마다 별도의 임시 스키마/파일 디렉터리. 실제 사용자 데이터나 모델 호출은 사용하지 않았다.
- 서로 겹치는 파일의 기존 2건 제외 + 신규 50,000원 추가 → **250,000원에서 300,000원**. 행별 기존 배치/원본 행/대상 행 연결 확인.
- 첫 파일 안 중복, 파일 안/파일 간 같은 키·다른 내용, UTC/한국 시간 표현과 Decimal 동치, 대소문자가 다른 ID, 5,000자를 넘는 ID, 원거래 하나의 독립된 부분 취소를 검증했다.
- ID 없는 후보 포함/제외 및 미결정 차단, 다른 탭의 오래된 토큰, 재미리보기 시 결정 초기화, 동시 겹침 반영 후 재검사, 레지스트리 저장 실패 시 전체 롤백을 검증했다.
- 일반 장부 전체 검사/전환/겹침 업로드, 기존 ID·스키마 유지, 검사 뒤 행 변경, 과거 중복·충돌 차단, ID 없는 과거 행의 명시적 유지, B 출처 기준점, 일반 쓰기와 전환의 경합, 다른 사용자/가게 차단을 검증했다.
- Next.js 프로덕션 빌드·TypeScript 검사 통과. Edge headless의 실제 UI에서는 **모의 API**로 비교 근거, 후보 결정, 새 토큰 사용, 충돌 반영 차단, 전환 설정 변경 시 재검사, 가게 전환을 검증했다. B의 동일 파일 재업로드 화면 검증도 통과했다.

```powershell
$env:DATAEZ_TEST_DATABASE_URL='postgresql://<test-user>@127.0.0.1:<port>/<test-db>'
python -m pytest api/tests -q
npm run build --prefix web
# 웹 서버를 127.0.0.1:3100에 실행한 후
npm run check:events --prefix scripts/ui-eval
npm run check:ledger --prefix scripts/ui-eval
```

## 남은 범위 / D단계

C 당시에는 실제 DB 브라우저 검증이 남아 있었다. 후속 [D단계](INTEGRATED_ACCEPTANCE.md)에서 실제 인증·API·PostgreSQL에 연결한 업로드→판정→결정→반영→저장 지표 갱신, 서버 재시작과 백그라운드 일정을 합성 CSV로 검증했다. 채팅 출처/검토 조회와 화면 링크도 추가했다. 실제 사업자 파일과 실제 LLM 응답 평가는 계속 미완료이며 고정 질문 20개를 준비했다.

서로 다른 출처 사이의 거래 자동 중복 제외, 충돌 거래의 정정·대체·되돌리기, 출처 매핑 편집, PG 자동 수집, 통화 변환, 100,000행 초과 기준점 전환은 이번 범위에 포함하지 않는다. 파싱 오류는 기존 규칙처럼 전체 반영을 막고 최대 50개 오류를 제공한다. 파싱 실패 파일의 정상 행까지 이벤트별 판정이 완료됐다고 표시하지 않는다.
