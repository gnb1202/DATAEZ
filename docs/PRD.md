# DATA:EZ PRD — 대화로 만드는 통합 매출 대시보드

버전: 0.2 · 최초 작성: 2026-09-08 · 갱신: 2026-09-10 · 상태: 확정 제품 방향과 현재 구현 범위

이 문서는 기존 코드 위에서 구현한 제품의 방향과 남은 검증 기준을 정리한다. 기능 구현과 사용자·운영 검증 완료는 구분한다. 최신 사용 계약은 [분석 범위·저장 설정·첫 사용 안내](FILE_SCOPE_AND_FIRST_USE.md), 통합 근거는 [실제 작업 공간 검증](WORKSPACE_LIVE_ACCEPTANCE.md)을 따른다. 이전 `AGENT_ADVANCEMENT_PLAN.md`의 환불 실행·Browser Agent 중심 제안보다 본 문서의 제품 범위와 우선순위를 우선한다.

## 1. 제품 정의

**DATA:EZ는 여러 채널과 결제수단에 흩어진 소상공인의 매출 데이터를 모으고, 자연어로 원하는 지표를 만들어 편집 가능한 대시보드에서 지속적으로 확인하는 서비스다.**

핵심 사용자: 예약·매출·결제를 여러 채널에서 관리하며 현금 장부, 카드 매출 파일, 예약 내역 등을 따로 확인하는 소상공인.

사용자가 제시한 문제는 데이터 기록과 조회가 여러 도구에 흩어져 있다는 점이다. 시장에 통합 솔루션이 전혀 없다는 주장은 제품 가설로 삼지 않는다. 기존 도구와의 비교 및 사용자 인터뷰는 후속 검증 사항이다.

제품이 제공할 가치:

- 현금과 카드 등 여러 출처를 같은 공간에서 관리한다.
- 필요한 파일과 컬럼을 일일이 찾거나 엑셀 수식을 새로 만들지 않아도 된다.
- 한 번 정의한 지표를 다시 질문하지 않고 대시보드에서 확인한다.
- 숫자의 계산 기준, 출처, 최신성을 확인할 수 있다.

## 2. 확정 요구와 초안의 가정

### 사용자 요구

1. 여러 채널에서 예약·매출·결제를 관리하는 소상공인을 대상으로 한다.
2. 현금 수기 기록과 카드 매출 등 흩어진 데이터의 통합이 핵심 문제다.
3. 자연어 대화 또는 메타프로그래밍으로 지표를 제작하고 대시보드에 추가한다.
4. 대시보드를 드래그 앤 드롭과 리사이징으로 편집한다.
5. RAG로 질문에 필요한 통계 파일을 찾고 대시보드를 일정 주기로 갱신한다.
6. 외부 PG 연동은 후순위다.
7. 한 계정이 여러 가게를 운영하며, 여러 가게 합산은 대상을 명시적으로 선택한다.
8. 업로드한 원본을 계정 보관함에서 다시 선택하고 AI 채팅에 연결한다.
9. 중앙 분석·대시보드, 왼쪽 메뉴와 오른쪽 접이식 채팅을 사용한다. Spoqa Han Sans Neo, Charcoal + Blue, 다크 기본·라이트 지원으로 확정한다.

### 실행 가능한 범위를 위한 제안

- 초기에는 CSV/XLSX 업로드와 현금 매출 직접 입력을 지원한다. 종이 장부 사진의 OCR은 후속 범위다.
- “메타프로그래밍”은 **실행 가능한 지표 정의를 생성·수정하는 방식**으로 우선 해석한다. 고급 사용자는 구조화된 수식/정의를 편집하며, 임의 Python/JavaScript 실행은 초기 범위에서 제외한다.
- 기본 사업장 시간대는 Asia/Seoul, 기본 통화는 KRW로 제안한다. 통화가 다르면 환산 근거 없이 합산하지 않는다.
- 갱신 옵션은 수동, 매시간, 24시간마다다. 누적 장부의 새 데이터는 다음 수동·예정 실행에 반영한다. 업로드 즉시 관련 위젯을 모두 계산하는 이벤트 트리거는 구현하지 않았다. 24시간 주기는 특정 시각의 매일 실행과 구분한다.
- 아래 정량 목표는 현재 성과가 아닌 검증용 목표이며, Phase 0에서 테스트 환경과 평가셋을 고정한다.

## 2.1. 한 사용자의 여러 가게

- 기존 project 하나를 가게 하나로 사용한다. 계정은 여러 가게를 생성·전환할 수 있다.
- 각 가게의 장부, 대화, 지표, 대시보드는 project_id로 분리한다.
- 같은 계정의 다른 가게 데이터도 명시적인 통합 기능 없이 섞지 않는다.
- 가게 전환 시 이전 가게의 위젯·작성 중 지표를 초기화한다.
- 여러 가게 순결제액 합산·비교는 명시적으로 선택한 소유 가게만 사용한다. 원화·결제/취소 발생일·공통 기간을 검증하고 현재 가게의 대시보드에 저장한다. 빈 가게를 제외한 부분 합계를 전체 합계로 제시하지 않는다. 상세 범위는 [M: 여러 가게 지표](MULTI_STORE_METRICS.md)를 따른다.

## 3. 대표 사용자 흐름

1. 사업장 프로젝트를 만든다.
2. 카드 매출 파일과 현금 장부를 보관함에 올리거나 현금 거래를 직접 입력한다. 샘플로 시작하면 별도 가게와 파일, 질문 초안을 준비한다.
3. 시스템이 날짜·금액·결제수단·거래 식별자 후보를 제안한다. 사용자는 모호한 매핑만 확인한다.
4. 채팅에서 보관 파일과 원본/누적 장부 범위를 선택하고 “이번 달 현금과 카드 매출을 일별로 비교해줘”라고 묻는다.
5. 관련 데이터 출처를 검색하고 지표 정의를 만든 뒤 실제 데이터를 집계한다.
6. 결과와 함께 기간·계산식·출처·제외 조건을 보여준다.
7. 사용자가 저장 버튼에서 이름·단위·기간·갱신 주기를 검토하고 현재 설정으로 미리보기하거나, 채팅으로 저장·갱신 주기를 명시적으로 요청한다.
8. 지표 정의와 갱신 주기를 저장하고 위젯을 생성한다.
9. 사용자는 위젯을 이동·리사이징한다. 다음 접속에도 배치가 유지된다.
10. 누적 장부에 새 파일이나 현금 입력을 반영하면 다음 수동·예정 실행에서 갱신한다. 파일 원본만 선택한 지표는 같은 원본 행에 기간·필터를 다시 적용한다.

후속 요청 예시: “카드만 보여줘”, “주별로 바꿔줘”, “지난달과 비교해줘”. 현재 지표와의 연결을 유지하되, 저장된 지표 변경인지 일회성 분석인지 명확히 표시한다.

## 4. MVP 범위

| 영역 | 필수 요구 | 완료 조건 |
|---|---|---|
| 데이터 등록 | CSV/XLSX 업로드, 현금 직접 입력 | 출처와 원본 행을 추적할 수 있음 |
| 파일 보관함 | 원본 보관·다운로드·검색, 채팅 재선택 | 계정·가게 소유권을 검증하고 원본/누적 범위를 구분함 |
| 데이터 정리 | 날짜/금액/수단 매핑, 오류·중복 검토 | 제외 행과 이유가 보이며 중복 파일을 조용히 합산하지 않음 |
| 출처 검색 | 파일·시트·장부·컬럼·기간·설명 검색 | 선택한 출처를 제시하고 다른 프로젝트 데이터는 조회하지 않음 |
| 지표 제작 | 자연어 → 검증된 지표 정의 → 실행 | 계산식과 결과가 일치하고 정의를 저장·재실행할 수 있음 |
| 대화형 수정 | 기간·필터·그룹·차트 변경 | “그 지표”의 참조가 유지되고 기존 저장본 수정 여부가 명확함 |
| 고급 편집 | 허용된 수식/구조화 정의 편집 | 잘못된 컬럼·집계·0 나눗셈을 검증하고 오류를 설명함 |
| 대시보드 | KPI/선/막대/구성비 차트, 추가·삭제·이동·크기 변경 | 배치가 저장되고 저장 실패를 사용자에게 알림 |
| 자동 갱신 | 서버의 주기 실행과 수동 실행 | 브라우저가 닫혀도 실행되고 최신 성공 결과를 표시함. 데이터 변경은 다음 실행에 반영 |
| 신뢰성 | 출처, 계산 기준, 기준 시각, 실행 상태 | 오래된 값이나 실패한 갱신을 최신 정상 수치처럼 보이지 않음 |

MVP 밖: 외부 PG/API 커넥터, 외부 사이트 화면 자동화, 실제 환불·결제 실행, OCR, 예측 매출, 세무 신고, 임의 코드 실행, 모바일 전용 앱. 기존 CRUD 기능은 유지하되 이러한 확장보다 지표의 정확성과 갱신을 우선한다.

## 5. 데이터 의미와 합산 규칙

서로 다른 파일을 단순히 합치는 것만으로 통합 매출을 만들 수 없다. 숫자의 의미를 아래처럼 다룬다.

- **판매 채널과 결제수단을 분리한다.** 매장/예약 플랫폼과 현금/카드는 별도 차원이다.
- 예약금, 승인금액, 취소금액, 입금된 정산액을 같은 “매출”로 자동 합산하지 않는다.
- 초기 기본 지표는 업로드된 결제 데이터 기준의 결제액/취소액/순결제액으로 제안한다. UI에서 매출이라는 명칭을 쓰면 적용한 기준을 함께 보여준다.
- 순결제액은 정의된 결제 이벤트 합계에서 취소 이벤트 합계를 뺀 값으로 한다. 원본이 최종 거래 상태를 담는 경우에는 별도 변환 규칙을 사용해 취소를 두 번 차감하지 않는다.
- 결제일/취소일/정산일의 기준을 저장한다. 부분 취소와 월을 넘긴 취소를 평가에 포함한다.
- 정산 파일과 결제 파일은 서로 다른 사실로 관리한다. 동일 거래의 원금과 정산금을 매출에 중복 반영하지 않는다.
- 거래 ID가 있으면 출처 범위의 ID를 우선 사용한다. ID가 없는 유사 거래는 중복 후보로 표시하며 임의 삭제하지 않는다.
- 파일 재업로드는 파일 해시와 적재 기록으로 감지한다. 신규 파일의 겹치는 기간도 별도로 점검한다.
- 서로 다른 구조의 파일은 공통 필드로 매핑한 뒤 함께 집계한다. 예약·결제 JOIN은 키와 관계를 검증해 행 증식에 의한 합계 오류를 막는다.
- 결측 금액, 파싱 실패, 모호한 날짜, 통화 불일치는 품질 문제로 표시한다. 합계에서 제외하면 제외 건수와 이유를 보여준다.
- 분모가 0인 증감률/비율은 0%로 바꾸지 않고 계산 불가로 표시한다.

예시 검증: 같은 기간의 정상 결제 이벤트가 현금 10만원, 카드 20만원, 카드 취소 5만원이라면 순결제액은 25만원이다. 취소 시점·데이터 형식·중복 여부를 통제한 fixture에서 확인한다.

## 6. RAG와 지표 실행의 역할

**검색 → 지표 정의 → 검증 → 계산 → 표시**로 책임을 나눈다.

검색 인덱스에는 파일/시트/장부 이름, 컬럼 설명과 별칭, 데이터 유형, 기간, 결제수단·채널, 데이터 단위, 출처 버전을 담는다. 기존 schema RAG를 이 데이터 카탈로그 검색으로 확장한다.

- RAG는 “어떤 데이터로 답할 수 있는가”를 찾는다.
- 계산은 정형 데이터 전체를 대상으로 검증된 SQL/집계 엔진이 수행한다. 검색된 일부 청크나 모델의 암산을 매출 합계로 사용하지 않는다.
- 문서 RAG는 용어·정책·지표 설명에 활용한다. 집계된 통계 파일은 집계 단위와 기간을 확인해 원시 거래와 섞어 더하지 않는다.
- 필요한 데이터가 없거나 두 출처의 의미가 충돌하면 부족한 정보와 선택지를 제시한다.
- 지표를 저장할 때는 선택된 출처 ID와 컬럼 매핑을 고정한다. 매 갱신마다 RAG로 임의의 새 파일을 선택하지 않는다.
- 새 파일은 사용자가 연결한 같은 논리 데이터셋의 새 버전/추가분으로 반영한다. 출처 자동 변경은 별도 사용자 검토 대상이다.

### 파일 원본과 누적 장부

보관함에서 새로 선택한 파일의 기본 범위는 `original_file`이다. 보관된 원본 바이트의 해시를 확인하고 읽기 전용 분석 자료를 만들며, 이후 장부에 추가한 거래를 포함하지 않는다. `linked_ledger`를 선택하면 연결 장부의 현재 거래 전체에 요청한 기간·필터를 적용한다. 범위 정보가 없는 이전 대화는 기존 누적 장부 동작을 유지한다.

저장한 지표는 같은 분석 출처를 재사용한다. 파일 원본의 새 버전을 자동으로 따라가지 않는다. 보관함 제외는 새 선택을 막고 기존 저장 지표·원본 기록은 유지하며, 가게 삭제는 그 가게의 출처 접근을 막는다. 다른 파일 사이의 실거래 중복을 자동으로 제거한다는 뜻은 아니다.

## 7. 저장할 지표 정의

현재의 차트 결과 저장에 아래 의미 정보를 추가한다.

| 필드 | 의미 |
|---|---|
| 이름·설명 | 사용자가 이해하는 지표의 목적 |
| 소유자·프로젝트 | 데이터 접근 범위 |
| 논리 데이터셋·컬럼 매핑 | 계산 대상과 데이터 버전 연결 |
| 집계·수식 | 합계, 건수, 평균, 비율, 허용된 파생 수식 |
| 차원·필터 | 날짜 단위, 결제수단, 채널, 상태 조건 |
| 시간 범위·시간대 | 이번 달/최근 30일 등 상대 범위 또는 고정 범위 |
| 단위·반올림 | KRW, 건, %, 표시 정밀도 |
| 차트 설정 | 시각화 종류, 축, 범례 |
| 정의 버전 | 변경 이력과 이전 실행의 해석 |
| 갱신 정책 | 주기, 활성 여부, 다음 실행 시각 |

기본 집계부터 시작하고 기간 비교·파생 수식을 확장한다. 자연어와 고급 편집은 같은 지표 정의를 생성한다. 정의는 검증 가능한 DSL/AST로 표현하고 허용된 쿼리로 변환한다.

정기 갱신은 저장된 정의를 재실행하므로 정상 경로에서 LLM을 다시 호출하지 않는다. 스키마 변경으로 실행이 불가능하면 수정 필요 상태로 표시한다.

## 8. 갱신과 최신성

데이터 수집과 지표 계산을 구분한다. PG 연동 전에는 마지막 업로드·직접 입력 이후 발생한 외부 매출을 알 수 없다.

각 위젯은 다음을 표시한다.

- 마지막 데이터 반영 시각 및 원본이 제공하는 데이터 기준 시각/커버 기간
- 마지막 계산 성공 시각과 다음 예정 실행 시각
- 정상, 갱신 중, 이전 결과 표시, 실패, 수정 필요 상태

원본의 기준 시각을 알 수 없다면 알 수 없다고 표시한다. 단순히 파일 내 최신 거래일을 원본의 완전한 최신성 보장으로 해석하지 않는다. 여러 출처의 갱신 시각이 다르면 출처별로 확인할 수 있어야 한다.

서버 갱신 작업은 중복 실행을 제어하고 재시도 횟수를 제한한다. 실패 시 마지막 성공 결과를 보존하되 실패 상태를 함께 표시한다. 브라우저 polling은 상태 조회용이며 실제 주기 계산은 서버가 맡는다.

상대 기간은 실행 시점과 사업장 시간대를 기준으로 다시 계산한다. 데이터 변경이 없어도 월초에는 “이번 달” 범위가 달라질 수 있다. 한 번의 실행은 일관된 데이터 버전/스냅샷을 사용하며 정의 변경 중 완료된 오래된 실행이 최신 결과를 덮어쓰지 않게 한다.

## 9. 성공 기준 — 제안

### 사용자 가치 검증

- 대표 사용자 5명 중 4명 이상이 안내 문서만 보고 샘플 파일 업로드부터 첫 지표 저장까지 10분 이내 완료한다.
- 사용자는 위젯의 출처, 기간, 현금/카드 포함 여부와 최신성을 설명할 수 있다.
- 파일을 추가한 뒤 같은 질문을 다시 하지 않아도 저장한 지표에 새 데이터가 반영된다.
- 사용성 파일럿에서 첫 지표 저장률, 소요 시간, 7일 내 재방문 및 저장 지표 조회를 기록한다. 유지율 목표는 초기 표본을 얻은 후 정한다.

### 기능·정확성 게이트

- 고정된 집계 fixture의 금액·건수 결과 100% 일치. 금액은 정밀 소수/정수로 계산하고 표시 반올림 규칙을 따로 적용한다.
- 최소 50개 질문에 대해 출처 선택→정의 생성→실행 결과의 전체 통과율 90% 이상을 초기 목표로 한다. 모호한 질문에는 명확화가 정답일 수 있다.
- 검색 recall@5를 보조 지표로 보고하되 최종 계산 정확성을 별도로 평가한다.
- 필수 격리·중복·파괴적 쿼리 테스트에서 타 프로젝트 접근, 중복 적재 반영, 지표 실행을 통한 데이터 변경 0건.
- 데이터 추가, 월 경계, 부분 취소, 0분모, 출처 삭제, 컬럼 변경, 갱신 실패와 재시도를 검증한다.
- 새로고침과 재로그인 후 위젯 위치·크기·지표 정의가 유지된다. 저장 실패는 사용자에게 표시된다.

### 성능·운영 목표

- 기준 환경은 Phase 0에서 CPU/RAM/데이터 크기/동시성까지 기록한다. 초기 벤치마크는 프로젝트당 10만 행, 위젯 10개, 동시 사용자 5명을 제안한다.
- 해당 조건에서 캐시된 대시보드 조회 p95 2초 이내, 기본 단일 지표 재계산 p95 5초 이내를 초기 목표로 한다.
- 부하 테스트의 예정 작업 99% 이상이 예정 시각 60초 이내 시작하는 것을 목표로 한다. 실패율과 큐 지연을 별도로 보고한다.
- 자연어 지표 생성은 성공률, 전체 지연 p50/p95, 성공 건당 LLM 비용을 측정한 후 예산을 정한다.
- 정상 주기 갱신의 LLM 호출 수는 0회여야 한다. 계산·저장·작업 실행 비용은 별도로 계측한다.

이 수치는 출시 성과가 아니라 테스트 조건 아래의 목표다. 실제 사용성·운영 결과와 분리하여 보고한다.

초기 코드 검토 당시 장부 업로드·CRUD, schema/document RAG, 차트, 위젯 API, `react-grid-layout` 기반 이동·리사이징 및 레이아웃 저장이 있었다. 아래는 목표 단계이며, 현재 구현 상태는 표 다음에 별도로 기록한다.

|---|---|---|
| 0. 의미·fixture | 현금/카드/취소 샘플, 공통 필드, 지표 정의·평가셋 | 기대 합계와 데이터 규칙을 고정 |

현재 구현 (2026-09-10): 가게별 재실행 지표, 대화 미리보기·저장, 서버 주기 갱신, 출처별 반복 파일 반영과 이벤트 중복·충돌 검토, 선택 속성 복원, RAG 검색의 비동기 갱신·자동 복구를 연결했다. v1 단일 장부, v2 여러 장부 합계, v3 두 스칼라 집계의 차이·비율·증감률, v4 날짜·분류별 계산식 그래프, v5 선택 가게의 원화 순결제액 합산·비교를 지원한다. [그룹별 계산식과 분석 근거](FORMULA_CHARTS.md)에서 범위와 SQL·집계표 표시를 설명한다.

사용자 요청으로 K·L을 먼저 구현했다. K는 저장 지표 수정·이력·복원과 고급 정의 편집, L은 가게별 현금 직접 입력과 대화 초안·검토·반영·중복 확인을 포함한다. 상세 범위는 [계산식 지표와 현금 입력](METRICS_AND_CASH.md)에 기록한다. 지표 수정은 위치·갱신 주기를 유지하고, 현금 반영은 기존 수동·주기 재계산에 포함된다.

A~I 및 K·L의 합성 데이터 검증은 실제 PostgreSQL·브라우저·모델을 사용했다. 실제 사업자 사용성·운영 부하·실제 PG 파일 검증까지 완료했다는 뜻은 아니다. 실제 PG 파일 파일럿은 서비스 일정이 정해질 때까지 보류한다. M의 여러 가게 합산·비교를 구현했으며 상세 범위는 [여러 가게 지표](MULTI_STORE_METRICS.md)에 기록한다. J의 [첫 대시보드 안내](FIRST_DASHBOARD.md)도 구현했다. 파일의 컬럼 후보·표본 확인, 전체 형식 검사, 중복 검토·반영, 첫 지표 미리보기·저장과 자연어 질문 초안을 연결한다. N의 [자연어 50문항 평가](NATURAL_LANGUAGE_ACCEPTANCE.md)는 전체 재평가 47/50, 실패 보완 후 관련 10문항 10/10을 기록했다. 다음 검증 과제는 실제 사용자 사용성, 보지 않은 자연어 질문·파일 구조, 운영 부하다.

기존 위젯은 마이그레이션 시 정적 결과로 보존한다. 과거 결과만으로 원래 쿼리를 추측하지 않는다. 갱신 가능한 지표로 전환하려면 출처와 정의를 다시 지정한다.

기존 고도화 계획의 비용 귀속·실패 상태·실제 DB 평가 개선은 본 흐름의 작업에 포함한다. 환불 승인, 장기 실행 복구, 외부 화면 조작은 본 MVP의 필수 의존성이 아니다.
