## 기술 영상 — 5분

### T01 · 00:00–00:25 — 해결하려는 문제

**내레이션:** 소상공인의 매출 기록은 카드, 현금, 여러 파일로 나뉘어 있을 수 있습니다. DATA:EZ는 이 자료를 가게별로 보관하고, 필요한 통계를 자연어로 만들어 저장하도록 설계했습니다. 지금 보이는 숫자는 합성 데이터로 검증한 결과입니다.

**자막:** 파일 보관 → 자연어 분석 → 저장 가능한 통계 / 실제 앱 시연 · 합성 데이터

### T02 · 00:25–01:05 — 자료를 찾는 일과 계산하는 일

**내레이션:** 분석할 파일과 범위를 먼저 정합니다. 원본 파일만 볼 수도 있고, 그 파일에 연결된 누적 장부 전체를 볼 수도 있습니다. 이번 시연은 보관함에서 파일을 직접 선택합니다. 서비스의 검색 구조는 관련 파일과 스키마, 문서를 찾는 데 쓰입니다. 금액 계산은 검색된 문장의 요약에 맡기지 않고, 선택한 데이터에 대한 데이터베이스 집계로 수행합니다.

**자막:** 어떤 자료를 분석할지 명시적으로 선택 / 관련 자료 검색과 금액 집계는 서로 다른 역할

**화면 유지:** 파일명·가게·범위를 읽을 시간을 확보한다. 구조 설명 화면에는 ‘동작 구조’ 표시. 이번 take에서 RAG 검색을 실행한 것처럼 표시하지 않는다.

### T03 · 01:05–01:50 — 자연어가 지표 정의로

**내레이션:** AI는 질문을 도구 호출과 구조화된 지표 정의로 바꿉니다. 서버는 데이터 출처와 권한, 계산 조건을 확인한 뒤 SQL을 구성합니다. 사용자가 모델의 임의 코드를 그대로 실행하는 구조는 아닙니다. 여기서는 날짜별 금액 합계와 원화 단위를 사용합니다. 집계표의 날짜와 금액, 실행 SQL을 확인하고 저장합니다. 저장하는 것은 그래프 이미지뿐 아니라, 같은 출처에서 다시 계산할 수 있는 지표 정의입니다.

**자막:** 자연어 → 구조화된 정의 → 서버 검증 → SQL 집계 / 같은 출처와 기준으로 다시 계산할 수 있게 저장

**화면 유지:** 실제 집계표를 먼저, SQL을 나중에 확대한다. SQL 전체를 빠르게 스크롤하기보다 집계·그룹 기준이 읽히는 부분을 유지한다.

### T04 · 01:50–02:35 — 같은 파일, 다른 분석 범위

**내레이션:** 이번에는 같은 파일의 누적 장부 전체를 선택합니다. 원본과 같은 날짜별 합계를 요청하고, 누적 장부 일별 순결제액이라는 이름으로 저장합니다. 아직 거래를 추가하지 않았기 때문에 두 그래프의 숫자는 같습니다. 범위가 같은 것은 아닙니다. 하나는 보관한 원본을, 다른 하나는 앞으로 거래가 추가될 수 있는 연결 장부를 기준으로 합니다.

**자막:** 같은 파일에서 원본과 누적 장부를 구분 / 추가 전 집계표 합계는 둘 다 690,200원

### T05 · 02:35–03:35 — 추가 거래 후 재계산

**내레이션:** 데모용 카드 거래 3만 원 한 건을 연결 장부에 추가했습니다. 이 단계는 준비한 API 작업이며, PG에서 새 거래를 자동 수집한 것은 아닙니다. 두 지표를 각각 재계산해보겠습니다. 원본 그래프는 네 날짜와 기존 금액을 유지합니다. 누적 장부에는 9월 5일의 3만 원이 더해집니다. 집계표의 합계는 원본 69만 200원, 누적 장부 72만 200원입니다. 어떤 범위를 저장했는지가 이후 계산에도 그대로 적용됩니다.

**자막:** 연결 장부에 데모 거래 +30,000원 / 원본 합계 690,200원 유지 · 누적 합계 720,200원

**화면 표기:** ‘데모용 거래 1건 추가 · API 준비 작업’ → 재계산 버튼 → 각 실제 집계표. 총합 보조 자막에는 ‘집계표 합계’라고 명시한다.

### T06 · 03:35–04:05 — 저장과 가게 구분

**내레이션:** 화면을 다시 열어도 저장한 지표와 배치가 유지됩니다. 다른 가게로 이동하면 그 가게의 대시보드가 보입니다. 여기의 세 지표는 미리 정의한 샘플 예시입니다. 촬영 가게로 돌아오면 방금 만든 두 그래프를 다시 확인할 수 있습니다.

**자막:** 저장한 지표와 배치를 다시 확인 / 가게마다 구분되는 파일과 대시보드

### T07 · 04:05–04:40 — 현재 규모에 맞춘 운영

**내레이션:** 웹과 API는 Vercel에, 데이터와 원본 파일은 Supabase에 배치했습니다. 원본은 서명된 업로드 경로로 전송하고, 서버가 완료 결과를 확인합니다. AI 실행에는 시간과 요청 횟수 제한을 둡니다. 현재 구성에서는 별도 Redis 대신 데이터베이스로 요청 한도를 공유합니다. 정기 작업은 저장한 통계를 다시 계산하며, 외부 PG 데이터를 새로 수집하는 기능과는 구분됩니다.

**자막:** 직접 업로드 · 실행 시간 제한 · 공유 요청 한도 / 현재 규모에 필요한 구성부터

### T08 · 04:40–05:00 — 확인한 것과 다음 과제

**내레이션:** 합성 파일로 실제 업로드와 분석, 저장, 재계산 흐름을 검증했습니다. 실제 PG 연동과 고객 사용성, 대규모 부하 검증은 다음 과제입니다. 구현과 검증 근거는 저장소에 정리했습니다. 공개 사이트에서 직접 체험할 수 있습니다.

**자막:** 구현과 검증 근거는 저장소에서 / DATA:EZ · dataez.vercel.app

## 자막 제작 규칙

- 각 장면의 두 자막은 필요에 따라 순차 노출한다. 한 번에 길게 3~4줄 쌓지 않는다.
- 수치·기간·파일 범위가 보이는 화면에서는 자막이 해당 증거를 가리지 않게 둔다.
- 전체 음성 원고를 강제로 110초·300초에 맞춰 빨리 읽지 않는다. 실제 조작·읽기 시간을 우선하고 문장을 줄인다.
- 응답 대기 축약 표시는 축약한 장면에만 넣는다. 실제 서비스 응답 시간은 별도 원본 기록으로 남긴다.
- ‘실시간 매출 자동 수집’, ‘모든 파일을 완벽하게 분석’, ‘비용 0원’, ‘고객 생산성 개선’ 같은 미검증 주장을 추가하지 않는다.
- 최종 음성과 자막은 리허설에서 확인한 결과와 일치시킨다. 대본과 다른 결과가 나오면 영상을 조작하지 않고 대본 또는 구현을 수정한다.
