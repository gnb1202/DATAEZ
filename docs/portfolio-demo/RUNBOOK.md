# 공개 배포 환경의 포트폴리오 시연 준비

2026-09-11 · Phase 0 완료. 이 문서는 Vercel + Supabase 공개 서비스 기준이다. Docker 로컬 실행은 별도 [기존 안내](../DEMO_RUNBOOK.md)를 사용한다.

2026-09-12: [Phase 1 촬영표](STORYBOARD.md)와 [내레이션·자막](NARRATION.md)을 작성했다. 질문과 시간표의 원본은 [scenario.json](scenario.json)이다. 실제 질문 실행은 Phase 2 리허설부터 진행한다.

## 접속과 계정

- 실제 웹: https://dataez.vercel.app.
- 실제 API: https://dataez-api.vercel.app.
- 이번 제작을 위해 생성한 합성 전용 계정의 이메일·비밀번호·가게 ID는 **`.local-test/portfolio-demo/account.json`**에 있다. 이 파일을 로컬에서 열어 로그인할 수 있다. 비밀번호를 문서·대화·영상·명령행에 복사하지 않는다.
- 계정은 촬영과 다음 Phase에서 계속 사용할 수 있도록 보존했다. 이전 테스트처럼 종료 시 삭제하지 않는다.
- 기존 사용자 계정·가게·파일은 사용하지 않았다. 이 도구는 DB 관리자 연결 없이 공개 API와 계정 인증으로만 준비한다.
- 비밀 파일이 없는 새 컴퓨터에서 `prepare`를 실행하면 별도 새 전용 계정을 만든다. 기존 계정으로 이어가려면 비밀 파일을 안전하게 복원해야 한다. 이 파일을 삭제해 상태를 초기화하지 않는다.

## 두 작업 공간의 역할

| 용도 | 현재 이름 | 준비 상태 |
|---|---|---|
| 완성 예시 | 샘플 가게 · 모퉁이 카페 | 원본 8행, 누적 8행, 미리 정의한 예시 지표 3개 |
| 촬영 시작 | 샘플 가게 · 모퉁이 카페 · 09/11 18:12 | 원본 8행, 누적 8행, 저장 위젯 0개 |

Phase 0 당시 ID·이름은 [baseline JSON](phase-0-baseline.json)에 보존한다. 현재 촬영 가게는 로컬 `account.json`의 `recording`, 최신 기준 검사는 `.local-test/portfolio-demo/baseline-latest.json`을 확인한다. 새 take를 만들면 촬영 가게의 이름과 ID는 바뀐다. 완성 예시와 이전 take는 남는다. 두 가게는 이번에 같은 합성 자료를 사용하므로 실제 서로 다른 지점의 매출 비교 자료로 설명하지 않는다.

예시 위젯은 **전체 결제액·일별 결제액·결제수단별 비교**다. 모두 ‘샘플 예시’로 표시되며 원본 파일 전체 기간, 원화, 수동 갱신이다. 실제 LLM이 만든 결과로 소개하지 않는다. 촬영 시작 가게에서 새 질문을 보내고 직접 저장하는 장면을 별도로 촬영한다.

## 기준 파일과 금액

- [촬영용 원본 CSV](../../samples/demo/portfolio-original.csv): 서비스 내 샘플 원본과 동일한 8행의 합성 자료.
- [추가 거래 CSV](../../samples/demo/additional-transaction.csv): 2026-09-05 카드 30,000원 1행.
- [독립 기대값](../../samples/demo/expected.json): 기존 데모의 정답을 그대로 사용한다.

| 확인 항목 | 값 |
|---|---:|
| 원본 기간 | 2026-09-01~2026-09-04 |
| 총 순결제액 | 690,200원 |
| 일별 순결제액 | 164,500 / 190,000 / 139,800 / 195,900원 |
| 카드 / 현금 | 582,700 / 107,500원 |
| 취소 | 9/2 카드 -24,000원이 합계에 포함됨 |
| 추가 거래 반영 후 누적 기대값 | 9행, 720,200원 |
| 추가 후 원본 기대값 | 8행, 690,200원 유지 |

이번 Phase에서는 추가 거래를 실제 촬영 장부에 넣지 않았다. 파일을 바탕으로 추가 후 기대값만 독립 계산했다. 촬영 초기 상태를 유지하기 위한 결정이다. ‘이번 달’ 대신 ‘파일 전체 기간’을 요청한다.

## 실행 명령

저장소 루트, 기존 Python API 의존성(`httpx` 포함), Node.js, `scripts/ui-eval`의 Playwright, Microsoft Edge를 사용한다. `.env.supabase.local`이나 관리자 키는 이 도구에 필요하지 않다.

```powershell
# 최초 준비. 이후 같은 명령은 기존 계정·가게를 재사용하고 기준만 확인한다.
python scripts/portfolio-demo/prepare.py prepare

# 원본·장부·위젯·검색 상태 확인. 업무 데이터는 변경하지 않는다.
python scripts/portfolio-demo/prepare.py check

# 실제 공개 웹 로그인·가게 전환·재접속을 확인하고 스크린샷 갱신.
python scripts/portfolio-demo/prepare.py browser

# 새로운 촬영 시작 가게를 생성. 이전 가게와 파일은 보존한다.
python scripts/portfolio-demo/prepare.py new-take
```

Windows 콘솔에서 한글이 깨지면 먼저 `$env:PYTHONIOENCODING='utf-8'`를 설정한다. 로그인은 인증 세션을 생성하므로 `check`도 완전히 무상태인 HTTP 요청은 아니다. 다만 가게·거래·대시보드는 변경하지 않는다.

준비 도중 중단되면 같은 `prepare`를 재실행한다. 가입 전 자격증명, 샘플 재시작 전 요청 ID를 로컬에 기록한다. 결과를 받지 못했더라도 해당 요청을 재사용한다. 촬영 중 변경된 데이터를 덮어쓰지 않으며, 기준과 다르면 검증이 중단된다.

현재 샘플 가게가 기록된 전용 가게와 다르면 `new-take`는 중단한다. 여러 컴퓨터·프로세스에서 동시에 준비 도구를 실행하지 않는다. 명시적으로 기록된 가게를 확인하고 진행하며, DB 전체 삭제·사용자 데이터 초기화 명령은 제공하지 않는다.

## 시연 시작 순서

1. `check`로 촬영 가게가 원본 8행·장부 8행·위젯 0개인지 확인한다.
2. 공개 웹에 전용 계정으로 로그인하고 현재 촬영 가게를 선택한다.
3. 데이터 관리 → 파일 보관함에서 `샘플_카페_매출.csv`와 분석 가능 상태를 확인한다.
4. 파일 원본/누적 장부 중 대본에 정한 범위를 선택하고 채팅으로 가져온다. 아직 자동 질문을 보내지 않는다.
5. Phase 1에서 확정한 질문으로 촬영을 시작한다. 계정 비밀번호 입력 화면은 녹화하지 않는다.
6. 다시 처음부터 찍으려면 `new-take` 후 새 촬영 가게를 선택한다. 기존 take에 같은 추가 거래를 반복 업로드하지 않는다.

추가 거래 장면은 현재 일반 장부 append API를 이용하는 별도 준비 작업이다. `POST /api/projects/{project_id}/tables/{table_id}/append`의 대상은 촬영 가게의 연결 장부 ID이며 원본 테이블이 아니다. 실제 촬영 단계에서 대상과 사전 행 수를 검증하는 절차를 보완한다. 이번 도구에는 중복 반영 위험이 있는 자동 append 명령을 넣지 않았다.

## 문제가 있을 때

| 상황 | 대응 |
|---|---|
| API 준비 실패 | `/health`, `/ready`를 확인. 준비 작업을 연달아 재전송하지 않음 |
| 계정 설정 파일 유실 | 기존 파일을 복원하거나 새 별도 계정으로 시작. 기존 DB 자료 삭제 안 함 |
| 기준 합계·행 수·위젯 개수 불일치 | 사용한 take인지 확인하고 `new-take`로 새 시작 상태 준비 |
| 검색 대기·실패 | 데이터 관리의 검색 색인 상태 확인. 완료 후 시연; 필요 시 해당 작업 재시도 |
| 가게 ID 충돌·현재 샘플 변경 | 기록과 실제 현재 가게 비교. 다른 가게를 강제로 현재 샘플로 지정하지 않음 |
| 모델 분석 실패·중단 | 분석 이력과 장부 반영 여부부터 확인. 질문·추가 거래를 무조건 재전송하지 않음 |
| 공개 환경 장애 | 준비된 실제 녹화본 또는 별도 로컬 데모 사용. 환경과 대기 편집 여부를 표시 |

## 촬영 전 보완 사항

기준 스크린샷에서 시작 안내·샘플 버튼이 상단 공간을 많이 차지하고, 예시 위젯 기본 배치는 세 지표가 한 화면에 잘 들어오지 않는다. Phase 2에서 실제 앱의 안내 접기와 위젯 배치를 조정하고 필요하면 화면 코드를 보완한다. 현재 캡처는 Phase 0 증빙이며 최종 홍보 이미지가 아니다.

이번 단계에서는 자연어 질문을 실행하지 않았다. 샘플 준비 과정의 검색 임베딩은 발생할 수 있으며 ‘LLM 비용 0’으로 표현하지 않는다. 검색 작업 상태에는 예시 가게의 과거 `cancelled`와 완료된 `succeeded`가 함께 있고 촬영 가게의 작업은 `succeeded`였다. 실제 검색·분석 결과는 이후 리허설에서 확인한다.

## Phase 2 이후 실제 리허설

```powershell
python scripts/portfolio-demo/rehearse.py
# 이미 사용한 take라면 새 가게에서 실행
python scripts/portfolio-demo/rehearse.py --new-take
# 같은 소스에서 연속 2회 성공한 뒤 공개 증거만 내보내기
python scripts/portfolio-demo/publish.py
```

리허설은 실제 공개 웹·API·모델을 사용한다. 가게마다 원본/누적 질문 2회, 수동 저장 2개, 추가 거래 1회, 두 지표 재계산, 마우스 드래그와 재접속·가게 전환을 수행한다. 실패한 시도에는 질문이 1회만 있을 수 있다. 계정 정보는 stdin으로 전달하며 명령행에 넣지 않는다.

진행 상태·모델 원응답·실패 화면은 `.local-test/portfolio-demo/takes/<project_id>/`에 남는다. 자동 재전송은 하지 않는다. 특히 `append_pending`에서 중단되면 실제 장부 행 수와 원본·위젯 상태를 확인한 뒤 판단한다. 기존 take에 append를 다시 보내지 말고 새 take를 사용한다. 이전 가게·자료는 삭제하지 않는다.

`check`는 **촬영 전 8행·저장 위젯 0개** 검사다. 완료 가게에서는 의도적으로 통과하지 않는다. 다음 촬영 준비는 `prepare.py new-take`로 만들고, 완료 가게는 리허설 JSON의 ID로 다시 연다. 이후 기준 검사는 로컬 `baseline-latest.json`에 기록하므로 최초 Phase 0 증거는 유지된다.

실제 응답에 차트가 여럿 있으면 재계산 가능한 지표인지 확인해야 한다. 최종 리허설은 요청한 선그래프 1개, 원본/누적 범위, 정확한 일별 금액, SQL, 수동 저장 설정을 모두 검사한다. 공개 스크린샷은 계정 이메일 부분만 캡처 시 가리며 숫자·차트·응답은 변경하지 않는다.
