# DATA:EZ 제품·기술 데모 촬영표

2026-09-12 · Phase 1. **제작용 대본 확정, 실제 리허설 전**이다. 질문과 장면은 현재 코드 및 Phase 0 샘플 기준으로 작성했다. 표현별 실제 LLM 결과와 촬영 소요 시간은 Phase 2에서 확인한다.

[질문·타임라인 원본](scenario.json) · [내레이션·자막](NARRATION.md) · [준비 안내](RUNBOOK.md)

## 장면을 연결하는 원칙

- 제품 영상 110초, 기술 영상 300초, 반복 영상 12초를 편집 목표로 한다. API 응답 시간이나 실제 전체 조작 시간을 의미하지 않는다.
- 하나의 촬영 가게에서 **Q1 원본 그래프 저장 → Q2 누적 장부 그래프 저장 → 거래 1회 추가 → 두 그래프 재계산**으로 이어간다. 다른 가게·다른 파일의 결과를 같은 분석인 것처럼 붙이지 않는다.
- 제품 영상은 Q1 결과만 사용한다. 기술 영상은 Q1 촬영 자료를 재사용하고 Q2 이후를 더한다. 한 take의 기본 자연어 질문은 2개다. 추가 리허설·재촬영은 별도 호출로 기록한다.
- 첫 장면은 뒤에서 완성한 P06의 실제 화면을 먼저 보여주는 구성이다. Phase 0의 예시 위젯을 방금 질문해 만든 결과로 소개하지 않는다.
- 차트는 음수 취소를 반영한 **순결제액**을 보여준다. 수수료·원가를 차감한 이익 또는 PG 정산액으로 표현하지 않는다.
- 금액은 차트 그림만 보고 판정하지 않고 정확한 집계표와 응답을 확인한다. 날짜 키와 금액 키의 이름은 응답을 따른다. 반환 필드가 반드시 `paid_at`·`amount`일 것이라고 가정하지 않는다.

## 시작 상태와 take 기록

`prepare.py check`를 실행해 촬영 가게 8행·690,200원·위젯 0개를 확인한다. Q1 실행 이후에는 위젯 0개 검사가 의도적으로 실패할 수 있으므로 이 시작 상태 검사를 완료 상태 검사로 재사용하지 않는다.

촬영 중 기록할 항목은 take 식별자, 앱 커밋·배포 주소, 가게·파일·연결 장부 ID, Q1/Q2 대화·메시지 ID, 저장 위젯 ID, 실제 처리 시간, 재시도 여부, append 전후 행 수와 합계다. `.local-test/portfolio-demo/takes/`에 실행 기록을 먼저 저장하고 비밀 값을 뺀 요약만 문서로 옮긴다. 이 기록 도구는 Phase 2에서 구현한다.

로그인과 비밀번호 입력은 촬영 전에 마친다. 파일 보관함에 원본은 이미 준비되어 있으므로 제품 본편에서 업로드를 새로 수행한 것처럼 보이지 않게 한다. 실제 업로드 장면이 필요하면 별도 take에서 촬영하고 ‘파일을 보관함에 추가하는 과정’으로 구분한다.

### T05의 금액과 표시 방식

| 범위 | 추가 전 | 추가 후 |
|---|---|---|
| 파일 원본만 | 4개 날짜, 총 690,200원 | 동일 |
| 누적 장부 전체 | 4개 날짜, 총 690,200원 | 5개 날짜, 총 720,200원 |

이번에는 현재 채팅 결과 저장 경로에 맞춰 **두 개의 일별 선그래프**를 비교한다. UI에 없는 총합 KPI가 있는 것처럼 합성하지 않는다. 총합을 편집 자막으로 보완할 때는 실제 응답에서 검증한 **‘집계표 합계’**라고 표시한다.

추가 거래는 `samples/demo/additional-transaction.csv`를 **연결 장부**에 1회 append하는 API 준비 작업이다. 거래 시각은 2026-09-05로 고정된다. 촬영 날짜가 바뀌어도 ‘오늘 새 결제가 자동 수집됐다’고 말하지 않는다. 브라우저 개발자 도구와 토큰을 촬영하지 않고, ‘데모용 거래 1건을 장부에 추가했습니다’라는 화면 설명으로 연결한다. 전송 전후 기대값과 응답은 별도 실행 기록에 남긴다.

갱신 주기는 Q1·Q2 모두 수동으로 고정한다. 영상 중 자동 갱신이 끼어드는 것을 피하고 재계산 버튼의 효과를 명확히 한다. Cron의 주기 동작은 이전 실제 [정기 작업 검증](../PUBLIC_DEMO_ACCEPTANCE.md)으로 설명하며 이번 촬영에서 새로 검증했다고 하지 않는다.

## 12초 무음 반복 영상

P03의 실제 질문 장면 4초 → P04의 성공한 차트 4초 → P06의 저장 결과 4초. 영상 아래에 ‘실제 시연 편집 · 합성 데이터’ 표시. 연결이 자연스럽도록 첫·끝 프레임을 편집하되 12초 내 실제 분석을 보장하는 문구를 넣지 않는다.

## 촬영 시 읽을 작업 순서

1. `check` 통과 상태를 기록하고 Q1·Q2 질문을 `scenario.json`에서 가져온다.
2. Q1 실행 전에 선택 파일 1개·원본 범위를 확인한다. 원본 차트의 재계산 가능한 정의와 실제 집계표가 있어야 P05로 진행한다.
3. Q1을 ‘원본 · 일별 순결제액’, KRW, 전체 기간, 수동으로 미리보기 후 저장한다. 위젯 ID를 기록한다.
4. P06 완료 화면과 새로고침을 촬영한다. 제품 영상용 원본을 확보한다.
5. 같은 가게에서 참조를 누적 장부 1개로 바꾸고 새 분석에서 Q2를 실행한다. 같은 저장 설정으로 두 번째 위젯을 저장한다.
6. 연결 장부 ID·사전 8행·690,200원, 추가 파일 해시를 기록한 뒤 1회 반영한다. 도중 실패하면 재시도 전에 실제 행 수를 확인한다.
7. 두 위젯을 재계산하고 T05의 전후 기대값을 검증한다. 성공한 화면만 촬영본으로 채택한다.
8. 새로고침·가게 전환을 촬영한다. 다음 반복은 `new-take`로 새 가게에서 시작한다. 기존 자료는 보존한다.

## Phase 2에 넘길 조건

- [x] 새 take 한 번에서 Q1·Q2가 올바른 범위와 재계산 가능한 선그래프를 반환하는지 확인.
- [x] 추가 거래·재계산·보존 검사를 담은 실행 기록 도구 구현. 실패와 정상 종료를 구분.
- [x] 시작 안내의 화면 점유와 위젯 배치를 보완해 실제 차트가 읽히게 구성.
- [x] 처리 시간·사용량을 확인하고 같은 의미의 결과가 2회 연속 재현되는지 리허설.

위 항목은 대본 완료의 선행 조건이 아니라 **촬영에 들어가기 위한 리허설 통과 조건**이다. Phase 2에서 동일한 질문으로 2회 연속 통과했다. [실행 결과](phase-2-rehearsal.json)를 참고한다. 토큰 사용량은 메시지 API에서 제공되지 않아 미확인으로 남기고 실제 처리 시간만 기록했다.

재계산 가능한 차트는 `preview_metric` 결과 자체를 사용한다. 최종 리허설에서는 정적 차트 중복 없이 한 개씩 반환했다. 입력 파일이 명시된 이 시연에서는 `library_references`와 `preview_metric`이 사용됐으며, 검색 도구를 호출한 장면으로 소개하지 않는다.
