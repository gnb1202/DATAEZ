# DATA:EZ — 업무 실행 Agent 고도화 계획

작성일: 2026-09-08 · 검토 기준 커밋: `14565f6`

> 우선순위 변경: 이후 사용자 요구에 따라 제품의 중심을 통합 매출 지표·대시보드·주기 갱신으로 확정했다. 현재 구현 기준은 [PRD.md](PRD.md)이며, 아래 환불 실행·Browser Agent 계획은 후속 확장 제안으로 보관한다. 코드 검토 결과는 참고하되 Phase 순서는 최신 PRD를 따른다.

## 1. 목표와 방향

제공된 FluidGPT AI 엔지니어/모바일 에이전트/LLM Engineer 공고를 기준으로 작성했다. 공고의 핵심은 실제 소프트웨어의 상태를 이해하고 여러 단계의 업무를 안전하게 실행하며, 품질·비용·지연을 측정하는 시스템이다.

DATA:EZ의 목표를 **“자연어 데이터 관리 플랫폼”에서 “데이터와 정책을 근거로 업무 시스템을 조작하고 결과를 검증하는 Agent”로 확장**한다. 기존 장부·RAG·도구 실행 기능을 출발점으로 삼는다.

지원 시점은 약 2주를 염두에 두되, 사용자 요청에 따라 아래 Phase는 기간이 아닌 의존성과 완료 기준으로 나눈다. 이번 작업 범위는 검토와 계획 수립이며 제품 코드 구현은 후속 작업이다.

포트폴리오의 핵심 질문:

> 예약·결제 불일치를 발견한 Agent가 정책 근거를 확인하고, 승인받은 조치만 업무 화면에서 실행한 다음, 실제 처리 여부를 재확인할 수 있는가?

## 2. 현재 프로젝트와 공고의 연결

| 공고의 요구 | 저장소에서 확인한 기반 | 고도화할 부분 |
|---|---|---|
| Python/LLM tool-use | FastAPI, OpenAI function calling, 14개 도구 | 상태를 지속 보관하는 실행 런타임 |
| action planning / workflow | 라우터 → worker → 도구 반복 실행 | 명시적 목표·단계·완료 조건, 승인 대기·재개 |
| RAG / domain knowledge | pgvector, dense+sparse RRF, 한국어 형태소 검색 | 검색·근거 평가, 정책 버전, 도메인 데이터 일관성 |
| memory / process log | 최근 대화 압축, 메시지별 steps, 변경 감사 기록 | 참조 대상 메모리, run/event 기록, 장애 후 재개 |
| evaluation / monitoring | 라우팅 골든셋, judge, 비용·지연·도구 메트릭 | DB 최종 상태·UI 결과에 기반한 업무 성공률 |
| GUI / browser / mobile | 웹 UI는 있으나 외부 UI 조작 구현은 발견하지 못함 | 별도 업무 앱에 대한 관찰→행동→재관찰 |
| ERP/MES/CRM 연동 | 자체 장부 CRUD | 외부 업무 앱 1개 연동부터 증명 |
| 운영 가능한 제품 | Docker Compose, 인증, SQL 제한, CI | 멱등성·복구·비동기 작업·실서비스 통합 테스트 |

강점은 이미 개선 과정을 설명할 재료가 있다는 점이다. 라우터 프리필터 수정, forbidden_tools 채점, 한국어 sparse 검색, SSE, 단계별 계측은 면접에서 설명하기 좋다. 다만 README 수치는 과거 기록이며 이번 검토에서 모델 평가를 재실행한 수치는 아니다.

## 3. 코드 검토에서 확인한 우선 과제

### A. 후속 질문 실패는 운영 경로에도 영향을 줄 수 있다

- `api/app/agent.py::_select_tools`와 `api/app/router.py::select_tools_via_orchestrator`는 질문과 첨부 여부를 받고 대화 이력은 받지 않는다.
- worker에는 이력이 전달되지만, 사용할 수 있는 도구는 앞선 라우팅에서 이미 제한된다.
- 따라서 “그중 취소된 것만 다시 보여줘” 같은 요청의 실패를 평가 하네스 문제로만 설명할 수 없다. 운영 경로도 같은 정보 부족을 가진다.
- 라우터에 검증된 최근 대상·작업 요약을 제공하고, 정보가 부족하면 재조회 또는 명확화로 전환해야 한다.

### B. 변경 전 스키마 확인과 실행 승인은 서로 다른 보호 장치다

- `api/app/agent_tools.py::_auto_describe_if_needed`는 컬럼 구조를 읽지만 변경 대상과 영향 범위를 승인받지는 않는다.
- `api/app/prompts.py:89`는 확인 없는 즉시 실행을 요구한다. `api/app/eval_judge.py:121` 및 관련 루브릭도 같은 행동을 장려한다.
- SQL의 WHERE 강제는 광범위한 조건에 의한 대량 변경까지 막지는 못한다.
- 변경안 생성, 서버 측 정책 판정, 영향 범위 미리보기, 승인 후 재검증을 함께 구현해야 한다. 프롬프트만 변경해서는 부족하다.
- 감사 로그는 변경 후 별도 호출이며 실패를 무시한다. 중요한 변경과 그 기록 사이의 원자성도 보강 대상이다.

### C. 계측은 있지만 턴별 비용과 실패 상태에 빈틈이 있다

- `api/app/llm.py::generate_embeddings`는 전역 메트릭을 기록하지만 `track_llm_call`에 TurnLedger를 넘기지 않는다. 검색 임베딩 비용이 현재 턴의 저장 사용량에 합쳐지지 않는다.
- `api/app/agent.py::run_agent_streaming`의 예산 초과·LLM 오류 분기는 최종 meta 프레임 전에 반환한다. 앞서 실행된 도구와 사용량의 최종 집계가 누락될 수 있다.
- 스트리밍 시작 시 동기 `_select_tools`를 직접 호출한다. 동시 요청에서 이벤트 루프를 막는지 측정하고 비동기화/스레드 분리를 검토한다.
- 예산 검사는 worker 누적 토큰 기준이다. 전체 실행의 비용·시간·도구 호출 예산으로 확장한다.
- `web/app/components/reasoning-steps.tsx`는 tool step에 항상 성공 아이콘을 표시한다. 실패·대기·검증 전 상태를 구분해야 한다.

### D. 문서 적재 실패와 검색 결과 없음이 구분되지 않는다

- `api/app/rag.py::chunk_and_embed_document`는 기존 청크를 먼저 삭제·커밋하고 배치별로 적재하며, 예외 시 지금까지의 삽입 수를 반환한다.
- `api/app/main.py::api_upload_document`는 그 수를 정상 응답으로 반환한다. 부분 실패가 검색 가능한 완성 문서처럼 보일 수 있다.
- 적재는 `to_thread`로 일부 오프로딩하지만 HTTP 요청이 완료를 기다린다. 지속 가능한 백그라운드 작업 큐와는 다르다.
- 검색 함수 역시 예외 시 빈 리스트를 반환한다. “근거가 없음”과 “검색 시스템 장애”를 제품과 평가에서 구분해야 한다.

### E. 업무 성공과 안전성은 아직 충분히 검증되지 않았다

- 현재 실행 가능한 eval CLI는 L1 라우팅을 중심으로 한다. `docs/ARCHITECTURE.md`의 L2 표기는 구현된 실제 DB 행동 평가로 확인되지 않았다.
- `api/tests/test_integration.py`도 DB/모델을 mock하는 API 테스트다. 실제 DB 제약·롤백·동시 실행을 증명하지 않는다.
- 이번 검토에서 핵심 8개 테스트 파일 **137개 통과**. 전체 테스트는 54개 진행 표시 이후 대기가 길어 중단했다. 원인을 확정하지 않았으며 전체 통과를 주장하지 않는다.
- 외부 모델 실측 평가, Docker 전체 기동, 웹 브라우저 실행 검증은 이번 검토에 포함하지 않았다.

## 4. 대표 업무 시나리오

### 시나리오: 예약 취소·결제 대조와 환불 처리 요청 등록

사용자 요청 예시:

> “어제 취소된 예약 중 결제가 남아 있는 건을 찾아줘. 규정에 맞는 환불안을 만들고, 내가 승인한 건은 관리 화면에 처리 요청으로 등록해줘.”

실행 흐름:

1. 예약·결제 장부를 대조한다. 기간·예약 상태·결제 식별자로 후보를 결정한다.
2. 적용 가능한 환불 정책을 검색한다. 문서 버전과 관련 조항을 함께 기록한다.
3. 대상별 금액·사유·근거·예외 사항을 포함한 처리안을 생성한다.
4. 사용자가 구체적인 대상과 금액을 승인한다. 정보 부족·정책 충돌은 보류한다.
5. 별도 예약/결제 관리 웹 앱에서 현재 상태를 관찰하고 승인된 처리 요청을 등록한다.
6. 등록 결과를 재조회하여 외부 처리 ID와 상태를 확인한다.
7. DATA:EZ에 처리 결과와 증거를 연결한다. 중복 요청과 미확인 상태는 별도로 표시한다.

데모에서 실제 결제 취소 대신 테스트 앱의 환불 요청 등록을 사용한다. 이 경우 이력서에도 “테스트 업무 앱 연동”으로 정확히 표현한다. 외부 등록 성공과 실제 자금 환급 완료는 별개 상태로 관리한다.

현재 `samples/refund_policy.md`는 일반 상품 정책이고 README의 스크린골프 예약 데이터와 도메인이 다소 다르다. 먼저 예약 서비스용 정책·데이터·예외 케이스를 일관되게 맞춘다.

## 5. 목표 구조와 설계 원칙

책임을 다음처럼 분리한다.

| 구성 요소 | 책임 |
|---|---|
| Task / Run | 사용자 목표, 소유자, 상태, 현재 단계, 비용·시간 예산 |
| Context | 최근 확인한 예약/결제 ID, 사용자 제약, 승인, 정책 버전 |
| Planner | 허용된 도구를 이용하는 다음 단계와 성공 조건 제안 |
| Policy / Approval | 도구 권한, 영향 범위, 승인 필요 여부를 서버가 판정 |
| Executor | DATA:EZ 도구 또는 외부 앱 어댑터 호출 |
| Verifier | DB·화면·외부 ID로 사후 조건 검사 |
| Event Store | 단계별 입력·상태·결과·실패·재시도·증거 저장 |
| Evaluation | 실제 결과와 금지된 부작용, 비용·지연을 평가 |

- 기존 ToolExecutor와 SQL 계층을 활용하되 실행 권한 검사는 공통 서버 경계에서 강제한다.
- 작업 계획 전체를 맹목적으로 실행하지 않고 단계마다 새 상태를 확인한다.
- 상태는 `planned → awaiting_approval → running → verifying → succeeded`를 기본으로 하고 `failed`, `cancelled`, `needs_attention` 분기를 둔다.
- 승인 대상은 action ID, 사용자/프로젝트, 대상 ID, 변경 내용 해시, 데이터 버전, 만료 시각에 묶는다. 승인 이후 변경안이나 대상 상태가 바뀌면 다시 검증한다.
- 외부 작업은 응답이 끊겨도 성공했을 수 있다. 중복 실행 전에 조회하며 결과가 불명확하면 `needs_attention`으로 보낸다.
- 내부 DB의 원자적 변경과 외부 시스템의 보상 작업을 구분한다. 임의의 외부 실행에 만능 undo를 약속하지 않는다.
- 로그는 모델의 숨은 추론이 아니라 실행 계획, 호출, 관측 결과, 승인, 증거를 저장한다.
- 프레임워크 도입 여부는 체크포인트·재개·테스트 요구를 기준으로 별도 결정한다. 현재 루프를 버리는 전면 재작성은 선행 조건이 아니다.

## 6. Phase별 실행 계획

### Phase 0 — 재현 가능한 기준선과 업무 정의

**목적:** 이후 개선을 비교할 수 있는 출발점을 만든다.

작업:

- 대표 업무와 비즈니스 규칙 확정: 예약 취소 시점, 결제 상태, 부분 처리, 중복 요청, 정책 미존재.
- 재생 가능한 seed/reset 데이터와 정상·예외 데모 구성.
- 전체 테스트 지연 원인 추적, 외부 호출 격리, 실제 DB 테스트 실행 경로 분리.
- 실행 환경·커밋·모델 설정·프롬프트/데이터 버전·평가 원본 저장 형식 확정.
- 현재 후속 질문, 비용 누락, 부분 적재 실패를 재현 사례로 남긴다.

완료 기준:

- 다른 환경에서도 같은 seed로 대표 업무를 시작할 수 있다.
- mock 테스트와 실제 DB/모델 평가가 분리되어 각 명령의 외부 의존성이 명확하다.
- 현재 결과가 실패하더라도 원본 보고서와 실패 원인이 남는다.

### Phase 1 — 변경 실행의 안전성과 결과 기록

**목적:** 에이전트가 실제 변경을 맡을 수 있는 최소 실행 경계를 만든다.

작업:

- `pending_actions`와 변경안 API: 대상·변경 전후·예상 영향 행 수·근거 표시.
- 서버 정책: 조회 자동 실행, 정해진 위험 변경은 승인 대기, 허용 범위 밖 변경은 차단.
- 승인·거절·만료·중복 승인, 실행 전 대상 버전 재검증과 멱등성 키.
- 내부 변경과 감사 이벤트를 같은 트랜잭션에 기록하거나 outbox로 전달 보장.
- 제한된 행 수정/삭제에 대한 before-image와 복구를 구현하고 복구 시 충돌을 검사한다. 스키마 변경 등 복원 어려운 작업은 별도 정책으로 제한한다.
- 프롬프트·judge 루브릭·API·프론트의 승인 정책을 함께 변경.
- 스트리밍 종료 사유와 사용량을 공통 종료 경로에서 기록. 임베딩 비용을 턴에 귀속.
- UI의 실행 상태를 성공/실패/승인 대기/검증 중으로 분리.

완료 기준:

- 모델이 임의로 mutation을 호출해도 승인 정책을 우회할 수 없다.
- 거절·만료·권한 불일치·승인 후 데이터 변경 시 수정이 발생하지 않는다.
- 같은 action을 반복 승인·재전송해도 실제 변경은 한 번만 발생한다.
- 성공/오류/취소 경로의 실행 결과와 발생한 비용이 남는다.

### Phase 2 — 실제 업무 결과를 측정하는 L2 평가

**목적:** 라우팅 점수에서 업무 완료율로 평가 범위를 넓힌다.

작업:

- 실제 PostgreSQL seed + 에이전트 호출 + 최종 상태 검사를 수행하는 하네스.
- 회귀 CI는 모델 응답을 고정하고 실제 도구/DB를 사용. 별도 모델 평가는 실제 LLM을 사용한다.
- 초기 30~50개 시나리오: 정상, 다중 턴, 모호한 대상, 승인 거절, 중복 실행, 권한 위반, 인젝션, 부분 실패.
- 참조 해결을 라우터에 연결하고 “그중/같은 조건/다시” 케이스를 end-to-end로 검증한다.
- 단일 worker와 현재 2단 라우팅, router/worker 모델 조합을 같은 데이터로 비교한다.
- 모델 평가 시나리오를 반복 실행하고 실패도 포함한 비용·지연·성공률을 기록한다.

완료 기준:

- 성공은 원하는 DB 결과와 금지된 부작용 부재로 판정한다. 답변이 그럴듯한지는 별도 항목이다.
- 모든 안전성 필수 케이스에서 승인 우회·타 사용자 변경·중복 변경이 0건이어야 한다.
- baseline과 개선 버전의 원본 결과를 동일한 명령으로 비교할 수 있다.
- 정상 업무 성공률의 초기 목표는 90% 이상으로 제안하되, baseline 확인 후 평가셋을 고정하고 변경 이력을 남긴다. 테스트 통과를 실제 운영의 무사고 보장으로 표현하지 않는다.

### Phase 3 — 지속 가능한 다단계 실행과 문맥

**목적:** 작업을 중단·재개할 수 있고 실패를 다룰 수 있게 만든다.

작업:

- `agent_runs`, `run_steps`, `run_events`에 실행 상태와 단계 결과를 저장한다.
- sync/streaming의 공통 실행 경로를 만들고 SSE는 저장 이벤트의 전달 계층으로 정리한다.
- 승인 대기, 재연결, 서버 재시작 후 재개 및 실행 소유권/lease 관리.
- 일시 오류에만 제한적으로 재시도. 비멱등 작업은 결과 확인 후 다음 행동을 결정한다.
- 최근 장부·예약·결제 대상과 정책 버전을 구조화해 보관한다. 소유자 범위, 만료, 갱신 규칙을 둔다.
- 토큰뿐 아니라 실행 시간·비용·도구 호출 수에 대한 예산을 적용한다.

완료 기준:

- 실행 도중 서버를 재시작해도 완료된 변경이 중복 실행되지 않는다.
- 재접속한 UI가 현재 단계와 승인 대기 상태를 복구한다.
- 모호한 지시를 임의 대상 변경으로 이어가지 않는다.
- 실패 주입 테스트에서 복구 또는 명시적인 수동 확인 상태로 끝난다.

### Phase 4 — 외부 업무 화면을 조작하는 Browser Agent

**목적:** 공고의 화면 상태 인식·실행 자동화 요구를 직접 보여준다.

작업:

- DATA:EZ와 분리된 예약/결제 관리 테스트 앱 또는 접근 가능한 테스트 업무 시스템 1개 선정.
- 화면 관찰 결과를 URL, 제목, 주요 텍스트, 조작 가능한 요소, 현재 레코드, 스크린샷 증거로 구조화.
- 허용된 화면 행동을 모델이 선택하고, 서버가 검증한 대상에 한해 실행.
- 클릭·입력·이동 후 화면을 다시 읽고 기대 상태를 확인한다. 클릭 성공을 업무 성공으로 간주하지 않는다.
- 텍스트/접근성 요소로 충분한 화면부터 만들고, 의미 있는 별도 시각 요소 케이스에서 스크린샷 인식을 검증한다.
- 외부 화면의 인젝션 문구, 세션 만료, 지연 로딩, 모달, 레코드 변경, 결과 응답 유실을 평가한다.
- 도메인 허용 목록, 사용자별 세션 격리, 민감 정보 마스킹과 실행 증거 보관.

완료 기준:

- 대표 업무가 DATA:EZ 요청에서 외부 등록 및 결과 재조회까지 이어진다.
- 페이지 상태·처리 대상이 달라지면 감지하고 복구하거나 보류한다.
- 단순 고정 클릭 스크립트와 상태를 보고 행동을 선택하는 Agent를 구분해 구현·설명할 수 있다.
- UI 실행 성공률, 잘못된 대상 조작 수, 재시도 및 복구율을 별도 보고한다.

범위 선택: 모바일과 데스크톱은 후속 확장이다. 먼저 브라우저 한 환경에서 전체 흐름을 완성한다. 모바일 역량을 별도로 보여주려면 이후 에뮬레이터와 테스트 앱 기반 동일 시나리오를 추가한다.

### Phase 5 — RAG와 적재의 운영 품질

**목적:** 잘못된 정책과 불완전한 문서가 실행 근거가 되는 것을 막는다.

작업:

- 정책 질문·정답 근거 청크를 가진 30~50개 검색 평가셋.
- recall@5, MRR, 인용 근거 적합성, 무근거 답변·판단 비율 측정.
- dense-only/sparse-only/hybrid를 비교하고 실패 유형에 따라 재작성·리랭킹의 필요성을 결정한다.
- 정책 유효 기간·버전·적용 대상 및 상충 정책 처리.
- 지속 가능한 적재 job과 상태: queued/running/ready/failed, 재시도와 실패 사유.
- 새 버전 적재 완료 후에만 공개한다. 실패 시 기존 검색 가능한 버전을 유지한다.
- “문서에 근거 없음”과 “검색 장애”를 별도 결과로 반환한다.

완료 기준:

- 임베딩 부분 실패가 ready 문서로 공개되지 않는다.
- 근거 미존재·만료·충돌 시 조치가 자동 확정되지 않는다.
- 검색 개선 전후를 같은 평가셋과 지연/비용 기준으로 비교할 수 있다.

대표 업무에서 필요한 최소한의 정책 근거 표시는 Phase 2부터 포함한다. Phase 5는 그 기능의 품질과 적재 신뢰성을 확장하는 단계다.

### Phase 6 — 운영 실증과 채용 제출물

**목적:** 구현 사실과 개선 효과를 검증 가능한 사례로 만든다.

작업:

- 대표 업무 end-to-end 실행과 실패 주입 회귀를 배포 환경에서 수행한다.
- trace/run ID로 화면 이벤트, 도구 실행, DB 변경, 모델 비용을 연결한다. ID를 Prometheus 라벨로 넣지는 않는다.
- 지표: 업무 성공률, 승인 위반, 중복 변경, 근거 없는 완료 보고, 복구율, TTFT, 전체 p50/p95, 성공 건당 비용.
- 성공 건당 비용에는 실패/재시도에 사용한 비용도 포함한다. 수동 승인 대기 시간과 시스템 처리 시간은 분리한다.
- 3~5분 정상 시연, 실패·복구 시연, 아키텍처 문서, 실험 원본, 주요 설계 결정 정리.
- README의 구현 여부와 계측 설명을 실제 코드에 맞추고, 테스트 앱·실사용·실측 범위를 구분한다.

완료 기준:

- “실행했다”는 답변과 실제 결과의 일치를 증거로 보여준다.
- 채용 담당자가 재현 절차, 성능 수치의 조건, 설계상 한계를 확인할 수 있다.

## 7. 우선순위와 오늘 시작할 순서

전체 의존성: **Phase 0 → 1 → 2 → 3 → 4 → 6**. Phase 5의 정책 근거 최소 기능은 앞 단계에 포함하고, 검색 최적화·대규모 적재는 이후 확장한다.

오늘은 다음 단위로 시작하는 것이 적합하다.

1. **업무 명세와 fixture 확정:** 대표 요청, 성공 조건, 금지된 부작용, 예약/결제/정책 샘플.
2. **현재 실패의 재현:** 후속 질문 도구 누락, 비용 누락, 거짓 성공 상태, 테스트 지연.
3. **첫 수직 기능 구현:** “환불 처리안 생성 → 승인/거절 → 내부 테스트 데이터 변경 → 사후 확인”을 API와 UI까지 연결.
4. **같은 기능의 행동 평가:** 정상/거절/중복/승인 후 변경/권한 위반 시나리오를 실제 DB로 검증.

첫 구현 이후 체크포인트와 외부 브라우저 실행으로 확장한다. 광범위한 파일 분할, UI 전면 개편, 프레임워크 전환을 먼저 진행하지 않는다.

지원이 먼저 필요하다면 제출 가능한 최소 범위는 **한 업무의 승인·실행·결과 검증 + 실제 DB 평가 + 외부 화면 실행 데모 + 정직한 측정 보고서**다. 모바일, 여러 ERP 커넥터, 복잡한 장기 메모리, 별도 벡터 DB 이전은 보류할 수 있다.

## 8. 이력서에서 만들고 싶은 문장

아래는 고도화 후 사용할 형식이며 현재 성과가 아니다. 숫자는 실측 결과로만 채운다.

> 자연어 요청으로 예약·결제를 대조하고 정책 근거를 확인한 뒤, 승인된 처리 요청을 외부 관리 화면에 등록하는 업무 Agent를 구현했습니다. 서버 측 승인 정책, 멱등 실행, 체크포인트와 사후 검증을 적용하고, N개 업무 시나리오에서 성공률 X%, p95 지연 Y초, 성공 건당 비용 Z를 측정했습니다. [실패 유형]을 개선해 [전후 결과]를 확인했습니다.

현재 제출 가능한 강점은 기존 라우팅·검색·스트리밍·평가 개선 경험이다. 향후 추가할 차별점은 **안전한 실제 실행과 검증 가능한 업무 완료**다.
