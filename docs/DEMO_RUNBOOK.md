# 지속형 데모 실행 안내

2026-09-10 · Phase 1–2. 실제 Next.js 앱, FastAPI, PostgreSQL을 사용한다. 웹·API 프로세스를 종료해도 가게·원본 파일·대화·저장 지표·레이아웃이 남는다. 외부에 공개한 서비스는 아니며, 기본 주소는 이 컴퓨터에서만 접속할 수 있다.

## 시작·상태·종료

필수: Docker Desktop/Engine과 Compose v2, Python 3.10 이상, 사용 가능한 모델 API 키. 저장소 루트에서 실행한다.

```powershell
# .env가 없을 때만 복사한 뒤 OPENAI_API_KEY를 설정한다.
Copy-Item .env.example .env
python scripts/demo/run.py start
python scripts/demo/run.py status
python scripts/demo/run.py stop
python scripts/demo/run.py start --no-build
```

- 실제 앱: [http://localhost:3000](http://localhost:3000). 회원가입 후 시작한다. 테스트용 계정을 필수로 요구하지 않는다.
- API/DB 준비 상태: [http://localhost:8000/ready](http://localhost:8000/ready).
- `3131`의 디자인 자료·HTML 화면과 실제 앱은 별개다.
- `start`는 이미지를 빌드하고 실행한다. `--no-build`는 기존 이미지를 사용한다.
- `restart --no-build`는 같은 환경을 종료한 뒤 다시 실행한다. 소스 변경 후에는 `start`로 빌드한다.
- 파일·DB를 삭제하는 명령은 제공하지 않는다. `stop`은 이 데모의 실행 중 컨테이너만 멈춘다.

다른 프로그램이 기본 포트를 사용하면 첫 실행 때 `start --web-port 3139 --api-port 8149`로 지정한다. 한 번 선택한 포트는 `.local-test/demo/settings.json`에 저장한다. 변경하려면 먼저 `stop`하고 이 파일의 포트 두 값을 수정한 뒤 `start`로 웹까지 다시 빌드한다. 브라우저용 API 주소는 웹 빌드에 포함된다.

## 무엇이 보관되는가

| 위치 | 내용과 동작 |
|---|---|
| `.env` 또는 실행 프로세스 환경 | 모델 키·모델 선택. 키를 화면·보고서에 기록하지 않는다. |
| `.local-test/demo/settings.json` | 데모 전용 DB 비밀번호·JWT 키·포트. 최초 생성 후 재사용하며 Git에서 제외한다. |
| `dataez-demo-<작업 경로 해시>_pgdata` | 계정, 가게, 거래, 대화, 지표 정의·배치 등 PostgreSQL 데이터 |
| `dataez-demo-<작업 경로 해시>_uploads` | 업로드한 원본 파일 |

이 실행 도구는 루트 Compose에 데모 설정을 덧붙인다. 고정 컨테이너 이름을 없애 일반 Compose, 임시 테스트 DB, 다른 프로젝트와 충돌하지 않도록 했다. 컨테이너와 볼륨의 작업 경로 소유 라벨을 확인하며 다른 소유자로 표시된 자원은 관리하지 않는다.

데모는 로컬 파일 저장, 로컬 주소, 별도 DB·JWT 설정을 강제한다. 루트 `.env`의 기존 사용자 DB나 원격 원본 저장소를 사용하지 않는다. PostgreSQL 포트는 호스트에 공개하지 않는다. API는 **1개 프로세스·복제본 1개**로 실행한다. Redis는 필요하지 않으며 요청 횟수만 API 재시작 때 초기화된다.

설정 파일을 지워도 볼륨은 남는다. 이때 새 비밀번호를 만들어 기존 DB에 연결하려 하지 않고, 원래 설정을 복원하도록 중단한다. 백업하려면 DB·원본 볼륨과 이 설정 파일을 함께 보관한다. 작업 폴더 경로를 바꾸면 다른 데모 프로젝트 이름이 되므로 기존 환경을 그대로 가져오는 이사 기능으로 사용하지 않는다.

## 첫 체험: 자연어 → SQL → 그래프 → 저장

1. 로그인 후 **샘플 데이터로 시작**을 누른다. 계정 전용 ‘샘플 가게 · 모퉁이 카페’와 가상 거래 8행의 원본 CSV를 준비한다.
2. AI 채팅에서 선택된 파일의 **파일 원본만** 범위와 질문 초안을 확인한다. 준비 버튼은 질문을 자동 전송하지 않는다.
3. 질문을 보낸다. 기본 초안은 `paid_at`별 `amount` 합계를 원화 꺾은선 그래프로 요청하고, 음수 취소를 유지하며 전체 기간을 사용한다.
4. 결과의 **집계표·SQL**에서 정확한 금액과 실행 근거를 확인한다.
5. **대시보드에 저장** → 단위·갱신 주기 확인 → **설정으로 미리보기** → **이 설정으로 저장**을 누른다.
6. **대시보드에서 보기**로 이동해 위젯을 이동하거나 크기를 바꾼다. `stop` 후 `start --no-build`하고 같은 계정·가게에서 기록을 확인한다.

날짜는 **2026-09-01~09-04**로 고정한다. 달이 바뀌어도 같은 시연 결과를 얻으려면 ‘이번 달’ 대신 ‘파일 전체 기간’으로 질문한다. 합성 데이터이며 실제 PG 파일은 사용하지 않는다.

## 완성 화면과 샘플 재시작

**예시 대시보드 보기**는 현재 샘플 가게에 합계 KPI, 일별 꺾은선, 결제수단별 막대그래프를 준비한다. 각 제목에 ‘샘플 예시’를 붙인다. 서버에 미리 정의한 지표를 기존 계산·권한 검사·저장 서비스로 실행하며, LLM이 즉석 생성한 결과로 표시하지 않는다. 원본 범위·전체 기간·원화·수동 갱신이 기본이다. 색인 작업은 서버의 기존 RAG 설정을 따르므로 모델 사용료와 별개라고 가정하지 않는다.

다시 눌러도 같은 저장 키로 기존 위젯을 반환한다. 중간에 실패하면 이미 만든 위젯은 재사용하고 나머지를 준비한다. 사용자가 바꾼 기존 위젯 제목·배치는 덮어쓰지 않는다. 직접 삭제한 예시 위젯은 버튼을 다시 누르면 생성된다.

대시보드가 이미 있어도 샘플·내 파일 시작 버튼이 바로 보인다. **시작 안내**는 사용 방법을, **직접 지표 만들기**는 수동 설정을 펼친다. **샘플 체험 다시 시작**에서는 현재 샘플 이름과 보존 범위를 확인한 뒤 **새 샘플 만들기**를 누른다.

- 새로운 가게·파일에서 질문 초안부터 시작한다. 대시보드 예시가 필요하면 별도로 준비한다.
- 이전 샘플의 파일·거래·대화·위젯은 그대로 보존한다. 왼쪽 가게 선택에서 다시 열 수 있다.
- 일반 가게와 다른 계정의 데이터도 유지한다. DB 전체 초기화나 자동 샘플 삭제를 수행하지 않는다.
- 현재 샘플 ID와 요청 ID를 함께 검증한다. 같은 요청의 재시도는 같은 새 샘플을 반환하고, 다른 탭에서 샘플이 바뀌었으면 새로고침을 안내한다.
- 재시작을 여러 번 하면 보존된 샘플 가게가 늘어난다. 이것은 데이터 보존 정책에 따른 동작이다.

## 원본과 누적 장부 비교

[추가 거래 CSV](../samples/demo/additional-transaction.csv)와 [독립 기대값](../samples/demo/expected.json)을 사용한다. 샘플에 추가 거래가 없는 상태에서 **한 번만** 추가한다.

1. 이 추가 시나리오는 현재 공개 API로 실행한다. [API 문서](http://localhost:8000/docs)에서 로그인한 계정의 Bearer 토큰으로 인증하고 `GET /api/library/files/sample-workspace`로 현재 샘플 가게 ID를 확인한다. 파일 목록의 해당 파일 `bindings[0].table_id`가 누적 장부 ID다.
2. `POST /api/projects/{project_id}/tables/{table_id}/append`의 `file`에 추가 거래 CSV를 전달한다. 원본 분석용 테이블 ID 대신 연결 장부 ID를 사용한다. 자동 브라우저 검증도 이 API로 추가한다. 현재 화면에 일반 테이블 추가 가져오기 전용 버튼을 새로 제공한 것은 아니다.
3. 실제 앱 보관함에서 기존 샘플 파일을 골라 원본과 누적 범위를 각각 명시하고, 전체 기간 `amount` 합계를 비교한다. 새 파일을 별도 보관만 하는 것은 기존 장부에 거래를 추가하는 동작과 다르다.

| 비교 | 원본 8행 | 추가 후 누적 9행 |
|---|---:|---:|
| 전체 합계 | 690,200원 | 720,200원 |
| 카드 | 582,700원 | 612,700원 |
| 현금 | 107,500원 | 107,500원 |

원본 일별 합계는 9/1 **164,500**, 9/2 **190,000**, 9/3 **139,800**, 9/4 **195,900원**이다. 누적 장부에만 9/5 **30,000원**이 추가된다. 원본 예시 위젯은 재계산해도 이 추가 거래를 포함하지 않는다. 일반 테이블의 추가 가져오기는 반복 결제 출처의 중복 검토 기능과 다르므로 같은 CSV를 반복 추가하지 않는다. 깨끗한 상태가 필요하면 새 샘플을 만든다.

## 오류별 확인

| 상태 | 다음 행동 |
|---|---|
| Docker 연결 실패 | Docker Desktop을 실행하고 다시 시도 |
| `Set OPENAI_API_KEY` | 루트 `.env` 또는 프로세스 환경에 사용할 수 있는 키 설정 |
| `Port ... is in use` | 점유한 프로그램을 확인하거나 위의 포트 변경 절차 사용 |
| 소유 라벨 불일치 | 다른 작업 폴더의 환경인지 확인. 강제로 종료하지 않음 |
| DB 볼륨은 있는데 설정이 없음 | 해당 볼륨에 사용하던 `settings.json` 복원 |
| API/DB 준비 실패 | `status` 및 Docker Desktop에서 이 데모의 API/DB 로그 확인 |
| 샘플 준비·저장 실패 | 같은 화면에서 재시도. 이전에 완료된 파일·위젯 재사용 |
| 현재 샘플 변경 충돌 | 페이지 새로고침 후 현재 샘플 이름 재확인 |
| 분석 오류·응답 수신 중지 | 복원된 질문·첨부를 확인하고 **이 대화의 처리 결과 확인**으로 저장 기록 조회. 전송은 자동 반복하지 않음 |
| 처리 기록 조회 실패 | 초안을 유지한 채 같은 조회 버튼으로 다시 확인 |

웹 이미지는 `HOSTNAME=0.0.0.0`으로 서버를 바인딩하고 `127.0.0.1`로 상태를 검사한다. 기존에는 Docker가 전달한 호스트 이름에만 바인딩돼 화면에 접속할 수 있어도 상태 검사에서 실패할 수 있었다.

## 검증 재실행

```powershell
python scripts/demo/test_run.py
# 실DB API 검사는 격리된 테스트 DB의 DSN을 설정한 뒤 실행한다.
python -m pytest api/tests/test_sample_demo.py api/tests/test_file_scopes.py api/tests/test_file_library.py api/tests/test_rate_limiter.py -q

# 최초 한 번 Playwright 의존성 설치; Windows 기본 브라우저 채널은 msedge.
npm --prefix scripts/ui-eval ci
python scripts/demo/verify.py --live-llm
```

브라우저 검사는 이미 실행 중인 데모에 별도 합성 계정을 만들고, 실제 모델 질문 **1개**를 보낸다. 데모 전체를 종료·재시작하므로 이 환경을 사용하는 동안에는 검사를 동시에 실행하지 않는다. 기존 계정의 자료는 삭제하지 않으며 검사 계정도 시연용으로 남긴다. 다른 OS에서는 설치된 Playwright 브라우저 채널을 `DEMO_BROWSER_CHANNEL`로 지정한다.

보고서·화면·세션·데모 로그인은 `.local-test/demo/acceptance-<UTC시각>/`에 보관한다. `access.json`과 `session.json`에는 계정 인증정보가 있으므로 공유 자료에 복사하지 않는다. 초기 단계가 성공하고 재접속 검사만 재시도할 경우 `--resume .local-test/demo/acceptance-... --live-llm`을 사용하면 질문을 다시 보내지 않는다.

검증 결과와 공개 가능한 근거는 [Phase 1 점검 기록](DEMO_ACCEPTANCE.md)에 별도로 기록한다. 이 단계는 합성 CSV와 로컬 Docker 데모 검증이다. 외부 호스팅, 실제 PG 연동, 원격 저장소와 실제 사용자의 사용성 관찰은 이후 작업이다.
