# 가게별 지표 — 여러 장부 통합·대화 생성·서버 주기 갱신

## 사용할 수 있는 기능

1. 사이드바에서 가게를 만들거나 선택한다. 기존 project API/데이터는 그대로 사용한다.
2. 장부 관리에서 선택한 가게의 파일을 등록한다.
3. 대시보드의 **갱신 가능한 지표 만들기**를 연다.
4. 장부, 숫자 컬럼, 집계 방식과 선택적인 그룹 컬럼을 지정한다.
5. **계산하고 대시보드에 추가**를 누른다.
6. 장부에 데이터를 추가한 후 위젯의 **재계산**을 누른다.

단일 장부는 합계·행 건수·평균·최솟값·최댓값을 지원한다. 날짜 컬럼은 일/주/월 단위로 묶을 수 있다. 기간은 전체/이번 달/지난달/최근 30일을 지원한다. 그룹 없는 지표는 KPI, 그룹 있는 지표는 차트다.

## 여러 장부 통합 (이번 페이즈)

대시보드의 **여러 장부의 결제액 합치기**에서 같은 가게의 장부 2~5개를 고른다. 각 장부의 표시 이름·금액 컬럼·결제/취소일 컬럼·금액 처리를 연결한 뒤 미리보기에서 결과와 포함 행 수를 확인한다. 서로 겹치지 않는 원화 결제 이벤트라는 조건을 확인하고 저장한다. 선택이 바뀌거나 미리보기가 실패하면 이전 미리보기로 저장할 수 없다.

- 통합 지표 v2는 **KRW 결제 이벤트 합계**를 지원한다. 전체 합계, 날짜별(일/주/월), 장부별 합계를 계산한다. 예약 건수·객단가·평균·정산액 합산·여러 통화 변환은 이 통합 정의의 범위가 아니다.
- `signed`는 원본 금액의 부호를 유지한다. 별도 취소 이벤트 장부의 `refund`는 `-abs(amount)`로 차감한다. 양수/음수 취소 파일 모두 같은 결과가 되지만, 본 장부에 이미 반영된 취소를 별도 장부로 다시 넣으면 안 된다.
- 예: 현금 100,000 + 카드 200,000 − 별도 취소 50,000 = 250,000원. 정산 입금액이나 기존 집계 통계를 결제 원금에 더하지 않는다. 이는 결제·취소 발생일 기준이며 회계상 매출 인식 규칙은 아니다.
- 같은 table ID·표시 이름·원본 파일 ID의 중복 선택을 거부한다. 동일 파일의 여러 시트도 현재는 함께 선택할 수 없다. 별도 파일에 반복 수록된 동일 거래는 자동 감지·제거하지 않는다. 거래 ID 기반 중복 규칙은 후속 작업이다.
- 각 원본을 공통 금액/일시/출처로 정규화한 후 `UNION ALL`로 합산한다. 원본끼리 JOIN해 거래가 곱해지는 문제가 없다. 품질 점검·행 수·합계는 단일 SQL의 동일 스냅샷에서 계산한다.
- 필터를 통과한 원본에 금액 누락·NaN/무한대가 있거나 필요한 날짜가 누락되면 전체 계산을 중단한다. 날짜가 없는 행을 기간 밖으로 임의 분류하지 않기 위해 품질 검사는 기간 필터 적용 전에 수행한다. 실패한 갱신은 마지막 정상 결과를 보존한다.
- 장부별 필터는 자연어 도구/API에서 지정할 수 있다. UI 폼은 컬럼·기간·금액 처리 매핑을 제공한다. 저장된 위젯의 **장부별 연결 기준**에 출처·필터·포함 행 수를 표시한다.
- 매번 가게 소유권과 모든 장부의 소속·스키마를 다시 검증한다. v1 정의와 기존 위젯은 그대로 실행된다. v2 도입에 추가 DB 컬럼 마이그레이션은 필요 없다.

## 채팅으로 만들기

현재 가게에 필요한 장부와 컬럼이 있으면 다음과 같이 요청할 수 있다.

- “결제 장부에서 이번 달 일별 카드 매출을 미리 보여줘.”
- “그 지표를 대시보드에 저장하고 매시간 갱신해줘.”
- “저장한 카드 매출 지표를 24시간마다 갱신하도록 바꿔줘.”
- “이 지표의 자동 갱신을 중지해줘.”
- “현금 장부와 카드 장부를 합치고 별도 취소 장부는 빼서 이번 달 일별 결제액을 미리 보여줘.”
- “그 통합 지표를 저장하고 매시간 갱신해줘.”

에이전트는 기존 search_schema/list_tables/describe_table로 출처를 확인하고 preview_metric/save_metric을 사용한다. 미리보기는 조회이며, 저장은 실제 도구 성공 후에만 완료로 보고하도록 안내한다. 동일 턴에서 같은 저장 도구를 반복 호출하면 같은 결과를 반환한다. 요청 재전송·다른 대화까지 포괄하는 저장 멱등성은 후속 과제다.

preview_metric의 차트를 고정하는 UI도 정의를 저장한다. 기존 일반 분석 차트는 정적 위젯으로 유지한다. 기간과 필터는 정의에 포함되고, 최근 지표 도구 입력은 대화 기록에 보존된다. 라우터도 최근 대화를 받아 후속 요청을 분류한다.

## 자동 갱신

- 수동(0), 매시간(3600), 24시간마다(86400)를 지원한다. 특정 시각 예약이나 임의 간격은 지원하지 않는다.
- 위젯에서 주기를 변경할 수 있고, 다음 계산 시각·실패·일시 중지 상태를 확인할 수 있다.
- API 서버가 15초 간격으로 DB의 예정 작업을 확인한다. 브라우저가 닫혀도 API 서버가 실행 중이면 계산한다.
- 정상 주기 계산은 LLM/RAG 호출 없이 저장된 정의를 재실행한다. 상대 기간은 실행일과 Asia/Seoul 시간대를 기준으로 다시 결정한다.
- DB 행 잠금과 SKIP LOCKED로 서버 간 중복 처리를 막는다. 작업 도중 프로세스가 종료되면 결과/일정 변경이 롤백되어 다시 실행 대상이 된다.
- 실패 후 60초, 120초에 재시도하고 3회 연속 실패하면 일시 중지한다. 마지막 정상 값을 보존한다. 수동 재계산 성공 또는 주기 재설정으로 재개한다.
- 서버가 꺼진 동안 놓친 실행 횟수만큼 반복하지 않고, 다시 시작하면 최신 데이터를 한 번 계산한다.
- 대시보드의 15초 polling은 서버에 저장된 결과를 읽으며 계산 스케줄러 역할을 하지 않는다.
- 즉시 데이터 변경 트리거는 아직 없으며 주기 실행 또는 수동 재계산으로 반영한다.

## 데이터 경계

- 각 project가 가게 하나다. 같은 계정의 다른 가게 장부로 지표를 생성할 수 없다.
- 재계산마다 가게 소유권과 원본 장부의 가게 소속·컬럼 타입을 검증한다.
- 가게 전환 시 대시보드 컴포넌트를 다시 생성해 이전 가게의 위젯과 작성 중인 지표를 제거한다.
- 가게 통합 조회는 이번 구현에 포함하지 않았다.

## 저장·실행

- API: `GET/POST /api/projects/{project_id}/metrics`, `POST /api/projects/{project_id}/metrics/preview`, `POST /api/projects/{project_id}/metrics/{metric_id}/refresh`, `PATCH /api/projects/{project_id}/metrics/{metric_id}/schedule`.
- 위젯 하나에 지표 정의 하나를 연결하며, 기존 `dashboard_widgets.widget_data`에 `metric_definition`을 저장한다. v1은 단일 장부, v2는 여러 장부의 매핑과 합계 규칙이다. 스케줄용 컬럼은 `003_metric_scheduling.sql`에 정의되어 있으며 API 시작 시 동일한 멱등 DDL을 적용한다. 기존 정적 위젯은 자동 갱신되지 않는다.
- `METRIC_SCHEDULER_ENABLED=true`가 기본값이다. 별도 프로세스에서 스케줄링하려면 API의 설정을 false로 끌 수 있다. 현재 전용 worker 배포는 제공하지 않는다.
- 기존 위젯 목록·삭제·레이아웃 API를 재사용한다. 정적 위젯에는 재계산 버튼을 표시하지 않는다.
- SQL은 허용된 집계 문법과 인용된 식별자로 구성한다. SQL 문자열이나 임의 코드는 입력으로 받지 않는다.
- 전체 행을 먼저 집계한다. 결과 그룹이 1,000개를 넘으면 잘린 합계를 보여주지 않고 오류를 반환한다.
- Decimal은 저장·API에서 문자열로 보존한다. 빈 합계를 자동으로 0으로 바꾸지 않는다. 행 건수는 COUNT(*)다.
- G부터 단일 장부 숫자 집계도 기간·필터 내 NULL이 있으면 부분 합계를 반환하지 않고 중단한다. NULL 건수는 `is_null`, 사용자가 명시한 제공분 집계는 `is_not_null` 필터로 구분한다. [선택 속성·누락 처리](PAYMENT_ATTRIBUTES.md)를 참고한다.
- 갱신 시 위젯 행 잠금으로 중복 요청을 직렬화한다. DB 오류는 savepoint로 격리해 마지막 정상 결과와 갱신 실패 사유를 함께 저장한다.
- 계산 시각은 실제 계산 완료 시각이다. 데이터가 외부 결제 시스템과 실시간 동기화됐다는 뜻은 아니다.

## 테스트

```powershell
# 저장소 루트에서: Docker 없이 SQL 실행 테스트를 준비한다.
npm ci --prefix scripts/sql-eval
cd api
python -m pytest tests/ -q
python -m app.eval.run --validate-only
```

`--validate-only`도 앱 설정 검증을 거치므로 DATABASE_URL, OPENAI_API_KEY, JWT_SECRET_KEY 등 환경 설정이 필요하다. 형식 검증 자체는 모델/DB를 호출하지 않는다. pytest의 단위 테스트 설정은 conftest에서 주입한다.

`test_multi_metrics_sql.py`는 실제 생성 SQL에 설치된 psycopg의 파라미터 변환을 적용하고 [PGlite](https://pglite.dev/docs/)의 PostgreSQL WASM 엔진에서 실행한다. 합계, 양수/음수 취소, 새 행 반영, 일/장부별 그룹, 상대 기간 경계, 정확한 소수, 빈 데이터, 누락/비정상 값, SQL 인젝션 문자열, `%`를 포함한 컬럼 이름, 그룹 제한을 검사한다. 17개 SQL 시나리오를 14개 테스트에서 검증한다. 이 의존성이 없으면 해당 테스트는 skip된다. PGlite는 앱 런타임 의존성이 아니다.

브라우저 검증은 실제 대시보드에 API 응답 fixture를 연결한다. 별도 터미널에서 웹 서버를 실행한 뒤 저장소 루트에서 아래 명령을 실행한다.

```powershell
# 터미널 1
cd web
npm run build
npm run start -- --hostname 127.0.0.1 --port 3100

# 터미널 2: 저장소 루트
npm ci --prefix scripts/ui-eval
npm run check --prefix scripts/ui-eval
```

기본 브라우저는 설치된 Microsoft Edge의 headless 모드다. `BROWSER_CHANNEL`과 `UI_BASE_URL`로 바꿀 수 있다. 이 테스트의 인증·장부·계산 응답은 모두 fixture이며 실제 계정이나 DB를 변경하지 않는다. 결과 화면은 `scripts/ui-eval/artifacts/`에 생성한다.

실제 PostgreSQL용 테스트는 별도 테스트 DB URL을 지정하면 실행한다. 테스트마다 고유 스키마를 만들고 해당 스키마만 제거한다.

```powershell
$env:DATAEZ_TEST_DATABASE_URL = 'postgresql://test:test@localhost:5432/test'
python -m pytest tests/test_dashboard_metrics_postgres.py -q
```

통합 지표 페이즈 당시 전체 테스트 382개가 통과했고(PGlite SQL 테스트 14개 포함), 외부 DB URL 미설정으로 PostgreSQL 테스트 5개는 skip했다. 웹 빌드·TypeScript 검사, 골든셋 60개/도구 18개의 형식 검증과 모의 API 브라우저 검증을 수행했다.

이후 [업로드 기반 A단계](IMPORT_FOUNDATION.md)에서 독립 PostgreSQL 16.15를 준비해 기존 5개와 새 적재 8개를 포함한 전체 435개 테스트를 skip 없이 통과했다. 실제 DB의 파일 적재·통합 집계·갱신을 확인했다. 실제 사업자 파일·실제 LLM·실제 DB를 연결한 브라우저 업무 실증은 남아 있다.

모델을 고정 응답으로 대체한 테스트에서 worker → 미리보기 → 저장 → 답변 흐름, 가게 격리, 정의/필터 유지, 일정 변경, 재시도/일시 중지와 종료 처리를 검증한다. 이는 실제 모델 성공률이나 실제 DB 잠금의 실측치가 아니다.

## 후속 구현 상태

A~I의 출처·이벤트 검토·RAG·선택 속성·검색 자동 복구를 구현했다. 2026-09-08의 [K·L 구현](METRICS_AND_CASH.md)은 v3 계산식 지표와 기존 지표 수정·복원, 현금 직접 입력을 추가한다. 본 문서의 과거 검증 수치와 최신 검증 기록을 구분한다.

남은 제품 작업 후보는 첫 사용·매핑 안내, 여러 가게 비교, 그룹별 계산식, 스키마 변경 재매핑이다. 실제 PG 파일 파일럿은 보류하며, 합성 데이터로 실제 DB·모델·브라우저 대표 흐름을 검증했다. 운영 성능·사업자 사용성까지 검증했다는 뜻은 아니다.
