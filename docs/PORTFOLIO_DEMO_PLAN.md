# DATA:EZ 포트폴리오 데모 제작 계획

작성: 2026-09-11 · 갱신: 2026-09-12 · 상태: Phase 1 대본 작성 완료, Phase 2 리허설 대기

## 목표와 완료의 의미

처음 보는 사람이 **30초 안에 서비스의 대상과 가치를 이해하고, 2분 안에 실제 작동을 확인하며, 이어지는 기술 설명에서 구현의 깊이를 판단할 수 있도록** 만든다. 이는 제작 목표이며 실제 사용자 검증 결과가 아니다.

서비스의 중심 메시지는 다음과 같다.

> 우리 가게 매출, 한눈에.  
> 매출 파일을 모으고, 자연어로 필요한 통계를 만들어 대시보드에 저장합니다.  
> 저장한 통계는 새 거래가 반영된 장부에서 다시 계산할 수 있습니다.

완성도는 새로운 기능의 개수가 아니라 **설명의 명확성, 실제 동작, 숫자의 정확성, 반복 시연 가능성, 시각적 일관성**으로 판단한다. 아래 완료 기준을 충족하면 핵심 제작을 마친다. 발견한 문제가 있을 때만 관련 부분을 수정·재검증하며, 취향만으로 전체 제작을 반복하지 않는다.

계획 MD와 문서 진입점을 작성한 뒤 Phase 0 준비와 Phase 1 대본 작성을 완료했다. [현재 완료 근거](portfolio-demo/ACCEPTANCE.md), [공개 환경 시연 준비](portfolio-demo/RUNBOOK.md), [촬영표](portfolio-demo/STORYBOARD.md)를 참고한다.

- 공개 웹: https://dataez.vercel.app / API: https://dataez-api.vercel.app.
- 웹·FastAPI는 Vercel, PostgreSQL·원본 Storage·검색 벡터·정기 작업은 Supabase를 사용한다. 계정 인증은 FastAPI의 자체 JWT 흐름이다.
- 앱 소스 `3944cf9`, 배포 기록 문서 `19c5b61`이 main과 원격에 반영되어 있다. 실행 시작 때 새 HEAD와 배포 상태를 다시 기록한다.
- Spoqa Han Sans Neo, Charcoal Blue, 다크 기본·라이트 지원, ECharts, 저채도 POS 사진과 로그인 카피가 확정되었다.
- 실제 공개 환경에서 업로드 → 자연어 분석 → 지표 저장 → 거래 추가 → 재계산 → 재접속을 검증했다. [공개 데모 검증](PUBLIC_DEMO_ACCEPTANCE.md), [최신 배포](LOGIN_RELEASE.md).
- 기존 [로컬 데모 안내](DEMO_RUNBOOK.md)와 [아키텍처](ARCHITECTURE.md)는 일부 이전 구성을 설명한다. 현재 배포 설명으로 그대로 복사하지 않는다.
- 실제 PG 연동, 실제 사업자 매출, 고객 확보·시간 절감 성과는 이번 포트폴리오의 검증된 실적으로 제시하지 않는다.

## Phase 0 — 사실과 데이터 고정

1. 배포 주소, 앱 소스 커밋, 현재 화면, API 준비 상태를 확인한다. 기존에 통과한 검사를 무조건 전부 재실행하지 않고 이후 수정 범위에 필요한 검사를 선정한다.
2. 공개 시연은 합성 데이터만 있는 전용 계정에서 진행한다. 비밀번호·토큰은 Git에서 제외된 로컬 설정으로 관리하며 공용 자격증명을 README나 영상에 공개하지 않는다.
3. 기존 샘플 ‘모퉁이 카페’를 주 시연 데이터로 사용한다. 고정 기간과 독립 기대값은 `samples/demo/expected.json`을 따른다.
4. 다중 가게 장면이 필요하면 같은 전용 계정에 보조 합성 가게를 만들고, 구분되는 이름·데이터·기대값을 별도로 둔다. 주 시연 데이터의 정답은 변경하지 않는다.
5. 새 샘플을 만드는 기존 기능으로 리허설·촬영 상태를 구분한다. 이전 자료는 보존하며, 정리가 필요하면 제작 전용 계정과 명시적으로 기록한 가게만 대상으로 한다.

| 주 시연 기준 | 기대 결과 |
|---|---:|
| 원본 기간 | 2026-09-01~2026-09-04 |
| 원본 행 수 / 합계 | 8행 / 690,200원 |

추가 거래 CSV는 `samples/demo/additional-transaction.csv`다. 현재 일반 장부의 추가 거래 시나리오는 API 준비 작업이 포함되어 있으므로, 화면에 없는 업로드 기능을 있는 것처럼 연출하지 않는다. 실제 UI로 가능한 결제 출처 가져오기와 구분하고, 기술 영상에서는 준비 방법을 설명한다. 같은 추가 거래를 반복 반영하지 않는다.

## Phase 1 — 제품 영상과 기술 영상의 대본

### 제품 영상: 한 가지 질문이 저장된 대시보드가 되는 과정

| 시간 목표 | 장면 | 전달할 내용 |
|---|---|---|
| 0~8초 | 완성 대시보드와 한 줄 카피 | 누구를 위한 어떤 서비스인지 먼저 보여준다 |
| 8~20초 | 보관함의 합성 매출 파일 | 흩어진 파일을 가게별로 모은다 |
| 20~38초 | 파일 선택·분석 범위·자연어 입력 | 분석할 자료와 질문을 사용자가 정한다 |
| 38~60초 | 실제 분석 결과·집계표·SQL | 그래프의 숫자와 계산 근거를 확인한다 |
| 60~85초 | 저장 설정·대시보드 추가·리사이즈 | 대화 결과가 다시 사용할 수 있는 지표가 된다 |
| 85~105초 | 재접속 또는 이미 저장한 다른 가게 화면 | 저장과 가게별 관리가 실제로 동작한다 |
| 105~120초 | 서비스 주소와 핵심 메시지 | 직접 체험하거나 기술 설명으로 이어간다 |

시연 질문 초안:

> 선택한 파일의 전체 기간에서 paid_at 날짜별 amount 합계를 원 단위 선그래프로 보여줘. 음수 취소 금액도 포함해줘.

질문은 리허설에서 확인한 실제 지원 표현으로 확정한다. 영상 길이에 맞추기 위해 상대 기간 ‘이번 달’로 바꾸지 않는다. 이미 준비된 예시 위젯은 ‘미리 준비한 예시’로, 실제 질문으로 만든 위젯은 ‘이번 분석 결과’로 구분한다.

### 기술 영상: 왜 단순한 차트 챗봇과 다른가

1. **사용자 문제와 범위:** 여러 결제수단·파일·가게를 관리하는 소상공인. 포트폴리오 데모와 실제 사업 성과를 구분.
2. **자연어에서 실행으로:** LLM이 구조화된 도구 인자·지표 정의를 만들고, 서버가 검증 후 SQL을 구성하는 경계. 임의 Python/SQL을 무제한 실행하는 서비스로 설명하지 않음.
3. **검색과 집계 분리:** RAG는 관련 파일·스키마·문서를 찾는 데 사용하고, 정확한 금액은 선택한 데이터 범위에 대한 DB 집계로 계산.
4. **원본과 누적 장부:** 690,200원 → 누적 장부에 거래 추가 → 720,200원. 같은 시점 원본은 690,200원으로 유지되는 이유 설명.
5. **저장된 지표와 재계산:** 스크린샷 저장이 아니라 정의와 출처를 저장하고 다시 계산. 수동 갱신을 보여주고 Cron은 실제 검증 이력으로 보완.
6. **운영 판단:** Vercel 함수 시간·요청 크기 제약에 대한 직접 업로드, 실행 시간 제한, DB 공유 요청 제한. Redis를 제거하고 현재 규모에 맞춘 이유.
7. **한계:** 실제 PG 수집, 실제 고객 사용성, 대규모 부하는 미검증 또는 범위 밖. 자동 갱신은 이미 수집된 데이터의 재계산이며 새 PG 거래 수집이 아님.

대본 산출물은 `STORYBOARD.md`와 `NARRATION.md`로 계획한다. 각 장면의 출처, 정확한 질문, 기대 숫자와 캡처할 화면을 함께 기록한다.

## Phase 2 — 촬영 리허설과 화면 보완

- 먼저 실제 공개 앱에서 시작부터 저장·재접속까지 실행한다. 준비 계정 외 데이터는 사용하지 않는다.
- 캡처 기본은 1920×1080, 30fps를 목표로 하며 작은 글자를 읽을 수 있도록 화면 확대와 커서 이동을 설계한다. 실제 캡처 도구가 지원하는 해상도·프레임률·포맷을 확인한 뒤 확정한다.
- 다크 모드를 주 영상으로 사용하고 라이트 모드는 별도 스크린샷으로 제공한다. 새 팔레트·폰트·로그인 디자인 탐색은 다시 시작하지 않는다.
- 파일명·가게명·지표 제목은 사람이 읽을 수 있게 정돈한다. 일반 서비스 데이터나 이미 저장한 사용자의 위젯을 바꾸지 않는다.
- 메뉴를 찾기 어려움, 문구 잘림, 오버플로, 잘못된 범위 표시 등 시연을 방해하는 문제가 확인되면 해당 부분만 수정한다. 필요 시 테스트·main 통합·배포·공개 재확인까지 완료한 후 촬영한다.
- 리허설 결과에 처리 시간과 재시도 여부를 기록한다. 실제 호출 한도를 확인하고 불필요한 LLM 반복 실행은 피한다.
- 두 번 연속 같은 의미의 집계·저장·재접속 결과를 얻는 것이 목표다. 자연어 답변의 문장까지 동일할 필요는 없다.

복구 방법도 준비한다. 검색 준비 중이면 상태를 확인하고 기다리며, 분석 오류가 나면 저장 이력과 장부 반영 여부부터 확인한다. 업로드·저장·거래 추가를 무조건 재전송하지 않는다. 공개 환경에 문제가 생기면 이전에 녹화한 실제 동작을 보여주거나 로컬 환경으로 전환하되 어느 환경인지 표시한다.

## Phase 3 — 실제 화면 녹화와 편집

- 기존 도구와 설치된 브라우저 캡처·영상 편집 도구를 확인하고, 가능한 조합으로 재현 가능한 녹화·출력 절차를 만든다.
- 핵심 상호작용은 실제 앱 화면을 사용한다. 생성 이미지나 HTML 시안을 작동 증거로 사용하지 않는다.
- 파일 선택, 범위, 질문, 결과, 저장은 인과관계가 이어지게 편집한다. 계정 정보·토큰·개발자 콘솔·개인 브라우저 기록은 촬영 범위에서 제외한다.
- 모델 대기를 줄여 편집하면 ‘대기 구간 단축’ 등으로 표시한다. 영상 길이를 실제 응답 속도로 주장하지 않는다. 연출된 클릭을 실제 성공 동작 대신 삽입하지 않는다.
- 실제 출력에서 소수점·음수·원화·날짜를 확인하고 확대 장면에서도 숫자가 달라지지 않게 한다.
- 1080p MP4는 호환성이 높은 H.264 출력, 반복 영상은 WebM을 우선 검토한다. GIF는 요청이 있을 때 짧은 파생본으로 만든다.
- 한국어 자막은 1~2줄, 충분한 표시 시간, 명확한 대비를 사용한다. 시연 중 읽어야 할 차트·금액·버튼을 가리지 않는다.
- 대표 캡처: 로그인, 보관함, 질문과 결과, SQL·집계 근거, 완성 대시보드, 원본/누적 차이. 필요하면 다중 가게·라이트 화면을 추가한다.

## Phase 4 — 사례 문서와 면접 설명

`CASE_STUDY.md`는 다음 순서로 작성한다.

1. 누구의 어떤 문제를 다루는가.
2. 한 장의 완성 화면과 실제 체험·영상 진입점.
3. 파일 → 자연어 → 구조화된 정의 → SQL 집계 → ECharts → 저장·재계산 흐름.
4. 직접 설계·검증한 기술적 선택 3~4개와 대안·제약.
5. 실제 테스트 결과와 관찰한 한계.
6. 다음 개선의 우선순위.

구조도는 브라우저, Vercel 웹/API, 모델 API, Supabase DB·Storage·벡터·Cron을 구분한다. 서버리스 기본 루프·토큰·시간 제한을 현재 설정과 대조한다. 이전 문서의 지속 실행 워커·로컬 저장·25회 루프 설명을 현재 배포 기본값으로 옮기지 않는다.

기술 선택 후보는 **구조화된 지표 정의와 서버 검증**, **원본/누적 범위와 소유권**, **직접 업로드와 서버리스 실행 제한**, **현재 규모에서 Redis 없이 운영하는 구성**이다. 코드와 검증 자료가 충분한 항목부터 채택한다.

‘개발 기여’는 실제 작업 내역을 근거로 정리하고, AI 도구 활용을 설명할 때 설계·검토·테스트·수정 판단과 구분한다. 사용자 수, 매출 개선, 비용 절감 비율을 추정해 성과처럼 쓰지 않는다. 개발·테스트 비용과 무료 할당량을 근거로 영구 무료를 약속하지 않는다.

README에는 작품 소개 → 실제 화면 → 서비스/데모 → 기술 근거 순서로 진입점을 정리한다. 전체 과거 Phase 문서를 첫 화면에 길게 나열하기보다 상세 문서 인덱스로 연결한다. 별도 포트폴리오 사이트나 슬라이드 덱은 핵심 산출물을 완료한 뒤 필요에 따라 확장한다.

## Phase 5 — 최종 완료 체크리스트

- [ ] 제품 영상만 봐도 대상·문제·핵심 흐름을 설명할 수 있게 구성되어 있다.
- [ ] 실제 화면에서 질문 → 계산 근거 → 저장 → 재접속이 이어진다.
- [ ] 기술 영상에서 원본 690,200원과 누적 720,200원의 차이를 재현하고 설명한다.
- [ ] 숫자·단위·기간·가게·파일 범위가 기대값과 모두 일치한다.
- [ ] 미리 준비한 결과와 실시간 LLM 실행, 실제 대기와 편집이 구분된다.
- [ ] 모든 영상은 처음부터 끝까지 재생해 검수했고, 핵심 장면은 일반 화면 크기에서 읽힌다.
- [ ] 자막·스크린샷·README·구조도의 용어와 제품 디자인이 일치한다.
- [ ] 공개 주소와 문서 링크가 작동하며 영상 경로에 실제 파일이 있다.
- [ ] 자격증명과 개인 데이터가 영상·문서·Git 산출물에 없다.
- [ ] 준비·시연·복구 절차가 문서화되어 같은 조건으로 다시 시연할 수 있다.
- [ ] 수정한 앱 코드가 있다면 관련 검사·main 반영·배포 확인을 완료했다.
- [ ] 진행을 막는 오류와 수치 불일치가 없으며, 남은 한계는 숨기지 않고 기록했다.
