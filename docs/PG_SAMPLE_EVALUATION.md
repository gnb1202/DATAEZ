# E — 합성 PG 파일과 실제 모델 평가

2026-09-08 실행. **CSV 12종·XLSX 1종과 실제 PostgreSQL 검증 43개를 마련했다.** 최초 실제 모델 평가에서 핵심 동작은 **15/20**이었다. 수정 후 전체 20문항을 추가로 4회 실행해, 답변 근거·충돌 처리 안내의 오류를 더 발견하고 고쳤다. **마지막 전체 실행은 자동 검사와 핵심 답변·근거 검토 모두 20/20**이다. 동일 합성 예제의 결과이며 일반 사용자 성공률을 뜻하지 않는다. 실제 RAG·채팅 화면 검증은 [F 기록](RAG_ACCEPTANCE.md)에 있다.

자료와 재실행 방법: [샘플 사용 안내](../samples/pg-evaluation/README.md). 독립 정답은 [expected.json](../samples/pg-evaluation/expected.json), 문항별 질문·답변·판정·사용량은 [평가 기록](evaluations/pg-2026-09-08.json)에 있다.

## 검증 환경과 정답

- 가상 강남점·홍대점, 현금 장부, 다른 소유자 가게, 정밀도 전용 가게를 임의 이름의 로컬 DB에 구성했다. 실행 종료 시 생성 DB를 모두 삭제했다. 사용자 앱에는 자동으로 샘플을 적재하지 않았다.
- PostgreSQL 16.15, 실제 업로드·미리보기·판정·커밋·SQL 집계 서비스를 사용했다. 모델 답변·SQL 결과를 모의 값으로 바꾸지 않았다.
- 프로젝트 설정 그대로 worker `gpt-5.4`, router `gpt-5.4-nano`를 사용했다. API 키는 기존 `.env`/환경변수에서 읽고 출력하지 않았다.
- Python 표준 CSV 파서와 Decimal로 독립 정답을 만들었다. 앱의 집계 결과를 정답 생성에 사용하지 않았다.
- 강남 PG: 승인 50건 1,420,000원 + 취소 4건 −62,000원 = **1,358,000원**. 현금 **146,000원**, 합계 **1,504,000원**. 9월 통합 순결제액 **1,386,000원**. 홍대 PG **835,000원**.
- 저장된 XLSX의 533개 셀을 CSV와 비교했다. 긴 거래번호·가맹점 ID는 앞자리 0을 포함한 문자, 금액은 숫자, 날짜는 날짜 셀이다. 앱의 정규화 결과도 CSV와 전체 행이 일치한다. [파일 QA 기록](../samples/pg-evaluation/verification.json).

파일 검증은 이름 변경 재시도, 이벤트가 겹치는 파일, 같은 원거래의 여러 부분 취소, 충돌 파일 전체 차단, 오류 행 3개 보고, ID 없는 후보의 명시적 포함/제외, 미결정 상태 커밋 차단, 가게·소유자 격리, 한국 시간 월 경계, `9,007,199,254,740,993.01` 보존을 포함한다.

코드 변경은 `prompts.py`의 계산·확인 규칙, `agent.py`의 동기/SSE 공통 업로드 이력 전달, `ledger_agent_tools.py`의 재시도 정책, `multi_metrics.py`의 출처 간 중복 설명이다. 실제 장부의 집계 엔진과 반영 규칙을 모델 오답에 맞춰 변경하지 않았다.

07 재검증에서는 첫 호출에 불필요한 최상위 `date_column`을 보내 검증 오류가 발생했으나, 두 번째 호출에서 올바른 정의로 회복했다. 이 동작도 원본 실행 기록에 남겼다. 14는 첫 재검증의 설명이 여전히 과도해 실패로 남기고 추가 수정 후 한 번 더 실행했다.

저장된 값·정의·주기, 원장/업로드/후보 판정 상태의 실행 전후 차이를 확인했다. 각 독립 문항 전에 지표를 초기화하고 03·04만 02의 실제 저장 지표와 대화를 이어 썼다. 원장은 모든 문항에서 불변임을 검사했다. 조회·모호한 요청의 미승인 저장, 원본 거래 변경, 다른 가게 거래 노출은 **0건**이었다.

자동 검사는 충분조건이 아니다. 14의 잘못된 근거 설명은 값·도구 검사만으로 통과할 수 있어 전체 답변과 도구 기록을 Codex가 읽어 별도로 판정했다. 독립 사업자나 사람 평가자가 참여한 결과는 아니다. 최초 채점 스크립트의 도구 결과 위치 가정, 불필요한 이력 도구 강제, UUID 숫자의 건수 오인도 수정했다. 원래 실행 기록을 덮어쓰지 않고 `summarize.py`에서 기록된 증거만 다시 채점했으며, 채점 보정을 위한 모델 재호출은 하지 않았다.

총 **106턴·433회 LLM 호출**, **1,813,253토큰**(입력 1,746,457 / 출력 66,796). 턴 지연 중앙값 **7.94초**, 관측 범위 **4.50~16.41초**다. 프로젝트 요율표 기준 비용 추정은 **$2.642918**이며 현재 요금 검증·실제 청구액·캐시 할인 반영 수치가 아니다. F의 검색·브라우저 호출은 이 합계와 별도다. 작은 고정 샘플의 결과이므로 통계적인 지연 보장이나 성공률로 해석하지 않는다.

반복 실행 중에는 지표의 잘못된 group_by나 누락된 count 인자가 거절된 뒤 회복하는 경우도 있었다. 최종 실행 09에서는 정확한 합계와 환불 표본을 얻은 뒤 부가 count 호출이 실패했으나, 실패한 건수를 답변에 만들어 쓰지는 않았다. 주요 요청의 결과와 모든 도구 호출의 무오류는 서로 다른 기준이며, 원본 기록에 두 경우를 모두 남겼다.

평가 설계는 정상·경계·오류 사례를 함께 두고, 도구 선택·인자·실행 결과와 답변 의미를 분리해 판단하는 [OpenAI 평가 가이드](https://developers.openai.com/api/docs/guides/evaluation-best-practices)를 참고했다.

## 아직 평가하지 않은 부분

1. **실제 PG 파일과 사업자 검증**: 합성 파일이며 특정 PG의 공식 포맷, 실제 가맹점 운영 적합성은 아직 검증하지 않았다.
2. **E 러너의 RAG 범위**: E에서는 RAG를 명시적으로 끄고 스키마 목록·SQL 도구를 평가했다. 실제 pgvector·임베딩 검색은 [F에서 별도 검증](RAG_ACCEPTANCE.md)했다.
3. **추가 속성 분석**: 관리 원장은 6개 필드로 정규화하므로 PG 원본의 결제수단·채널·수수료 분석은 별도 확장이 필요하다.
4. **UI와 운영**: E는 서비스 함수와 실제 모델을 직접 실행했다. 실제 채팅 검색·저장·후속 주기 변경은 F, 브라우저 종료 후 백그라운드 갱신·재시작 복구는 [D](INTEGRATED_ACCEPTANCE.md)의 별도 검증 결과다.
5. **답변 품질과 운영 안정성**: 반복 실행은 수행했지만 장기간·다양한 실제 사용자 평가는 남아 있다. 답변이 길고 내부 컬럼명·불필요한 제안이 많으며 미지원 후속 계산을 제안하기도 한다. included를 이미 포함으로 옮겨 미리보기의 선택 상태와 반영 완료를 혼동할 수 있는 문구도 개선 대상이다. 재시도 자체의 감사 이력은 현재 저장하지 않는다.

현재 E의 합성 데이터·실제 모델 반복 점검과 F의 실제 RAG·채팅 검증은 완료했다. 실제 사업자 자료·대규모 검색·장기 운영 검증은 남아 있다.
