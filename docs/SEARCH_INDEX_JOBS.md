# I단계: 검색 갱신 자동 복구

장부 반영과 문서 저장 후 검색 갱신을 DB에 기록한다. 외부 임베딩 연결이 실패해도 저장된 자료는 유지하며, 서버가 자동으로 다시 처리한다. **장부 관리 → 검색 갱신 상태**에서 현재 가게의 진행 상황을 확인한다.

## 사용 흐름

1. 출처 파일 반영·과거 속성 복원·일반 장부 가져오기 또는 행 편집을 완료한다.
2. 해당 장부가 `갱신 대기 → 갱신 중 → 검색 준비 완료`로 바뀐다. 참고 문서는 같은 화면에서 PDF·MD·TXT로 올린다.
3. 일시적인 장애는 `자동 재시도 대기`에 시도 횟수와 다음 시각을 표시한다. 기존 검색 내용이 있으면 유지한다.
4. 자동 시도가 끝나거나 원본을 읽을 수 없으면 `확인 필요`와 원인을 표시한다. 원인을 해결한 뒤 `다시 시도`를 누른다. 준비가 끝난 자료에도 `검색 다시 갱신`을 사용할 수 있다.

빈 문서·원본 누락·해시 불일치·해독 실패·크기 초과는 즉시 확인 대상으로 전환한다. 스캔 PDF의 OCR은 이번 범위에 포함하지 않는다. 실패한 문서도 목록에서 확인하고 삭제할 수 있다.

화면은 열려 있을 때 5초마다 갱신한다. 서버의 검색 작업은 브라우저가 닫혀 있어도 실행한다. 가게를 바꾸면 해당 가게의 작업만 표시한다. 조회 실패 시에는 마지막으로 확인한 상태라는 안내를 함께 표시한다.

## 저장과 복구 계약

- `search_index_jobs`는 장부 또는 문서당 하나의 작업을 유지한다. 새 장부 변경은 세대 번호를 증가시키고 최신 자료를 처리하도록 요청한다.
- `table_meta`, `ledger_sources`, 반영 완료한 `import_batches`, `projects`의 지연 트리거가 원본 변경과 **동일한 트랜잭션**에서 요청을 저장한다. 트랜잭션이 롤백되면 갱신 요청도 롤백된다. HTTP 응답 직후 서버가 중단되어도 커밋된 요청은 남는다.
- 일반 장부의 행 추가·수정·삭제도 메타데이터 잠금을 먼저 얻고 원본 수정·행 수·갱신 요청을 함께 반영한다. 출처로 관리하는 장부의 직접 편집 제한은 그대로 적용한다.
- 문서는 서버가 생성한 저장 키로 원본을 저장한 뒤, 파일 등록과 작업을 같은 DB 트랜잭션에 기록한다. SHA-256과 크기를 보존하여 재시도 때 원본을 검사한다. 임베딩 API 호출은 업로드 HTTP 요청에서 분리했다.
- 작업자는 `FOR UPDATE SKIP LOCKED`로 하나의 작업을 짧게 점유하고 DB 트랜잭션을 끝낸다. 외부 API 호출 동안 DB 행 잠금을 유지하지 않는다.
- 점유 시간은 10분이다. 작업자가 중단되면 만료 후 다음 작업자가 새 토큰으로 이어받는다. 갱신 주기는 5초이며, API 프로세스당 한 번에 한 작업, 한 회차에 최대 10개를 처리한다.
- 일시적인 실패는 세대당 최대 **5회** 시도한다. 실패 후 대기는 **15초 → 60초 → 5분 → 15분**이다. 실행 중 반복 중단된 경우도 시도 상한에 포함한다. 실제 시작 시각은 대기열과 작업자 가용성에 따라 늦어질 수 있다.
- 저장 직전에 최신 원본과 작업의 세대·점유 토큰·만료 시각을 확인한다. 오래된 작업은 최신 색인이나 작업 상태를 덮어쓰지 못한다. **검색 색인 교체와 작업 성공 상태는 같은 트랜잭션에서 커밋**한다.
- 장부 카탈로그가 동일하면 임베딩 호출을 생략하고 작업을 완료한다. 이전 색인의 사용자·가게 범위도 비교한다. 문서 재색인은 전체 청크를 준비한 뒤 한 번에 교체하여 부분 색인을 노출하지 않는다.
- 삭제된 자료의 작업은 취소되거나 FK로 제거된다. 작업 중 삭제되어도 검색 자료를 다시 만들지 않는다. 조회·재시도·문서 삭제는 사용자와 가게 범위를 검사한다.

화면용 오류에는 공급자 응답·SQL·인증 정보를 저장하지 않는다. 검색 도구는 색인 누락뿐 아니라 대기·실패 상태도 `index_incomplete`로 반환한다. 따라서 챗봇이 검색 갱신 중인 자료를 “자료 없음”으로 단정하지 않도록 안내한다. 검색 중에는 이전에 성공한 색인을 사용할 수 있으므로 실제 통계는 원본 장부를 조회해 계산한다.

## API 및 설정

| 경로 | 동작 |
| --- | --- |
| `GET /api/projects/{project_id}/search-index?limit=50&offset=0` | 상태·횟수·다음 시도·최근 완료·실패 원인, 가게 전체 상태별 개수 |
| `POST /api/projects/{project_id}/search-index/{job_id}/retry` | 실패 또는 완료한 자료를 다시 요청. 대기·처리 중인 요청의 반복 호출은 점유와 대기 시간을 초기화하지 않음 |
| `POST /api/projects/{project_id}/documents` | 원본·작업 저장 후 `index_status=pending`, `index_job_id`, `chunks=0` 반환 |
| `GET /api/projects/{project_id}/documents` | 아직 청크가 없는 대기·실패 문서도 조회 |
| `DELETE /api/projects/{project_id}/documents/{file_id}` | 문서 등록·검색 청크·작업 제거 |

문서 업로드의 `chunks=0`은 비동기 처리 전 응답이다. 실제 청크 수는 문서 목록의 `chunk_count`로 확인한다. H 복원 적용 응답의 `index_status`는 이제 `queued`이며 최종 상태는 검색 갱신 조회 API로 확인한다. 완료한 복원 요청을 반복해도 실패한 검색 작업의 횟수를 자동 초기화하지 않는다.

`INDEX_WORKER_ENABLED=true`가 기본이다. `false`이면 요청을 보존하며 작업자를 실행하지 않는다. `RAG_ENABLED=false`이면 의미 검색과 작업자를 모두 끄지만 장부·문서 저장과 작업 기록은 가능하다. 값을 바꾼 뒤 서버를 재시작한다.

`007_search_index_jobs.sql`은 006 이후에 적용한다. 앱 시작에서도 동일한 DDL을 적용한다. 첫 설치 시 기존의 활성 장부를 찾아 갱신 요청을 만든다. 이후 재시작은 기존 시도 횟수와 점유를 유지한다. 이미 색인된 문서는 기존 청크의 소유자·가게가 일치할 때만 등록을 인계한다. 과거에 첫 색인에 실패하여 가게 정보가 남지 않은 업로드는 임의로 가게에 연결하지 않는다.

임베딩 요청은 백그라운드 작업에서 호출당 30초, SDK 내부 재시도 0회로 설정하고 작업 큐에서 재시도한다. 문서는 업로드 크기 제한(기본 20MB) 외에 최대 192개 청크로 제한한다. 대량 문서나 이 상한에서의 성능을 보장하는 부하 실험은 수행하지 않았다.

## 검증

자동화 테스트는 실제 PostgreSQL/pgvector와 고정 벡터로 트랜잭션·동시성·장애를 검증한다. 별도의 수용 검사에서는 실제 HTTP 서버·Edge 브라우저·실제 임베딩 API를 사용한다.

```powershell
$env:PYTHONIOENCODING='utf-8'
$env:DATAEZ_TEST_DATABASE_URL='postgresql://dataez_test@127.0.0.1:55439/postgres'
$env:DATAEZ_RAG_TEST_DATABASE_URL='postgresql://dataez_test@127.0.0.1:55440/postgres'
cd api
python -m pytest -q
cd ..
python scripts/index-eval/run.py
```

수용 검사는 임의 이름의 새 DB에서 다음을 실행한다.

1. 작업자를 끈 상태에서 장부·기존 지표를 만들고, 브라우저에서 참고 문서·빈 문서를 올린다.
2. 임베딩 접속 주소를 닫힌 로컬 포트로 바꾸어 연결 장애를 주입한다. 브라우저에서 자동 재시도와 빈 문서의 실패 이유를 확인한다.
3. 브라우저를 종료하고 서버를 실제 임베딩 연결로 재시작한다. DB에 저장된 재시도가 이어져 장부와 문서의 색인을 완료한다.
4. 실제 임베딩 검색으로 장부·문서의 정확한 ID를 찾는다. 다른 가게의 조회·재시도는 격리된다.
5. 브라우저에서 수동 갱신과 실패 문서 삭제를 실행한다. 장부 금액과 기존 지표의 ID·정의·배치·주기·값을 대조한다.

실행 중 점유를 잃은 작업의 차단은 DB 테스트에서 만료 시각을 앞당겨 검증한다. 실제 브라우저 검사는 재시도 대기 중 서버 재시작을 검증하며, 실제 10분 대기나 실행 중인 외부 API 호출의 강제 종료 실험을 대신하지 않는다. 대화 모델의 답변 품질 평가는 이번 단계에서 반복하지 않았다.

2026-09-08 최종 검증은 전체 API **589개 통과, skip 0개**(I의 PostgreSQL 검사 22개), TypeScript 검사, 웹 빌드, 실제 수용 검사 **17개 항목 통과**다. 마지막 실행은 `dataez_index_eval_f3e43ea190164c71b7631772753197c7`이며, 이전 성공 실행을 포함해 같은 장애·복구 시나리오를 두 번 통과했다. 별도로 H의 실제 HTTP 복원 검사도 새 비동기 계약으로 재실행해 통과했다.

첫 브라우저 실행은 자동 선택된 다른 가게에서 검사하려다 실패했다. 검증 스크립트가 가게 선택 UI로 검증점을 명시적으로 선택하도록 수정했다. 앱의 가게 격리 오류는 아니었다. H 재실행에서 발견한 임의 비밀번호 생성의 간헐적 정책 위반도 검증 스크립트에서 수정했다. 최종 검사에 실제 사업자나 운영 파일은 참여하지 않았다.

## 남은 범위

- 실제 PG 공식 파일을 사용한 사업자 파일럿과 업로드 매핑의 사용성 개선.
- 문서 재업로드 버전 관리, 원문 미리보기·근거 연결, OCR, 대량 처리와 큐 처리량 관측.
- 스토리지와 DB는 분산 트랜잭션이 아니다. 원본 저장 후 DB 등록이 실패하거나 문서 등록을 삭제하면 저장 객체가 남을 수 있다. 스토리지 보관 정책과 고아 객체 정리는 별도 범위다.
- 운영자가 DB를 직접 수정하거나 색인을 직접 삭제하는 경우까지 자동 감지하지 않는다. 임베딩 모델 변경 후 전체 재색인은 별도 운영 작업이다. 화면의 수동 갱신과 기존 사용자·가게 범위 CLI를 사용할 수 있다.
- 오래된 카탈로그의 파일명 최대 20개와 큰 원장의 기간 조회 비용 제한은 F에서와 동일하다.
