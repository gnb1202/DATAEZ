# DATAEZ 의사결정 모델 비교 평가 설계

작성일과 레퍼런스 확인일: 2026-10-03 KST. 상태: 설계 초안과 첫 개발 라우팅 실험. [실행 방법](../scripts/decision-eval/README.md)과 [첫 실측 결과](DECISION_MODEL_PILOT.md)를 함께 읽는다.
검토한 저장소 HEAD: bef489f74e64ebb8f29f03f5fd9d56055e495311.

현재 DATAEZ 라우터, Laya, Jev를 비교해 한국어 업무 정확성을 유지하면서 전체 응답 시간과 성공 업무당 비용을 개선할 수 있는지 확인한다. 우선 질문의 의도와 도구 목록을 정하는 단계만 비교한다. 작업 모델, 검색, SQL 계산, 권한 검사, 파일 범위 계약은 고정한다.

이 문서의 표본 수와 도입 기준은 DATAEZ에 대한 제안이다. 인용한 연구가 이 숫자를 권장하거나 DATAEZ에서 성능을 보장한다는 의미는 아니다. 최초 설계 후 별도 로컬 환경에 Laya를 설치하고 개발 라우팅 호출을 시작했다. 운영 데이터와 운영 배포는 실험에 사용하지 않았다. 전체 업무 평가와 최종 holdout은 아직 실행하지 않았다.

## 현재 기준점과 평가기의 확인 사항

코드 기본 설정은 router gpt-5.4-nano, worker gpt-5.4다. 실행 때 실제 설정과 공급자가 반환하는 모델 식별자를 기록한다. 환경변수에서 적용한 값이 기본값과 다를 수 있다.

## 확인할 질문과 비교군

주요 질문은 세 가지다. 판단 단계가 필요한 도구를 빠뜨리지 않는가, 전체 업무가 같은 정확도로 완료되는가, 완료한 업무당 비용 또는 실제 완료 시간이 개선되는가.

| 비교군 | 판단 단계 | 목적 |
|---|---|---|
| A0 | 현재 nano 라우터와 현재 처리 정책 | 제품 도입 판단의 주 기준점 |
| B0 | 지정 revision의 Laya multilingual과 DATAEZ 어댑터 | 현재 시스템을 Laya로 바꿨을 때의 효과 |
| C0 | 고정 버전의 Jev와 DATAEZ 어댑터 | 현재 시스템을 Jev로 바꿨을 때의 효과 |
| A1 | nano에 B0/C0와 같은 작은 판단 질문과 코드 조합 정책 적용 | 구조 변경 자체가 개선 원인인지 확인하는 보조 비교 |

B0/C0 대 A0는 모델과 어댑터를 포함한 시스템 변경 비교다. 모델만의 우열이라고 표현하지 않는다. B0/C0 대 A1은 공통 판단 구조 안에서의 백엔드 비교다. 같은 사실과 판단 정의를 전달하되 API 형식 때문에 바이트 수준의 동일 프롬프트를 강제하지 않는다. 각 모델에 대한 최적화 시간과 개발 데이터 접근 범위를 기록한다.

초기에는 DATAEZ 학습 없이 제공된 체크포인트를 평가한다. fine tuning을 한다면 B1 등 별도 비교군으로 만들고, training split, 학습 비용, label 출처를 추가 기록한다. 영어 tuned checkpoint의 공개 점수를 한국어 B0의 기준값으로 사용하지 않는다.

추가 통제가 필요한 경우 모든 허용 도구를 worker에 주는 no router 비교 또는 정답 도구 묶음을 주는 oracle routing을 소규모 개발 실험으로 수행할 수 있다. 이 경우 intent와 worker 프롬프트를 만드는 정책까지 명시한다. 기본 A/B/C 결과와 합치지 않는다.

## 판단 입력과 출력 계약

한 사례는 current_request, recent_messages, has_attachments, available_tools를 포함한다. A0 라우터가 실제 받는 정보와 절단 정책을 정확히 보존한다. selected_file_refs, current_store, 범위 상태는 전체 업무 실행기의 상태와 채점 자료에 저장한다. 현재 라우터가 받지 않는 정보를 B0/C0에만 추가하지 않는다. 이 정보를 새로 활용하려면 A1에도 똑같이 제공하는 별도 구조 실험으로 구분한다.

현재 라우터의 비교 출력은 intent, tools, degraded다. ambiguity에 대한 기대 동작은 질문셋에 저장하되, 현재 라우터가 없는 clarification 필드를 출력했다고 가정하지 않는다. 사용자의 추가 정보 요청은 전체 worker 답변 단계에서 평가한다.

Jev/Laya의 Choice는 하나의 선택이고 현재 tools는 복수 선택이다. intent는 네 선택지 Choice로 표현할 수 있으나 tools를 단일 Choice로 대체하지 않는다. 초기 B0/C0는 각 도구가 필요한지 묻는 독립 이진 질문들을 한 요청에서 평가하고, 선택된 도구를 기존의 공통 보완 코드에 전달한다. 지표 저장과 행 추가를 구분하는 정의는 현재 도구 설명과 동일한 의미를 가진다. 지표 workflow 묶음이나 계층 분류 방식은 개발셋에서만 비교한 뒤 최종 방식 하나를 고정한다.

첫 비교에서는 모든 이진 확률에 0.5를 적용한 결과도 보조로 남긴다. 실제 정책 임계값은 별도 selection set에서 정한다. 도구마다 개별 임계값을 무제한 튜닝하지 않고, 읽기 및 변경 도구 등 미리 정한 소수 그룹을 사용해 과적합을 줄인다. 독립 질문으로 출력됐다는 이유로 여러 도구 확률을 곱해 전체 도구 집합의 정답 확률로 해석하지 않는다.

기본 처리 불가, 타임아웃, 잘린 입력을 제외한 성공 사례만 비교하지 않는다. 주 평가 분모는 계획한 전체 사례다. 입력이 너무 길면 unsupported와 원인을 기록하고, 사전 정의된 폴백 실험에서 전체 비용과 시간을 포함한다. 세 모델 모두 지원하는 입력의 교집합 성능은 보조 표로만 제시한다.

## 질문셋과 정답 작성

과거 54문항 라우팅 보고서, 현재 검증되는 65문항 라우팅 자료, 24문항 업무 자료는 회귀와 개발 자료다. 새로운 최종 테스트에 옮겨 100% 정확도 근거로 삼지 않는다. 새 질문은 합성 매출 fixture와 서비스 계약에 맞춰 작성한다. 공개 기본 벤치마크의 한국어 번역을 새 독립 업무 정답으로 취급하지 않는다.

정답 작성자는 nano/Laya/Jev의 출력을 보기 전에 필요한 업무 동작을 정한다. LLM이 초안을 만들 수 있으나 사람이 서비스 계약과 독립 계산으로 검토해야 한다. 검토자가 없는 경우 그 상태를 표시하고 질문셋을 최종 승인된 ground truth라고 부르지 않는다.

각 사례에는 family_id, split, question, history, attachment 상태, 선택 파일과 범위, fixture_id, expected_intents, required_tools, optional_tools, forbidden_tools, 허용 가능한 도구 대안, expected_behavior, independent_expected_values, expected_db_state, critical_contracts를 둔다. 분석 값은 기존 Decimal oracle을 재사용하거나 독립 계산기를 확장한다. 정답 생성에 피평가 앱의 SQL 생성 코드를 재사용하지 않는다.

복수로 타당한 intent나 도구 경로가 있다면 허용 대안을 명시한다. 지원하지 않는 계산을 요청하는 사례는 올바른 불가 설명이나 추가 자료 요청이 정답일 수 있다. optional 도구 선택을 오답으로 세지 않는다. 동등한 SQL의 날짜 표현과 그룹 순서는 계산 의미로 비교하고, 금액 반올림 규칙은 사례 작성 시 고정한다.

초기 신규 데이터 규모는 아래처럼 제안한다. 이는 작성과 실행 규모의 초안이며 작은 차이를 입증할 수 있는 표본 수 보장은 아니다.

| 분할 | 신규 업무 가족 수 | 허용되는 사용 |
|---|---:|---|
| Development | 60 | 어댑터와 프롬프트 작성, 도구 묶음 방식 선택, 실행 비용 pilot |
| Calibration | 40 | 확률 보정 파라미터만 맞춤. 학습 없음이면 생략 가능 |
| Selection | 40 | 이진 선택과 폴백 임계값 선택 |
| Confirmation | 40 | 고정한 임계값의 독립 확인. 실패하면 후보를 탈락시키거나 새 프로토콜 버전으로 개발 재시작 |
| Test | 200 | 잠근 최종 평가. 성능 보고 전까지 튜닝 금지 |

같은 거래 구조, 업무 시나리오, 원문을 바꾼 표현은 같은 family_id로 묶고 다른 분할에 나누지 않는다. 작은 calibration/selection 집합의 확률 결과는 탐색적이다. 개발 pilot의 불일치율과 희귀 실패 수를 보고, 최종 테스트를 열기 전에 검정력과 필요한 추가 표본 수를 산정한다.

제안한 Test 200가족의 기본 구성을 다음과 같이 둔다. 표의 분류는 가장 대표적인 업무 기준이고, 위험 및 맥락 tag는 여러 개 붙일 수 있다.

| 주 분류 | 가족 수 | 대표 내용 |
|---|---:|---|
| 단순 조회와 집계 | 30 | 목록, 기간 합계, 취소 반영, 빈 기간 |
| 장부 구조 조회와 변경 | 20 | 컬럼 질문, 장부 찾기, 이름 변경과 행 변경 구분 |
| 지표와 대시보드 | 25 | 미리보기, 저장, 기간 변경, 이력 복원, 주기 변경 |
| 현금 입력과 가져오기 검토 | 25 | 현금 초안과 실제 반영 구분, 중복 후보 조회, 첨부 shortcut |

| 지원 범위와 입력 교란 | 20 | 불가능한 환율 요청, 지시처럼 보이는 파일명, 인젝션, 오타와 부정 표현 |

이 분포는 현재 제품의 실제 트래픽 분포라는 증거가 없다. 균형 평균과 업무별 결과를 보고하고, 추후 합법적으로 수집한 대표 사용 패턴이 있으면 별도 traffic weighted 표를 작성한다. 같은 패턴을 반복 생성해 독립 200가족인 것처럼 세지 않는다.

## 평가 단계와 실행 규모

### 단계 1 라우팅 판단 평가

먼저 Development에서 실제 기준점과 어댑터를 확인하고 분할을 잠근다. Test에서는 A0/B0/C0에 동일한 가족을 배정한다. 전체 제품 경로에서는 현재 shortcut을 동일하게 유지한다. 별도 모델 판단 표는 shortcut을 우회하고 판단 백엔드로 전달한 결과라고 명시한다. 두 표를 섞지 않는다.

처음에는 가족당 대표 요청 한 번으로 200 × 3 = 600 라우팅 요청을 계획한다. 동일 입력 재호출, 표현 변화, 선택지 순서 변경 검사는 별도 개발 자료나 사전에 잠근 부가 사례로 수행한다. 표현이 다른 요청을 같은 입력의 반복으로 계산하지 않는다. A1의 200요청은 구조 효과 비교를 수행할 때 별도로 추가한다. 이는 요청 단위 수이며 어댑터 내부 질문 수, 재시도, 실제 provider 호출 수를 함께 보고한다.

### 단계 2 전체 업무 평가

새 개발 자료에서 12시나리오 × 3비교군 × 1회 = 36episode로 실행 비용과 평가기 계약을 먼저 확인한다. 최종 테스트를 열기 전에 정한 60가족을 Test에서 업무 층별로 선정하고, 3군을 각각 3회 실행한다. 60 × 3 × 3 = 540episode이며 한 episode는 여러 사용자 turn과 worker 호출을 포함할 수 있다. 나머지 140가족은 라우팅 결과만 있으므로 전체 업무 결과라고 표현하지 않는다.

각 episode의 DB, 파일 선택, 대화 상태를 새로 복원한다. 고정 날짜와 KST 날짜 경계, fixture revision, 검색 색인을 동일하게 유지한다. 후속 사용자 메시지는 사전 정의한 스크립트 또는 분기 규칙을 쓰며, 모델마다 다른 정보를 주지 않는다. 이전 답변을 참조하는 대화의 자연스러운 차이는 전체 업무 효과에 포함된다. 라우터만의 문맥 비교는 별도 동일 이력 replay로 한다.

각 반복에서 A/B/C 실행 순서를 seed 기반으로 섞고 시간 블록별로 교차 실행한다. worker 설정과 가능한 seed를 고정해도 공급자 결정성을 보장한다고 표현하지 않는다. 쓰기 요청은 전용 평가 DB에서만 실행하며, 실제 운영 데이터는 사용하지 않는다.

### 단계 3 확률과 폴백 정책 평가

원시 판단의 품질을 보고한 뒤, 낮은 확신 또는 transport 오류 시 현재 nano로 돌아가는 후보 정책을 별도로 평가한다. calibration, selection, confirmation 데이터만으로 보정과 경계를 정하고 Test에서는 바꾸지 않는다. 후보 정책에 필요한 공통 nano 폴백의 재시도까지 비용과 시간에 포함한다.

A0에는 현재 오류 폴백이 있지만 수치 confidence 기반의 폴백은 없다. A0 확률 지표는 N/A다. 숫자로 자신감을 말하게 하는 새 프롬프트를 넣어 A0의 확률인 것처럼 사용하지 않는다. A1에서 수집한다면 해당 측정 방식과 비용을 별도 기록한다.

임계값 정책의 coverage는 라우팅 요청 중 후보가 nano 폴백 없이 결정을 낸 비율이다. 전체 업무를 무인으로 완료한 비율과 다르다. 추가 확인을 올바르게 요청하는 성공 사례도 이 정의를 따라 분리한다.

전체 업무 폴백 정책을 주장하려면 같은 60가족에 대한 실제 episode를 추가 실행해야 한다. 라우팅 replay 결과만으로 최종 업무 성공을 추정하지 않는다. 이 추가 비용은 초기 540episode에 포함되지 않는다.

## 채점 지표와 실패 분류

| 층 | 주요 지표 | 정의와 해석 |
|---|---|---|
| 원시 판단 | intent accuracy, 클래스별 recall | 모호한 사례의 허용 intent 집합을 인정하고 confusion matrix 공개 |
| 원시 도구 선택 | required tool recall, 사례별 평균 tool F1, tool set pass | 필수 도구를 빠뜨린 사례 비율도 함께 계산. optional 및 허용 대안을 반영 |
| 변경 위험 | forbidden tool selected | 모델 최초 선택과 최종 worker 제공 목록 각각 집계. 실제 실행 위반과 분리 |
| 시스템 처리 | effective tool coverage, unsupported/invalid/retry/degraded rate | 보완 코드가 누락을 회복했는지 기록. 실패도 전체 분모에 포함 |
| 전체 업무 | contract success | 독립 집계값, 날짜, 출처, 목표 상태, 금지 변경 없음, 필요한 설명 모두 충족 |
| 반복 신뢰성 | pass^3 | 같은 시나리오의 독립 초기화된 세 episode가 모두 성공한 가족 비율. 한 번이라도 성공하는 pass@3와 다름 |
| 확률 | Brier score, reliability diagram, ECE | Choice는 전체 분포, 이진 도구 질문은 Bernoulli 확률. 결합 도구 집합의 확률로 해석하지 않음 |
| 폴백 정책 | coverage, accepted set routing error, high confidence forbidden selections | 낮은 오류가 대부분 폴백한 결과인지 함께 확인. confidence 경계와 raw probability 경계를 구분 |
| 시간 | routing wall time 및 업무 완료 wall time p50/p95 | 첫 요청 실패와 재시도 포함. 첫 SSE 이벤트 시간은 보조 지표 |
| 비용 | 전체 비용과 성공 업무당 비용 | 실패·재시도·폴백·worker·embedding까지 포함. 성공 0건이면 비율은 정의되지 않음 |

전체 업무 성공률의 분모에는 timeout, 취소, 모델 처리 불가도 포함한다. 실행기 자체가 fixture를 만들지 못하는 등 평가 인프라 실패는 별도 분류하고 같은 조건으로 세 군을 재실행한다. 특정 모델의 실패를 인프라 문제로 바꿔 제외하지 않는다.

필수 불변 계약은 다른 사용자 자료 접근 없음, 선택 파일 범위 준수, 잘못된 금액 또는 기간 결과를 정답으로 제시하지 않음, 요청하지 않은 원본 변경 없음, 지원하지 않는 작업을 완료했다고 주장하지 않음이다. 조회 대상이 없으면 올바른 추가 정보 요청도 성공일 수 있다. 루프 종료나 응답 완료 상태만으로 성공이라고 판정하지 않는다.

글의 유용성, 근거 설명, 추가 질문의 적절성은 모델명을 가린 검토 rubric으로 평가한다. 금액과 DB 상태는 LLM judge로 정답을 만들지 않는다. 독립 사람 검토를 못 했다면 Codex 검토 등의 실제 평가자를 명시하고 객관적 자동 계약 결과와 분리한다.

확률 ECE는 사전 고정한 10개 구간과 구간별 표본 수를 보조로 제시한다. 작은 그룹의 빈 구간을 숨기지 않는다. Brier는 calibration만 측정하는 지표가 아니므로 신뢰도 그림과 함께 해석한다. 선택 오류를 검토하면서 정답을 고칠 필요가 생기면 세 군 모두 동일한 grader로 다시 채점하고 변경 사유를 공개한다. 해당 Test를 사용한 모델 튜닝은 새 테스트 없이 확정 결과로 발표하지 않는다.

## 시간과 비용의 공정한 측정

제품 지연 비교는 동일한 API 호출 위치에서 측정한다. Jev/nano의 네트워크와 Laya 추론 서버까지의 왕복을 포함한다. Laya의 장치 내부 추론 시간은 별도 breakdown이며 외부 API 왕복 시간과 같은 열에서 순위를 매기지 않는다. 가능하면 실제 사용자 요청이 들어오는 배포 지역에서 한 번 더 확인한다.

따뜻한 서버와 첫 모델 로딩을 구분하고, 캐시 설정, batch size, 동시 요청 수, 연결 재사용, 하드웨어, 시간대를 기록한다. 서버 로딩 20회 같은 소규모 cold start 확인은 범위와 중앙값 위주로 보고하고 안정적인 p95 추정이라고 부르지 않는다. 실제 품질 평가에서 이전 예측을 재사용하는 결과 캐시는 끈다. 오프라인 재채점용 raw response 보존과 warm 모델 메모리는 구별한다.

API 비용은 실행 시점의 요금 근거와 실제 사용량을 보존한다. nano의 입력/출력 및 캐시 요금, Jev의 청구 방식, worker와 embedding을 분리하고 기존 하드코딩 가격표를 최신 실제 청구라고 취급하지 않는다. 할인이나 무료 크레딧을 포함한 실지출과 표준 요금 추정치를 구분한다.

Laya는 API 토큰 비용이 0이어도 운영비가 0은 아니다. 고정 서버비, idle 시간, 요청당 전력 또는 가변비의 측정 가능 범위를 분리한다. 로컬 장치의 실제 비용을 모르면 unknown으로 두고 측정된 자원 사용량을 표시한다. 월 비용은 F + vN으로 시나리오를 계산하고, 월 요청량 N을 검증된 트래픽처럼 쓰지 않는다. 서버비 중복 배분을 피하고, 학습비는 운영비와 별도 보고한다.

성공 업무당 비용은 실패 포함 총비용 / 계약을 충족한 episode 수로 정의한다. 개발/교정 비용과 서비스 요청 비용은 별도 표로 둔다. 전체 처리 비용을 worker와 router로 나눠 라우터만 빨라져도 체감 효과가 작은 경우를 확인한다.

## 통계와 도입 판정

모든 비교는 같은 가족에 대한 paired 차이로 보고한다. 95% 신뢰구간은 family_id 전체를 재표집하는 paired cluster bootstrap으로 계산하며 반복 episode를 독립 가족처럼 세지 않는다. 초기 반복 수는 2,000 resamples로 고정하고 seed를 기록한다. 한 번의 이진 판단 정확도에는 paired discordance 분석을 보조로 쓸 수 있다. 각 모델의 별도 신뢰구간이 겹치는지만으로 차이를 판정하지 않는다.

테스트 두 후보의 우열을 공식적인 통계 검정으로 주장한다면 다중 비교 보정을 미리 정한다. 초기 보고서는 효과 크기, 신뢰구간, 가족별 개선/악화 사례를 중심으로 내고, 표본 부족을 승리나 동등함으로 해석하지 않는다.

도입 기준 초안은 다음과 같다. 실제 Test를 보기 전에 다음 버전의 protocol manifest에 수치를 확정한다.

| 항목 | 제안 기준 | 판정 |
|---|---|---|
| 핵심 계약 | 재현되는 데이터 범위 위반, 무단 변경, 잘못된 금액의 완료 주장 없음 | 한 건이라도 확인되면 전면 도입 보류. 원인을 수정한 후보는 새 버전으로 재평가 |
| 업무 성공 | A0 대비 차이의 신뢰구간 하한이 -2 percentage points 이상 | 비열등 허용 폭의 제안. 하한이 더 낮으면 표본 부족인지 실제 악화인지 구분하고 확정 도입 보류 |
| 반복 신뢰성 | pass^3의 차이와 실패 유형 함께 검토 | 평균 성공률만 좋아지고 반복 실패가 늘어난 경우 채택 근거로 쓰지 않음 |
| 실익 | 성공 업무당 비용 또는 전체 업무 p95가 사전 목표만큼 개선 | 초안 목표는 20%. 다른 자원 제약의 악화 허용 범위도 Test 전에 고정 |
| 범위 | 전체 업무 또는 특정 읽기 업무만 채택할지 개발 단계에서 명시 | Test에서 유리한 업무만 찾아 전체 우위라고 주장하지 않음 |

200개의 독립 사례에서 오류가 0건이어도 오류율 0을 증명하지 못한다. 이항 가정의 단측 95% 상한은 1 - 0.05^(1/n)이므로 n=200일 때 약 1.49%다. 핵심 경계 사례가 그보다 적으면 상한은 더 크다. 반복 세 번은 이 n을 세 배로 늘려주지 않는다. 따라서 초기 결과는 도입 후보 선별용이며 아주 낮은 실패율의 운영 보장이 아니다.

60가족 전체 업무 평가로 2 percentage points 비열등성을 입증할 수 있다고 사전 가정하지 않는다. 개발 pilot의 paired 불일치와 분산으로 표본 수를 계산하고, 테스트 공개 전 실행 규모를 확정한다. 예산상 확대가 어렵다면 결과를 exploratory 또는 inconclusive로 남긴다. 실패를 본 뒤 임계값을 낮추거나 성공할 때까지 반복해 첫 성공만 남기지 않는다.

## 실행 기록과 보고서 계약

protocol manifest에는 소스 commit과 변경 파일 hash, actual model ID와 Laya weight revision, API/SDK 버전, 원문 요청 hash, 어댑터/질문 템플릿/후처리 hash, 데이터 분할과 fixture hash, grader version, 임계값과 confidence 집계 정책, 날짜/시간대, timeout/retry/fallback, hardware/region/concurrency/cache, pricing source, 분석 seed, 예산을 포함한다. latest 별칭만 기록하지 않는다. worker를 snapshot으로 고정할 수 없으면 실제 반환 ID와 실행 시간 블록을 기록하고 그 한계를 보고한다.

시도별 레코드는 case_id, family_id, arm, episode_id, turn_id, attempt_id, 원시 응답, 확률 유무와 보정 상태, raw tools, effective tools, worker tools, degraded, fallback_reason, unsupported_reason, elapsed_ms, 토큰, pricing_status, estimated_cost, error_type을 보존한다. router 비용과 worker 비용을 한 레코드로 숨기지 않는다. 키와 인증 헤더는 저장하지 않는다. synthetic fixture만 사용하며 raw response와 추론 요청은 재채점 가능한 로컬 산출물로 보존한다.

보고서에는 계획한/실행한/지원된/채점된 분모, 업무별 표, raw/effective 도구 누락, 전체 계약 및 pass^3, 지연/비용과 확률/폴백 표, paired 신뢰구간, 모든 실패와 근거 링크, 검토자 및 미검토 항목, 후보별 판정과 한계를 포함한다. cancelled 또는 needs_review 상태를 자동 통과로 세지 않는다.

## 구현 준비 순서

1. 질문과 실행 결과 계약을 정의하고 기존 평가기의 문맥 입력, degraded 수집, unknown 비용 처리를 보완한다. 도구 보완 전후의 관측을 추가한다.
2. 신규 개발 가족을 작성하고 독립 정답을 검토한다. 기존 회귀 자료는 별도 suite로 유지한다.
3. 동일 의미의 backend adapter를 작성하고 Development에서 모델 지원 범위와 실행 비용을 확인한다.
4. Calibration, Selection, Confirmation을 사용해 정책을 정한다. 모델 버전과 분석 계획, 예산, Test 크기를 잠근다.
5. 새 A0 기준 측정과 B0/C0 라우팅 평가를 같은 실행 묶음으로 수행한다. 기준점의 과거 점수를 복사하지 않는다.
6. 전체 업무 3군을 동일한 테스트 DB 상태에서 반복 평가하고, 확률 폴백의 전체 업무 실험은 필요 시 별도 실행한다.
7. 잠근 기준으로 도입, 제한된 업무에서 추가 검증, 보류를 판정한다. 다음 튜닝을 한다면 새로운 최종 테스트를 마련한다.

최초 설계 시점에는 1~7 모두 앞으로 수행할 작업이었다. 현재 1의 입력·폴백·비용 계약 보완, 2의 Codex 검토 development 12문항, 3의 opt-in adapter와 첫 Laya 라우팅 실험을 구현했다. 사람 검토, 새 nano 기준선, Jev 실측, 보정·정책 선택, 전체 업무 평가와 최종 Test는 아직 남아 있다. 첫 라우팅 결과를 36개 전체 업무 episode나 최종 도입 근거로 표현하지 않는다.
